# 2026-10-14 Сокет против опроса и память на сжатие кадров

Вопрос: насколько живой канал дешевле опроса. Одна и та же нагрузка на оба транспорта, потом память процесса и
лесенка в контейнере как на проде. Сервер — `main` на `c7172bb`. Машина: облачный контейнер, 4 ядра, 16 ГБ.

## Одинаковая нагрузка: 1 200 игроков

Сервер «на машине» (`perf/server.sh`: куча 480 МБ, Serial GC, 2 ядра для JVM), перед каждым прогоном перезапущен.
Счётчики сервера (`/actuator/prometheus`) и байты интерфейса `lo` — за 60 с с сотой секунды прогона, потом 40 с
профиля `cpu`; память процесса (RSS) — отдельным прогоном на 110-й секунде.

```bash
./gradlew :perf:gatlingRun --simulation app.hovanki.perf.OrdinaryGames -Pperf.games=40 -Pperf.rampSeconds=20 -Pperf.minutes=4
./gradlew :perf:gatlingRun --simulation app.hovanki.perf.OrdinaryGames -Pperf.transport=socket -Pperf.games=40 -Pperf.rampSeconds=20 -Pperf.minutes=4
```

| | опрос | сокет со сжатием | сокет без сжатия |
|---|---|---|---|
| синхронизаций в секунду | 400 | 400 | 400 |
| CPU на синхронизацию, мс | 0,80 | 0,53 | 0,44 |
| CPU сервера, % одного ядра | 32 | 21 | 18 |
| аллокации на синхронизацию, КБ | 88 | 58 | 48 |
| трафик на синхронизацию, КБ | 2,4 | 0,5 | 6,5 |
| время внутри `GameService.sync`, мкс | 58 | 67 | 64 |
| /sync p95 / p99, мс | 2 / 5 | 1 / 4 | 1 / 3 |
| память процесса (RSS), МБ | 360 | 780 | 459 |
| ошибок | 0 | 0 | 0 |

Трафик — байты `lo` в обе стороны вместе с заголовками TCP/IP, делённые на синхронизации. Опрос — с gzip ответов и
заголовками HTTP на каждом запросе. Сокет со сжатием — permessage-deflate, который Gatling просит, как OkHttp на Android:
словарь живёт между кадрами, и похожий снимок ужимается в сотни байт. Без сжатия кадр — чистый JSON снимка. Память до
нагрузки — около 310 МБ на всех трёх.

Сама игра стоит одинаково (около 60 мкс). Куда уходит CPU (профиль `cpu`, доля сэмплов):

| | опрос | сокет со сжатием |
|---|---|---|
| gzip / deflate | 30 % | 20 % |
| Spring: маршрут, фильтры, аргументы | 28 % | 1 % |
| JSON | 11 % | 19 % |
| `GameService.sync` | 7 % | 13 % |
| Tomcat: HTTP / WebSocket | 6 % | 17 % |
| сеть (NIO) | 10 % | 14 % |

Сокет экономит то, что опрос делает на каждом запросе: маршрут Spring, фильтры, заголовки и gzip каждого ответа с нуля.

## Память сжатия

Сокет со сжатием на 1 200 игроках, с `-XX:NativeMemoryTracking=summary`: JVM учитывает 516 МБ (куча — 338 МБ),
RSS — 780 МБ. Около 264 МБ вне учёта JVM — это zlib: Tomcat держит `Deflater` и `Inflater` на каждый сжатый сокет всё
время его жизни, около 220 КБ на сокет. В куче их не видно, поэтому прошлый замер (`char[]` в гистограмме кучи) их
пропустил. Окно и уровень памяти `java.util.zip.Deflater` не настраиваются, а в Tomcat 11 нет настройки, чтобы не
соглашаться на расширение.

## Лесенка в контейнере как на проде

`perf/up.sh --container`: 2 ядра, 640 МБ, куча 75 % от лимита (как `deploy/compose.yaml`). Ступени по 10 игр (300
игроков) на минуту, память — `docker stats` каждые 15 с.

```bash
perf/up.sh --container
./gradlew :perf:gatlingRun --simulation app.hovanki.perf.OrdinaryGames -Pperf.transport=socket \
  -Pperf.games=10 -Pperf.steps=6 -Pperf.rampSeconds=20 -Pperf.minutes=1
```

| игроков на сокете | со сжатием, МБ | без сжатия, МБ |
|---|---|---|
| 300 | 410 | 326 |
| 600 | 553 | 375 |
| 900 | 638, затем контейнер убит (`OOMKilled`, код 137) | 417 |
| 1 200 | — | 448 |
| 1 500 | — | 525 |
| 1 800 | — | 557 |

Со сжатием лесенка остановилась на 900 (p95 выше 50 мс), и контейнер убило нехваткой памяти. Без сжатия прошла все 6
ступеней: p95 1 мс, p99 4 мс, 0 ошибок. Прошлая лесенка «на машине» (журнал
[2026-10-14-ordinary-games.md](2026-10-14-ordinary-games.md)) дошла до 1 800 и со сжатием, но без лимита памяти.

## Что поменяли

`NoSocketCompression` прячет от Tomcat заголовок `Sec-WebSocket-Extensions` на маршруте сокета, и сжатие не
согласуется. Цена — трафик: около 6,5 КБ на синхронизацию, примерно 8 МБ на час игры на телефон (опрос — около 3 МБ).
Своё сжатие кадра без состояния на сокет (как gzip у опроса, около 2 КБ) — если трафик станет важен; для него нужны
правки в приложении.
