## Commands

```bash
./gradlew spotlessApply                    # format (ktlint); CI runs spotlessCheck
./gradlew check                            # all tests + checks available on this OS, without the e2e scenarios
./gradlew :shared:jvmTest :radar:jvmTest :device:jvmTest :clientCore:jvmTest :server:test   # fast feedback loop
./gradlew :e2e:test                        # e2e scenarios: bots play whole games (~6 min); reports in e2e/build/reports/e2e/
./gradlew :e2e:test -Pe2e.slow=true        # plus the slow ones (tag `slow`: default rules in real time, a big game of 300 bots), as nightly
./gradlew :e2e:test -Pe2e.transport=socket # every scenario with the bots on the live channel (WebSocket) instead of polling
./gradlew :e2e:devices                     # app on the emulators already running (Android Studio) + bots; needs Maestro
e2e/run-devices.sh --android 2 --bots 3    # app on 2 emulators + bots (needs KVM + Maestro; --ios 1 on macOS); ~15 min in CI
docker compose -f deploy/compose.dev.yaml up -d   # local PostgreSQL for bootRun (tests bring their own)
./gradlew :server:bootRun                  # server on :8080, health at /actuator/health; emailed codes go to its log
./gradlew :androidApp:installDebug         # Android debug build
./gradlew :androidApp:assemblePreview      # tester build (release code, app.hovanki.preview); CI: preview.yml with -Phovanki.channel=preview
./gradlew :androidApp:testPreviewUnitTest  # the preview build's Sentry glue (part of check)
./gradlew :shared:iosSimulatorArm64Test    # macOS only
```

CI on push (`ci.yml`) is fast: spotlessCheck, `check`, Android and iOS builds. `check` does not depend on `:e2e:test`; the e2e bots and the device layer run only nightly and on demand (`.github/workflows/nightly.yml`, Actions → Nightly → Run workflow on any branch, `suite` = all / bots / devices). A failed scheduled run opens an issue labelled `nightly-failure`. `ios-testflight.yml` signs the widget extension `HovankiLive` (`<app>.live`) with `IOS_LIVE_PROVISIONING_PROFILE_BASE64` once its target is in the project; without the target the build is unchanged, without the secret it is unsigned and not uploaded. Tester builds: `preview.yml` builds them for the main server of `gradle.properties` (there is no staging server for now; the optional repo variable `STAGING_SERVER_URL` points them to one) and publishes them with `-Phovanki.channel=preview` and the Sentry DSN: the signed APK on the pre-release, the AAB on the Google Play internal track of `app.hovanki.preview` (secret `PLAY_SERVICE_ACCOUNT_JSON`), iOS to TestFlight; the iOS steps are the reusable `ios-testflight.yml`, also called by `release.yml` for the App Store build (production server, version from the tag, build number `100000 + run number`). The TestFlight build of `preview.yml` must never be submitted to the App Store. Gradle properties reach Xcode's Kotlin framework build through `gradle.properties` of the Gradle user home; after the build both apps are searched for the expected server address. After a tag `vX.Y.Z` raise `MARKETING_VERSION` in `iosApp/Configuration/Config.xcconfig`.

iOS (framework, app, simulator tests) builds only on macOS with Xcode 26.4+; on Linux iOS targets are skipped (`kotlin.native.ignoreDisabledTargets=true`). Don't try to fix iOS-only failures blind — say so.

## Conventions

- **Shared rules live in `:shared`** and are used by both client and server: thresholds (`GameRules`), zone math (`ZoneSchedule.stateAt`), GPS filtering, TOTP. Never re-implement them on one side.
- **Feature flags:** everything from ADR 0012/0013 is behind `ServerFeature` (off by default, switched by an admin in the admin, `FeatureFlags`) and `GameSettings.features` (the host, in the lobby); `FeatureFlags.requireAllowed` refuses a setup with a feature that is off (`FEATURE_DISABLED`), a running game keeps its settings. `RADIO_LAB` and `FIELD_LOG` (ADR 0018, the field log of real games) are server-wide, not a game's choice: their routes answer 404 while off. The radio lab's run list in the admin is lab runs only; a game's field run is listed and shown by `/api/v1/admin/field/games`. The e2e bots turn everything on with `enableAllFeatures()`, except `LIVE_SOCKET` (ADR 0015: server-wide, not a game's choice; on in e2e with `-Pe2e.transport=socket`); `FIELD_LOG` on is harmless there, only bots with `fieldLog` join; unit tests pass the features in the settings.
- **Server is authoritative.** It decides phases, catches and visibility; `Game.snapshotFor(viewer)` never includes positions the viewer may not see. The client only renders and hints.
- **Protocol changes must stay backward compatible**: add fields with default values; never rename or remove fields, enum values or routes. A new enum value breaks old clients when the property has no default (e.g. `VisibleLocation.reason`) — add a new defaulted field instead, or a new API version.
- **All timestamps are server time** (epoch millis). The client converts via `ServerClock`; never use the device clock for protocol data, deadlines or TOTP.
- **`Game` is a pure domain object**: no Spring, no threads, time passed in as `nowMillis`. Time-based transitions go into `advance(now)`; no background tickers inside it: `GameDeadlines` wakes a game at `Game.nextDueMillis` through `GameService.wake`. Access goes through `GameService.update(...)` (lock + advance + snapshot, then the pokes and the next deadline after the lock). A new state change a player should see soon adds to `Game`'s pokes (`Pokes`).
- **Safe area:** screens keep clear of the system bars, cutouts and the keyboard through `WindowInsets.appSafeDrawing` / `Modifier.appSafeDrawingPadding()` (`ui/common/SafeArea.kt`), never `safeDrawing` directly: on iOS Compose can lose the safe area after the app returns from the background, and the iOS twin also measures the window (`docs/design.md`, «Отступы экрана»). The Compose string resources use typographic quotes (’ “ ”), never `\'`: `:composeApp:checkStringResources` (part of `check`) fails on it.
- **No platform code in `commonMain`.** Platform services are interfaces in `commonMain`, implemented in `androidMain`/`iosMain`, bound via Koin. `expect`/`actual` only for small glue.
- **GDPR:** location data and chat stay in memory and are deleted with the game. Exceptions: routes of players who turned on «save my routes» themselves (explicit consent, off by default), kept 90 days and shown to nobody but their owner (`docs/adr/0007-game-history-and-routes.md`); and the recording of every ordinary game played to its end (`docs/adr/0011-spectators-and-recordings.md`): everybody's replay track, kept 90 days, readable only by that game's players with an account, a player's way deleted with their account (`ON DELETE CASCADE`), never shown to staff or used for analytics, never recorded for big games; the lobby tells everybody; and the radio lab's run logs (ADR 0017): test phones of the debug build only, no coordinates, kept 90 days after the run, readable by admins only (raw download with a reason in the audit log; the report keeps labels, models and numbers); the server strips `lat`/`lon` from a lab run's lines; and the **field log** (ADR 0018): only the field build (`preview`) on a server with `FIELD_LOG`, after the tester's explicit consent (`ClientStorage.fieldConsentAt`, `lab_devices.consent_at`); coordinates (only in `gps` events), radar, RSSI and the phone's events per player, in a game's run (`lab_runs.kind = GAME`), deleted whole 90 days after the game (`DataRetention`), the player's device and chunks with the account (`ON DELETE CASCADE`), admins only (raw with a reason in the audit log), never in production analytics; withdrawing the consent drops what has not gone up yet. Sentry (the field build and the staging server only) gets errors only: exception types, scrubbed messages cut to 300 characters (`SentryScrubber`), stack frames, app version, phone model and OS, screen-name breadcrumbs; never user, request, extras, tags, coordinates, tokens, emails, nicknames or chat. Game results are numbers without coordinates. Never store or log positions beyond these, never expose one player's history or saved route to another. The replay: a finished round's tracks (`ReplayTrack`, in memory) go to that game's players until the game is deleted (ADR 0007, section 6). An SOS (ADR 0019) shows every player of that game the caller's last fix while it is on (`GameSnapshot.sos`), in memory only: never stored, logged, in the field log or shown to staff (they see a count). An open game (the host's choice) shows everybody's positions to its spectators, the host's delay behind, and to admins live; spectators are in memory only and never get anything newer than the delay allows (`Game.spectatorSnapshot`, e2e `SnapshotAudit.checkSpectator`). Accounts live in PostgreSQL with the retention periods of `docs/adr/0004-accounts-friends-chat.md` (`DataRetention`); personal data in a new table needs a retention period and must go with the account (`ON DELETE CASCADE`). Never log coordinates, tokens, passwords, emailed codes, email addresses or chat text. The radar's tokens, sightings and `DeviceReport`s stay in memory with the game; RSSI is never logged or exposed to any player; `DeviceReport.model` is sent only in a game with the radar; `radio_calibration` holds aggregates by phone model only (no game, player, time or position). Paid extras (`entitlements`, ADR 0023) go with the account and are deleted once they end. The device stores only the game session, the account (token + profile), the guest name, the host's last game setup (sizes and times, no place), the map's look (theme, 3D houses, relief) and, in the field build, when the tester agreed (`fieldConsentAt`), through `ClientStorage`/`SecureStore` (Keystore/Keychain, `docs/adr/0002-session-storage.md`); never store coordinates or chat on the device.
- **Database:** migrations are only ever appended (`V<n>__*.sql`); never edit one that was applied. Times come from the injected `Clock`, not SQL `now()`. Games never touch the database on the hot path (`sync`); write after releasing the game lock. Tests get a fresh database from `TestPostgres` (embedded PostgreSQL 17, or `HOVANKI_TEST_DATABASE_URL` pointing at a running server; the `.claude/` SessionStart hook sets it in cloud sessions).
- **The admin is the most dangerous surface** (`docs/adr/0008-admin.md`): every `/api/v1/admin` route takes a `Staff` parameter (the session cookie; never the app's account token) except the login steps, checks the role in `AdminService` (moderator vs admin), needs a reason and writes `AuditLog` in the same transaction as the change. Staff never see coordinates, routes, recordings, chat outside reports, passwords or tokens — the one exception: admins watch an open game live, with a reason in the audit log (ADR 0011); emails only masked, in full to admins with a reason. The page puts server data in as text only (`textContent`, never `innerHTML`), loads nothing from other hosts (CSP), and every request carries `X-Hovanki-Admin: 1`. `ADMIN` is only ever set on the server (SQL), never through the API.
- **Debug/test hooks never reach production:** the observer endpoints (games, emails, reports, roles) exist only with the Spring profile `e2e`; keep `DebugEndpointAbsentTest` green. Test tags (`TestTags`) and `LaunchOptions` must not change release behavior: launch parameters are read only in debug builds. The Android `preview` build type (tester builds, `preview.yml`) is release plus its own application id and shares the no-op twins in `androidApp/src/release`. The field log, the consent screen, «Something is wrong», the survey and Sentry exist only in the field build (`BuildInfo.channel == preview`, never `isDebug`); release and debug never show or start them; the Sentry SDK is physically in the Android `preview` build only. The lab's screen reaches `preview` for staff only (`labAccess`, a server with `RADIO_LAB`; there only staff join a lab run, `hovanki.lab.join-staff-only`), without «Share»/«Export». iOS dev exceptions (local-network ATS) are added to Debug only by `iosApp/Configuration/debug-info-plist.sh`.
- **Build-time settings** come from Gradle properties via the generated `BuildConstants` in `:composeApp` (`hovanki.serverUrl`: the one server of non-debug builds, required, https only; `hovanki.channel`: `release` (default) or `preview`, anything else fails the build; `hovanki.sentryDsn`: the field build's Sentry project, https or empty, never needed to build; `hovanki.sentryProguardUuid`: the R8 mapping's id in the Android preview manifest). Don't hardcode server addresses; non-debug builds talk HTTPS only. Debug builds use the development machine or `LaunchOptions.server`.
- **Run the long tests yourself before a PR** (CI on push doesn't): changed rules, protocol or client–server behavior → `./gradlew :e2e:test` (~6 min, works in a cloud container without KVM); changed UI or platform code (`:composeApp`, `androidApp`, `iosApp`, Maestro flows) → `./gradlew :e2e:devices` on local emulators if you have them, or trigger `nightly.yml` manually on your branch (`suite=devices`, only the scenario you need). Say in the PR what you ran. See `docs/ci-cd.md`.
- **Tests next to the code:** `shared/src/commonTest`, `device/src/commonTest` and `clientCore/src/commonTest` (run on JVM and iOS), `radar/src/jvmTest` and `device/src/jvmTest` (the module boundaries), `shared/src/jvmTest` for JDK cross-checks, `server/src/test` (`GameTest` for rules with an explicit `now`, `GameApiTest` for HTTP round trips with MockMvc). New rule → unit test in `GameTest` or `commonTest`, and an e2e scenario in `e2e/src/test` when it spans client and server. A bug found by an e2e scenario is fixed in the game or server with a test, never worked around in the scenario.
- **Style:** ktlint `intellij_idea`, max line 120, trailing commas (see `.editorconfig`). Run `./gradlew spotlessApply` before committing.
- **Gradle:** configuration cache is on — no configuration-time side effects; no hardcoded versions in build scripts.

## AGP 9 / KMP structure

- Never apply `org.jetbrains.kotlin.android` (kotlin-android) in `androidApp`: AGP 9 has built-in Kotlin.
- Never add `androidTarget()` in KMP modules: they use `com.android.kotlin.multiplatform.library` and the `kotlin { android { ... } }` block.
- Android/shared bytecode is JVM 17, the server toolchain is JDK 21.

## When you change things

- New endpoint: `ApiRoutes` + DTO in `:shared` → `Game`/`GameService` (or an account/social service with an `AuthenticatedUser` parameter) + controller in `:server` → `GameApi`/`AccountApi`/`SocialApi` + `GameSessionManager`/`AccountManager`/`SocialManager` in `:clientCore` → UI in `:composeApp` → API table in `docs/architecture.md`. New errors: an `ErrorReason` on the existing `ErrorCode` (`ApiError.reason`), never a new `ErrorCode`.
- Behavior, commands or setup changed → update `README.md` / `docs/`. Big decisions → new ADR in `docs/adr/NNNN-*.md`.
- Something a player can see or do is new (a feature, a milestone) → add an entry at the end of `docs/devlog.md`, the marketing log: Russian, plain words, what the player gets, with a 🎬 hint how to film it; see its «Как добавить запись». Not working on a phone yet → its «Пока нет» section.
- Recipes for endpoints, platform services and screens: `docs/architecture.md`, section «Как добавить…».
