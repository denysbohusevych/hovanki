# CLAUDE.md

Hovanki: street hide-and-seek for Android + iOS. Kotlin Multiplatform + Compose Multiplatform client, Spring Boot server, shared Kotlin module for protocol and rules. Docs are in Russian (`docs/`), code and comments in English.

Read first: `docs/architecture.md` (how it works), `docs/adr/` (why: 0001 stack and game rules, 0002 session storage, 0003 map and buildings, 0004 accounts, friends, groups and chat; 0005 is a draft for the future: game modes and other games on one platform, not implemented; 0006 visual style; 0007 game history, saved routes and statistics; 0008 the staff admin: roles, login, moderation; 0009 game setup, the glow, the zone by streets and the lobby on the server; 0010 the zone's capacity by its ground and big games; 0011 spectators of open games, admins watching them live, and the recordings of games; 0012 the radar by Bluetooth and UWB, the pulse from the pocket, the phones' capabilities in the lobby and the server feature flags the operator switches in the admin; 0013 quests, sparks, perks, the board and the phone's sensors — both implemented behind the flags, their «Отличия реализации» sections say where the code differs from the plan; the spike on real phones is still ahead; 0014 the settings and lobby redesign (the draft's map on top, less text, animated hints, the zone's center by a pin) and the buildings the host opens for hiding — implemented, its «Отличия реализации» says what differs, the server's preview of a draft zone is still ahead), `docs/metrics.md` (what can be measured for analytics, what is collected, what never is), `docs/design.md` (UI spec: colors, fonts, components, screens, animations, and the plan to redo the UI), `docs/roadmap.md` (what is missing).

## Layout

- `shared/` — KMP (jvm, android, iosArm64, iosSimulatorArm64). `protocol/` DTOs + `ApiRoutes` + `protocolJson` (games, `Accounts.kt`, `Social.kt`, chat, `Features.kt`: `ServerFeature`, `GameFeatures`, `DeviceReport`; `Radar.kt`, `Board.kt`), `totp/` catch codes and staff TOTP (pure-Kotlin SHA-1/HMAC), `qr/` QR encoder (pure Kotlin), `geo/`, `rules/` (`LocationTrack`, `ZoneRules`, `CatchRules`, `BuildingMap`/`BuildingRules`, zone schedule, `ZoneArea`/`StreetZone`: a circle or the zone by streets, `Glow`: when the hiders glow, `GameSetup`/`SettingsLimits`: the host's choices and what the server accepts, `withEndgame`: the zone squeezes to the end of the search, `Capacity`: how many players a zone fits by its ground, `BigGameSetup`/`BigGameLimits`: big games, `AccountRules`, `GroupRules`, `ChatRules`, `RouteRecorder`: a route's points and distance for the history, `Proximity.kt`: radar tokens, bands, smoothing and the pulse's pace, `Quests.kt`: the quest and perk catalogs and the board's rules, `CheckpointPayload`, `OpenBuildings`: the buildings the host opened for hiding, split the same way on the server and the phones); `protocol/Spectators.kt` (watching an open game).
- `server/` — Spring Boot. Games stay in memory; accounts, friends, blocks, groups, chat reports, the history of finished games and the big games' schedule and sign-ups are in PostgreSQL (`JdbcClient`, Flyway migrations in `src/main/resources/db/migration`). `api/` thin controllers (`GameController`, `AccountController`, `SocialController`) + error mapping + bearer auth (game token → `PlayerRef`, account token → `AuthenticatedUser`), `game/` domain (`Game`, with the chat, the round's tracks for the replay and the recording, `ReplayTrack`, the spectators of an open game; `Radar.kt`: one smoothed signal per pair and the bands, `RadioCalibration.kt`: the radar's readings by phone model, `Board.kt`: the board's items, quests, perks and sparks), `GameService` (locking), `GameRegistry` (in memory; player and spectator tokens), `GameJanitor` (deletes old games), `account/` (`AccountService`, repositories), `mail/` (`EmailSender`: smtp / log / recording), `social/` (friends, blocks, groups; `InviteRegistry` in memory), `history/` (`HistoryWriter` saves a finished game's `GameRecord` off the request thread, `HistoryService`: own stats, games, routes, consent, the recordings of the caller's games), `moderation/` (`ReportRepository`, bans and chat bans: `SanctionService`), `admin/` (the staff admin: `StaffAuthService` — password + TOTP, admin sessions; `AdminService`; `AuditLog`; `SecretBox` encrypts the TOTP secrets; `AdminController` + `AdminWebConfig` in `api/`; the page is static `src/main/resources/static/admin/` at `/admin`, plain JS without a build), `ratelimit/` (`RateLimiter`), `features/` (`FeatureFlags`: the server-wide feature flags the operator switches in the admin, table `feature_flags`, cached in memory, checked at game creation and settings — `FEATURE_DISABLED`), `radio/` (`RadioCalibrationRepository`: table `radio_calibration`, aggregates by model only, written by `HistoryWriter`), `db/` (`DataRetention`), `buildings/` (`BuildingLoader`: the zone's building outlines at game creation and after the host changes the zone; `hovanki.buildings.source` = tiles / overpass / fake / off), `map/` (`VectorTiles`: the players' map tiles from OpenFreeMap with an own MVT decoder and a cache; `StreetZoneBuilder`/`StreetZoneLoader`: the zone by streets from the `transportation` layer; `hovanki.map.streets` = tiles / fake / off; `TerrainReader`/`TerrainLoader`: the ground under a zone for its capacity, `hovanki.map.terrain` = tiles / fake / off), `bigGames/` (big games made by admins, hosted by the server: `BigGameService` with the schedule, sign-ups and the lobby, `BigGameScheduler`, `DrawnZone`, `RestartHoldEndpoint` at `/actuator/restarthold` that `hovanki-update.sh` asks before a restart). `TestPostgres` is in the `testFixtures` source set (used by `:e2e` too).
- `clientCore/` — KMP (jvm, android, iosArm64, iosSimulatorArm64), client logic without UI: Ktor `GameApi`/`HttpGameApi`, `AccountApi`, `SocialApi`, `GameConnection`/`PollingGameConnection`, `LocationOutbox`, `ServerClock`, `GameSessionManager` (saves the session and resumes it after a restart, chat), `AccountManager` (the logged-in account, `AccountCredentials`), `SocialManager` (friends, groups, polled inbox), `HistoryManager` (own stats, game history, saved routes, «save my routes», game recordings), `SpectatorManager` (watching an open game: `SpectatorApi`, polled, nothing saved), `BigGameManager` (the big games of «Play», sign-ups), `session/Chat.kt`, `session/Results.kt` (awards, the replay), `tracking/HiderAlerts` (when the hider's alerts vibrate from the pocket), `tracking/CarryMonitor`, `PocketPulse`, `ActivityMonitor` (with `ActivityClassifier`: running by the accelerometer), `radio/ProximityRadio` (Bluetooth: advertise the token, scan) and `radio/PrecisionRadio` (UWB, `NoopPrecisionRadio` everywhere), `device/DeviceInfo`, `session/Radar.kt` (the band for the screen); `GameSessionManager` runs the radio by phase and settings, puts sightings and the `DeviceReport` into `sync` and beats the pulse from the seekers' tokens; `ClientStorage` (also `radarEnabled`), `LocationProvider`/`BackgroundTracker`/`SecureStore` interfaces. No Compose, no platform code; the JVM target is for headless e2e bots.
- `composeApp/` — KMP library (`com.android.kotlin.multiplatform.library`): Compose UI (welcome/login, location consent, email verification, main screen with tabs, lobby/game/results, full-screen panels for chat, invites, the host's game settings (`ui/settings/`: the draft on the map, tabs Zone / Time / More, «What changes», `Explainers` — Canvas loops behind every «?», «Buildings in the zone» to open buildings for hiding; the extras only those the server has on), the lobby's «Where we play» map, the host's board (map with tap-to-place, the QR code of a scan checkpoint, custom quests), quests and perks in the round, groups, game history, a saved route and a game's recording; the spectator's screen; the lobby's feature chips, radar card and capability tags, the round's beating radar chip, sparks and hint chips, checkpoint scanning by camera, decoy placement on the map; an invite banner over the lobby and the results; map: `GameMap`, maplibre-compose + OpenFreeMap tiles), Koin, Ktor engines, platform services (`LocationProvider`, `BackgroundTracker` with the hider's alert notifications, `SecureStore` — Android Keystore / iOS Keychain, `ProximityRadio` — `AndroidProximityRadio` on `android.bluetooth.le` (seekers advertise an iBeacon frame, hiders the game's service) / `IosProximityRadio` on CoreBluetooth + CoreLocation ranging (written without a build), `PocketPulse` — `Vibrator` with the screen off (the foreground service has the `connectedDevice` type) / system vibration on screen and silent notifications in the background, `CarryMonitor`, `ActivityMonitor`, `DeviceInfo`, `BluetoothPermission`, `CatchCodeScanner` — CameraX + ZXing / AVFoundation, `ShareSheet` — the system «Share» menu). No dBm number is verified on real phones yet (ADR 0012 §8). The server address is fixed at build time (`BuildConstants`), no address field.
- `androidApp/` — thin Android entry point (`Application`, `MainActivity`).
- `e2e/` — JVM end-to-end tests: `BotPlayer` runs `:clientCore` (Ktor/OkHttp) on a simulated phone (`FakeGps` + `Route`/`GpsNoise`, `DeviceClock`, `FakeNetwork`, `FakeRadio` in the scenario's `RadioWorld` — `bot/Radio.kt`: who hears whom by the bots' true positions, a log-distance model with noise and −12 dB per phone in a pocket, an iPhone in a pocket heard by iPhones only; bots have `platform`, `carry`, `pulse`, Bluetooth on/off); `Scenario` DSL; `Observer` reads the server's debug endpoints (Spring profile `e2e` only: games with the radar pairs, emailed codes, reports, making an account staff, switching the server features); `StaffConsole` is a staff member in the admin (also the feature flags). `SnapshotAudit` checks every response's privacy, the radar's and the board's too. Scenarios: `RadarTest`, `ProximityCatchTest`, `FeatureFlagTest` (own server), `BoardTest`, `OpenBuildingsTest`. Bots have accounts (`AccountManager`, `SocialManager`) with unique nicknames per run. Tests start the server in-process on a random port on a fresh `TestPostgres` database; `HOVANKI_E2E_SERVER_URL` targets an external one. Device layer: `e2e/run-devices.sh` builds the server and the debug app and starts emulators/simulators, then `e2e devices` (`src/main/.../devices/`) starts the server jar next to its own PostgreSQL (`LocalPostgres`), registers the host's account (`DeviceAccounts`), and drives the devices with Maestro flows (`e2e/maestro/`) mixed with bots: the host logs in from launch options, the others join as guests. `./gradlew :e2e:devices` (and the `.run/` configurations in Android Studio) does the same on the emulators already running, without bash. See `docs/e2e.md`; step-by-step local runs and troubleshooting in `docs/e2e-local.md`.
- `iosApp/` — Xcode project, SwiftUI shell around `MainViewControllerKt.mainViewController()`; see `iosApp/README.md`. Settings in `Configuration/Config.xcconfig` (fixed bundle id `app.hovanki.ios`), per-machine overrides in git-ignored `Local.xcconfig`.
- `deploy/` — server deployment: one EC2 VM with `compose.yaml` (server + Caddy for TLS; database, secrets and SMTP in `.env`), the database on Amazon RDS for PostgreSQL in the same region (TLS verified with the RDS CA bundle `rds-ca.pem`, backups and point-in-time recovery by RDS), `compose.dev.yaml` (PostgreSQL only, for local development), `aws-user-data.sh`, and `hovanki-update.{sh,service,timer}` that pull the `main` image, which `ci.yml` publishes after every push to `main`, and restart the server when it changed (so every push to `main` ends running ordinary games; it waits while a big game is on); see `docs/deploy.md`.
- Versions: only in `gradle/libs.versions.toml`. Modules reference each other via typesafe accessors (`projects.shared`).

## Commands

```bash
./gradlew spotlessApply                    # format (ktlint); CI runs spotlessCheck
./gradlew check                            # all tests + checks available on this OS, without the e2e scenarios
./gradlew :shared:jvmTest :clientCore:jvmTest :server:test   # fast feedback loop
./gradlew :e2e:test                        # e2e scenarios: bots play whole games (~6 min); reports in e2e/build/reports/e2e/
./gradlew :e2e:test -Pe2e.slow=true        # plus the slow ones (tag `slow`: default rules in real time, a big game of 300 bots), as nightly
./gradlew :e2e:devices                     # app on the emulators already running (Android Studio) + bots; needs Maestro
e2e/run-devices.sh --android 2 --bots 3    # app on 2 emulators + bots (needs KVM + Maestro; --ios 1 on macOS); ~15 min in CI
docker compose -f deploy/compose.dev.yaml up -d   # local PostgreSQL for bootRun (tests bring their own)
./gradlew :server:bootRun                  # server on :8080, health at /actuator/health; emailed codes go to its log
./gradlew :androidApp:installDebug         # Android debug build
./gradlew :androidApp:assemblePreview      # tester build (release code, app.hovanki.preview); CI: preview.yml
./gradlew :shared:iosSimulatorArm64Test    # macOS only
```

CI on push (`ci.yml`) is fast: spotlessCheck, `check`, Android and iOS builds. `check` does not depend on `:e2e:test`; the e2e bots and the device layer run only nightly and on demand (`.github/workflows/nightly.yml`, Actions → Nightly → Run workflow on any branch, `suite` = all / bots / devices). A failed scheduled run opens an issue labelled `nightly-failure`.

iOS (framework, app, simulator tests) builds only on macOS with Xcode 26.4+; on Linux iOS targets are skipped (`kotlin.native.ignoreDisabledTargets=true`). Don't try to fix iOS-only failures blind — say so.

## Conventions

- **Shared rules live in `:shared`** and are used by both client and server: thresholds (`GameRules`), zone math (`ZoneSchedule.stateAt`), GPS filtering, TOTP. Never re-implement them on one side.
- **Feature flags:** everything from ADR 0012/0013 is behind `ServerFeature` (off by default, switched by an admin in the admin, `FeatureFlags`) and `GameSettings.features` (the host, in the lobby); `FeatureFlags.requireAllowed` refuses a setup with a feature that is off (`FEATURE_DISABLED`), a running game keeps its settings. The e2e bots turn everything on with `enableAllFeatures()`; unit tests pass the features in the settings.
- **Server is authoritative.** It decides phases, catches and visibility; `Game.snapshotFor(viewer)` never includes positions the viewer may not see. The client only renders and hints.
- **Protocol changes must stay backward compatible**: add fields with default values; never rename or remove fields, enum values or routes. A new enum value breaks old clients when the property has no default (e.g. `VisibleLocation.reason`) — add a new defaulted field instead, or a new API version.
- **All timestamps are server time** (epoch millis). The client converts via `ServerClock`; never use the device clock for protocol data, deadlines or TOTP.
- **`Game` is a pure domain object**: no Spring, no threads, time passed in as `nowMillis`. Time-based transitions go into `advance(now)`; no background tickers. Access goes through `GameService.update(...)` (lock + advance + snapshot).
- **Safe area:** screens keep clear of the system bars, cutouts and the keyboard through `WindowInsets.appSafeDrawing` / `Modifier.appSafeDrawingPadding()` (`ui/common/SafeArea.kt`), never `safeDrawing` directly: on iOS Compose can lose the safe area after the app returns from the background, and the iOS twin also measures the window (`docs/design.md`, «Отступы экрана»). The Compose string resources use typographic quotes (’ “ ”), never `\'`: `:composeApp:checkStringResources` (part of `check`) fails on it.
- **No platform code in `commonMain`.** Platform services are interfaces in `commonMain`, implemented in `androidMain`/`iosMain`, bound via Koin. `expect`/`actual` only for small glue.
- **GDPR:** location data and chat stay in memory and are deleted with the game. Exceptions: routes of players who turned on «save my routes» themselves (explicit consent, off by default), kept 90 days and shown to nobody but their owner (`docs/adr/0007-game-history-and-routes.md`); and the recording of every ordinary game played to its end (`docs/adr/0011-spectators-and-recordings.md`): everybody's replay track, kept 90 days, readable only by that game's players with an account, a player's way deleted with their account (`ON DELETE CASCADE`), never shown to staff or used for analytics, never recorded for big games; the lobby tells everybody. Game results are numbers without coordinates. Never store or log positions beyond these, never expose one player's history or saved route to another. The replay: a finished round's tracks (`ReplayTrack`, in memory) go to that game's players until the game is deleted (ADR 0007, section 6). An open game (the host's choice) shows everybody's positions to its spectators, the host's delay behind, and to admins live; spectators are in memory only and never get anything newer than the delay allows (`Game.spectatorSnapshot`, e2e `SnapshotAudit.checkSpectator`). Accounts live in PostgreSQL with the retention periods of `docs/adr/0004-accounts-friends-chat.md` (`DataRetention`); personal data in a new table needs a retention period and must go with the account (`ON DELETE CASCADE`). Never log coordinates, tokens, passwords, emailed codes, email addresses or chat text. The radar's tokens, sightings and `DeviceReport`s stay in memory with the game; RSSI is never logged or exposed to any player; `DeviceReport.model` is sent only in a game with the radar; `radio_calibration` holds aggregates by phone model only (no game, player, time or position). The device stores only the game session, the account (token + profile), the guest name and the host's last game setup (sizes and times, no place), through `ClientStorage`/`SecureStore` (Keystore/Keychain, `docs/adr/0002-session-storage.md`); never store coordinates or chat on the device.
- **Database:** migrations are only ever appended (`V<n>__*.sql`); never edit one that was applied. Times come from the injected `Clock`, not SQL `now()`. Games never touch the database on the hot path (`sync`); write after releasing the game lock. Tests get a fresh database from `TestPostgres` (embedded PostgreSQL 17, or `HOVANKI_TEST_DATABASE_URL` pointing at a running server; the `.claude/` SessionStart hook sets it in cloud sessions).
- **The admin is the most dangerous surface** (`docs/adr/0008-admin.md`): every `/api/v1/admin` route takes a `Staff` parameter (the session cookie; never the app's account token) except the login steps, checks the role in `AdminService` (moderator vs admin), needs a reason and writes `AuditLog` in the same transaction as the change. Staff never see coordinates, routes, recordings, chat outside reports, passwords or tokens — the one exception: admins watch an open game live, with a reason in the audit log (ADR 0011); emails only masked, in full to admins with a reason. The page puts server data in as text only (`textContent`, never `innerHTML`), loads nothing from other hosts (CSP), and every request carries `X-Hovanki-Admin: 1`. `ADMIN` is only ever set on the server (SQL), never through the API.
- **Debug/test hooks never reach production:** the observer endpoints (games, emails, reports, roles) exist only with the Spring profile `e2e`; keep `DebugEndpointAbsentTest` green. Test tags (`TestTags`) and `LaunchOptions` must not change release behavior: launch parameters are read only in debug builds. The Android `preview` build type (tester builds, `preview.yml`) is release plus its own application id and shares the no-op twins in `androidApp/src/release`. iOS dev exceptions (local-network ATS) are added to Debug only by `iosApp/Configuration/debug-info-plist.sh`.
- **Build-time settings** come from Gradle properties via the generated `BuildConstants` in `:composeApp` (`hovanki.serverUrl`: the one server of non-debug builds, required, https only). Don't hardcode server addresses; non-debug builds talk HTTPS only. Debug builds use the development machine or `LaunchOptions.server`.
- **Run the long tests yourself before a PR** (CI on push doesn't): changed rules, protocol or client–server behavior → `./gradlew :e2e:test` (~6 min, works in a cloud container without KVM); changed UI or platform code (`:composeApp`, `androidApp`, `iosApp`, Maestro flows) → `./gradlew :e2e:devices` on local emulators if you have them, or trigger `nightly.yml` manually on your branch (`suite=devices`, only the scenario you need). Say in the PR what you ran. See `docs/ci-cd.md`.
- **Tests next to the code:** `shared/src/commonTest` and `clientCore/src/commonTest` (run on JVM and iOS), `shared/src/jvmTest` for JDK cross-checks, `server/src/test` (`GameTest` for rules with an explicit `now`, `GameApiTest` for HTTP round trips with MockMvc). New rule → unit test in `GameTest` or `commonTest`, and an e2e scenario in `e2e/src/test` when it spans client and server. A bug found by an e2e scenario is fixed in the game or server with a test, never worked around in the scenario.
- **Style:** ktlint `intellij_idea`, max line 120, trailing commas (see `.editorconfig`). Run `./gradlew spotlessApply` before committing.
- **Gradle:** configuration cache is on — no configuration-time side effects; no hardcoded versions in build scripts.

## AGP 9 / KMP structure

- Never apply `org.jetbrains.kotlin.android` (kotlin-android) in `androidApp`: AGP 9 has built-in Kotlin.
- Never add `androidTarget()` in KMP modules: they use `com.android.kotlin.multiplatform.library` and the `kotlin { android { ... } }` block.
- Android/shared bytecode is JVM 17, the server toolchain is JDK 21.

## When you change things

- New endpoint: `ApiRoutes` + DTO in `:shared` → `Game`/`GameService` (or an account/social service with an `AuthenticatedUser` parameter) + controller in `:server` → `GameApi`/`AccountApi`/`SocialApi` + `GameSessionManager`/`AccountManager`/`SocialManager` in `:clientCore` → UI in `:composeApp` → API table in `docs/architecture.md`. New errors: an `ErrorReason` on the existing `ErrorCode` (`ApiError.reason`), never a new `ErrorCode`.
- Behavior, commands or setup changed → update `README.md` / `docs/`. Big decisions → new ADR in `docs/adr/NNNN-*.md`.
- Something a player can see or do is new (a feature, a milestone) → add an entry at the end of `docs/devlog.md`, the marketing log: Russian, plain words, what the player gets, with a 🎬 hint how to film it; see its «Как добавить запись». Not working on a phone yet → its «Пока нет» section.
- Recipes for endpoints, platform services and screens: `docs/architecture.md`, section «Как добавить…».
