# Лаборатория производительности сервера

Стенд на своём компьютере, чтобы мерить и ускорять сервер: только сервер, своя база, нагрузка из Gatling, графики в Grafana, флеймграфы из async-profiler. Ничего из этого не попадает на прод: профиль `perf` включается только руками. Нагрузка не запускается ни в `check`, ни в CI; `check` только компилирует сценарии.

Чем отличается от e2e-ботов: `LoadTest` и `BigGameLoadTest` (`docs/e2e.md`) играют настоящим клиентским кодом в одном JVM с сервером. Это проверка, что игра не ломается под нагрузкой. Здесь генератор и сервер — разные процессы, сервер можно зажать в лимиты прода и профилировать отдельно.

## Что внутри

| Что | Где |
|---|---|
| Профиль сервера `perf`, запуск как `e2e,perf` | `server/src/main/resources/application-perf.yaml` |
| База, Prometheus, Grafana; сервер в контейнере с лимитами прода | `perf/compose.yaml` |
| Дашборд «Hovanki: сервер» | `perf/grafana/dashboards/hovanki.json` |
| Нагрузочные сценарии Gatling на Kotlin | `perf/src/gatling/kotlin/app/hovanki/perf/` |
| Скрипты: поднять, сервер, профиль, база, погасить | `perf/up.sh`, `perf/server.sh`, `perf/profile.sh`, `perf/pg-top.sh`, `perf/down.sh` |

Нужны Docker с Compose и JDK 21. Сценарии ходят в протокол через `:shared` (`ApiRoutes`, DTO, `protocolJson`): поменяли протокол — CI упадёт на компиляции сценария, а не нагрузочный тест посреди прогона.

## Быстрый старт

```bash
perf/up.sh                    # база (5433), Prometheus (9090), Grafana (3000)
perf/server.sh                # сервер на :8080, в другом терминале; Ctrl+C — стоп
./gradlew :perf:gatlingRun --simulation app.hovanki.perf.OrdinaryGames
open http://localhost:3000    # дашборд «Hovanki: сервер» открывается сам
perf/profile.sh cpu 60        # во время прогона: флеймграф в perf/build/profiles/
perf/down.sh                  # всё погасить; --wipe — со стёртой базой и графиками
```

Отчёт Gatling: `perf/build/reports/gatling/<сценарий>-<время>/index.html` (ссылку Gatling печатает в конце прогона).

## Два режима сервера

- **На своей машине:** `perf/server.sh` (собирает jar и запускает его с `e2e,perf`) или IDE: запуск `HovankiServerApplication` с активными профилями `e2e,perf`, с отладчиком. JVM по умолчанию как в контейнере прода: куча 480 МБ, Serial GC, JVM считает, что у неё 2 ядра (`PERF_JAVA_OPTS` меняет). Но процессор у сервера весь ваш, поэтому цифры лучше прода.
- **«Как прод»:** `perf/up.sh --container`. Тот же `server/Dockerfile`, только на JDK (нужен `jcmd`), лимиты машины прода: 2 ядра и 640 МБ (`PERF_SERVER_CPUS`, `PERF_SERVER_MEM`). JVM сама выбирает Serial GC и кучу 480 МБ, как на проде. Цифры сравнимы между прогонами и ближе к проду. Логи: `docker compose -f perf/compose.yaml logs -f server`.

Профиль `perf` поверх `e2e`:
- **от `e2e`:** отладочные эндпоинты наблюдателя (сценарии делают админа и читают коды из писем), письма в памяти, лимиты запросов выключены (тысячи игроков с одного адреса), здания, улицы и рельеф фальшивые (не меряем чужую сеть);
- **от прода:** bcrypt 10, тик больших игр 10 с, законченные игры живут 30 мин, полевого журнала нет (`ProfileConfigTest` следит, что значения совпадают с `application.yaml`);
- **своё:** база на 5433, `/actuator/prometheus` открыт, гистограммы `http.server.requests` и `hovanki.game.sync` для Grafana, потоки Tomcat в метриках.

Пул базы, сжатие ответов и всё остальное — как на проде.

## Нагрузка: сценарии Gatling

`./gradlew :perf:gatlingRun --simulation <класс> -Pperf.<параметр>=<значение>`. Сервер по умолчанию `http://localhost:8080`, другой — `-Pperf.baseUrl=…`.

| Сценарий | Что делает | Параметры (по умолчанию) |
|---|---|---|
| `app.hovanki.perf.OrdinaryGames` | Обычные игры рядом: гости создают игру, входят по коду, хост стартует, все шлют `/sync` раз в `GameRules.syncIntervalSeconds` (3 с) с точкой, которая идёт пешком. Лобби, прятки, поиск. Никто никого не ловит: горячий путь — `/sync` | `games` (10), `players` (30), `rampSeconds` (60), `minutes` (5) |
| `app.hovanki.perf.BigGame` | Одна большая игра: админ стенда создаёт её до прогона, каждый игрок регистрирует аккаунт, записывается, входит в лобби и синхронизируется; раунд стартует планировщик сервера, всех разом | `players` (300, максимум 1 600), `rampSeconds` (60), `lobbySeconds` (ramp + 45), `minutes` (5) |

В отчёте запросы `/sync` разделены по фазам (`sync LOBBY`, `sync HIDING`, `sync SEEKING`): снимок в поиске больше и дороже. Сценарий падает, если ошибок больше 1 %.

Как добавить сценарий: класс `Simulation` рядом с этими, запросы из `Requests.kt` (`hovankiHttp()`, `sync()`, `asPlayer()`), параметры через `LabConfig.int("имя", умолчание)`, они приходят из `-Pperf.имя=…`. Для админских действий — `LabAdmin`.

## Grafana

<http://localhost:3000>, без логина. Дашборд «Hovanki: сервер», переменная `job`: `hovanki-host` (сервер на машине) или `hovanki-container`. Prometheus снимает метрики раз в 5 с.

- **Нагрузка:** запросы/с по маршрутам, p95 по маршрутам, ответы 5xx и 429.
- **Игра:** `/sync` p50/p95/p99 по транспорту (опрос и сокет), синхронизаций в секунду, игры, игроки, сокеты.
- **JVM:** CPU процесса и машины, куча, скорость аллокаций, паузы GC, потоки, соединения Tomcat.
- **База:** пул Hikari (занятые, свободные, ждущие), время получения соединения и время его использования.

Дашборд можно править в Grafana. Чтобы правка осталась в репозитории: Share → Export → JSON в `perf/grafana/dashboards/hovanki.json`.

## Профайлер

`perf/profile.sh <вид> [секунды]` снимает профиль работающего сервера, ничего не перезапуская: на машине или в контейнере стенда, скрипт находит его сам. По умолчанию 60 с. Результат: `perf/build/profiles/<время>-<вид>.html`, открыть в браузере.

| Вид | Что показывает | Когда |
|---|---|---|
| `cpu` | куда уходит процессор | p95 растёт вместе с CPU |
| `alloc` | кто создаёт мусор | частые паузы GC, большая скорость аллокаций |
| `lock` | кто ждёт замков и сколько | CPU не загружен, а ответы медленные |
| `wall` | все потоки, работающие и ждущие | ожидание базы, сети, пула |
| `jfr` | запись Java Flight Recorder | открыть в JDK Mission Control: GC, мониторы, потоки, всё сразу |

Как читать флеймграф: снизу вверх — стек вызовов, ширина — доля времени (или аллокаций, или ожидания). Ищите широкие «плато» в коде `app.hovanki`. Клик увеличивает, поиск (Ctrl+F) подсвечивает и пишет долю.

Внутри async-profiler 4.5 из Maven Central (Linux x64/arm64, macOS). В контейнере и на macOS `cpu` идёт по таймеру (`itimer`), а не по счётчикам процессора: Docker их не даёт. Дамп кучи для долгих прогонов: `jcmd <pid> GC.heap_dump /tmp/heap.hprof`, смотреть в Eclipse MAT или VisualVM.

## База

`perf/pg-top.sh` — самые дорогие запросы по суммарному времени из `pg_stat_statements` (вызовы, всего, среднее, максимум, строки, чтения с диска). `perf/pg-top.sh --reset` перед прогоном, чтобы топ был только этого прогона. Разобрать один запрос:

```bash
docker compose -f perf/compose.yaml exec postgres psql -U hovanki -d hovanki
EXPLAIN (ANALYZE, BUFFERS) SELECT …;
```

На пустой базе медленные запросы истории и рейтинга не видны: сидер с данными — следующий шаг.

## Как работать

1. **Базовая линия.** Сценарий с прогревом 1–2 мин и замером 5 мин. Записать p50/p95/p99, запросы/с, CPU, аллокации/с, паузы GC.
2. **Предел.** Растить нагрузку (`-Pperf.games`, `-Pperf.players`), пока p95 не выйдет за цель или не появятся ошибки. Цель для начала: `/sync` p95 ≤ 50 мс, p99 ≤ 200 мс, 0 ошибок на 2 ядрах и 640 МБ.
3. **Профиль** на 70–80 % предела: `cpu`, `alloc`, `lock`.
4. **Одна гипотеза — одно изменение.** Тот же прогон, сравнить. Не стало лучше — откатить.
5. **Поведение не сломано:** `./gradlew check` и `./gradlew :e2e:test`.
6. **Каждая оптимизация — отдельный PR** с цифрами до и после.

Журнал замеров — `perf/results/<дата>-<сценарий>.md`:

```markdown
# 2026-10-14 OrdinaryGames, 20 × 30, контейнер (2 ядра, 640 МБ)

Коммит: abc1234. Машина: MacBook M2, 16 ГБ.
Параметры: -Pperf.games=20 -Pperf.minutes=5

| | до | после |
|---|---|---|
| /sync p50 / p95 / p99, мс | | |
| запросов/с | | |
| CPU сервера, % | | |
| аллокации, МБ/с | | |
| паузы GC, мс/с | | |

Что поменяли и почему. Ссылки на флеймграфы не нужны: они локальные.
```

## Первые гипотезы

Из чтения кода, не замерены:

- **Один замок на игру.** Каждый `/sync` берёт `synchronized(game)` и строит снимок под ним (`GameService.sync`, `server/src/main/kotlin/app/hovanki/server/game/GameService.kt`). В большой игре 1 600 игроков проходят через один монитор. Возможная причина хвоста p99 241 мс и max 1,5 с из ADR 0010. Проверять профилем `lock` на `BigGame` с 1 600.
- **Сжатие ответов.** Ищущий в большой игре получает десятки КБ раз в 3 с, gzip включён (`server.compression` в `application.yaml`). Смотреть его долю на `cpu`.
- **Сериализация снимка** на каждый запрос: одинаковые части снимка, возможно, собираются заново для каждого игрока. Смотреть `alloc`.
- **Пул базы на 5 соединений** (`hikari.maximum-pool-size`) против рейтинга и достижений, которые считаются из `game_results` на каждый запрос. Смотреть «ждущие» в Grafana.
- **bcrypt 10 на регистрации и логине:** пик CPU, когда сотни людей входят перед большой игрой. Виден в `BigGame` на разгоне.

## Ограничения

- **Генератор и сервер делят процессор.** Gatling тоже ест CPU, поэтому сервер лучше держать в контейнере с лимитом ядер. Для точных цифр позже: генератор на второй машине.
- **На проде Serial GC.** Машина прода (2 ядра, 640 МБ на контейнер) — ниже порога, где JVM выбирает G1. Режим «на машине» повторяет это флагами, контейнер — сам.
- **Сервер стенда открыт.** У него отладочные эндпоинты наблюдателя (координаты всех игроков, коды из писем) и тестовый ключ админки. Все порты стенда слушают только `127.0.0.1`. Никогда не запускать профиль `e2e` или `perf` на сервере в интернете.
- **Профили и записи — только локально.** Флеймграф, JFR и дамп кучи живого сервера содержат данные игроков (координаты, токены). На проде их не снимаем, в репозиторий не кладём (`perf/build/` в `.gitignore`).
