# Метрики и данные для аналитики

Что можно знать об игроках и играх Hovanki, что уже собирается, что можно добавить и чего собирать нельзя. Решение о хранении истории и маршрутов, сроки и GDPR — [ADR 0007](adr/0007-game-history-and-routes.md).

## Уровни данных

Каждая метрика относится к одному уровню. Уровень определяет, нужно ли согласие, сколько хранить и кто видит.

| Уровень | Что это | Основание | Хранение | Кто видит |
|---|---|---|---|---|
| **A. Обезличенные** | числа об игре или системе без людей: длительность игры, сколько игроков, задержки сервера | персональных данных нет | без срока | команда |
| **B. Итоги игрока** | числа, привязанные к аккаунту, без координат: игры, победы, находки, пройденное расстояние, скорость | функция приложения («твоя статистика»), указано в политике | до удаления аккаунта | сам игрок (профиль) и команда (агрегаты) |
| **C. Геоданные** | координаты: маршруты и всё, что считается из точек, а не из итогов | явное согласие «Сохранять мои маршруты» | 90 дней | сам игрок (карта) и команда (агрегаты, без выгрузки маршрутов) |
| **Нельзя** | см. [ниже](#чего-не-собираем) | — | — | — |

Гости (без аккаунта) дают только уровень A.

Статус в таблицах:
- ✅ — уже собирается (таблица или API);
- 🧮 — можно посчитать SQL-запросом из того, что уже есть;
- ➕ — нужно добавить сбор (сервер или приложение).

| `users`, `friendships`, `group_members`, `friend_requests`, `blocks`, `reports` | B | аккаунты и социальные связи ([ADR 0004](adr/0004-accounts-friends-chat.md)) |
| `feature_flags` | A | какие фишки сервера включены, кто и когда переключил ([ADR 0012, 4.1](adr/0012-nearby-radar.md#41-модель)) |
| `radio_calibration` | A | показания радара по паре моделей телефонов, где они были (в руке, в кармане), якорю и dBm — счётчики без игры, игрока и места ([ADR 0012](adr/0012-nearby-radar.md#отличия-реализации-2026-09-28)) |
| `big_games`, `big_game_signups` | A / B | большие игры: место, время, лимит, оценка вместимости; кто записался (B, с аккаунтом), 90 дней после игры ([ADR 0010](adr/0010-big-games.md)) |
| `GET /api/v1/me/stats`, `/me/games`, `/me/games/{id}/route` | B, C | то же самое для самого игрока в приложении |
| Лог сервера | A | счётчики очистки, ошибки; без координат, email, чата |
| e2e-отчёты (`SyncMetrics`) | A | задержки запросов в тестах, не в проде |
| Полевой журнал ([ADR 0018](adr/0018-field-test-build.md), `lab_runs.kind = GAME`) | C | только полевая сборка (`preview`) на сервере с `FIELD_LOG` (staging), после согласия тестера: журнал лабы в настоящей игре — координаты (только в `gps`), радар (прорежен), `sync`, ошибки, отметки «Что-то не так», ответы после игры, скорость и курс в `gps`, размер ответа `sync`, датчики (прорежены), разрешения, экраны и ключевые действия (без текста), касания телефонов и тени кармана; события сервера (устройство `server`): фазы, заявки с расстоянием по GPS в метрах и ответом правила «вплотную» в тени, находки, споры, раскрытия, свечения, вердикты точек, полосы радара по парам (id игроков, без ников и координат) и `srv` раз в 10 с; удаляется целиком через 90 дней после игры, устройство игрока — с аккаунтом; только админы; в аналитику прода не идёт |
| Sentry ([ADR 0018, §7](adr/0018-field-test-build.md#7-sentry)) | A | только полевая сборка и staging-сервер, регион EU: тип исключения, текст после фильтра (до 300 знаков), стек, версия приложения, модель и ОС, имена экранов; без пользователя, запросов, координат, токенов, email, ников и чата |
| Метрики сервера (Micrometer, `/actuator/prometheus`) | A | только staging, порт управления 8081 (наружу не виден): игры и игроки в памяти, открытые сокеты, задержки `sync` по транспорту и всех маршрутов (p50/p95/p99), ответы по кодам; в базу не пишутся |

## Чего не собираем

- **Координаты без согласия — для аналитики.** Точки игроков без «Сохранять мои маршруты» в аналитику не идут. Запись игры ([ADR 0011](adr/0011-spectators-and-recordings.md)) хранится только для её игроков и 90 дней; из неё ничего не считаем и не выгружаем. Никаких «временных» копий в логах, бэкапах аналитики или метриках.
- **Координаты гостей** — ни в каком виде дольше игры, кроме записи игры для её игроков (90 дней, [ADR 0011](adr/0011-spectators-and-recordings.md)).
- **Где человек живёт и работает.** Не выводим «дом» и «работу» из маршрутов, не ищем повторяющиеся места одного человека, не склеиваем маршруты с другими данными.
- **Чужие маршруты другим игрокам.** В приложении никто, кроме самого игрока, не видит его историю и сохранённые маршруты. Пути всех видят только игроки той же игры: в разборе и в записи игры ([ADR 0007](adr/0007-game-history-and-routes.md#6-исключение-разбор-после-игры), [ADR 0011](adr/0011-spectators-and-recordings.md)); в открытой игре — её зрители, с задержкой.
- **Текст чата для аналитики.** Только число сообщений; текст живёт в памяти игры и в жалобах ([ADR 0004](adr/0004-accounts-friends-chat.md#9-модерация)).
- **Радар по игрокам.** RSSI, жетоны, кто кого слышал и когда, где был телефон (в руке или в кармане) во времени — только в памяти игры, ни в базу, ни в логи. В базе — счётчики по моделям телефонов (`radio_calibration`), без игры, игрока, времени и места; модель телефона (`DeviceReport.model`) приходит только в игре с радаром и отдельно от игрока не хранится.
- **Рекламные идентификаторы** (IDFA, AAID), контакты телефона, список приложений, сторонние SDK аналитики, которые отправляют данные третьим лицам. Исключение — Sentry в полевой сборке ([ADR 0018, §7](adr/0018-field-test-build.md#7-sentry)): только ошибки, без координат и персональных данных; в release его нет.
- **Email и ники в выгрузках.** Для анализа хватает `user_id`.

## Кто и как смотрит

Сводные цифры (регистрации, активные игроки, игры, баланс, жалобы) показывает админка, раздел «Цифры» ([ADR 0008](adr/0008-admin.md)), по тем же правилам: средние — только по 5 играм и больше. Остальная аналитика — SQL-запросы к базе.

- **Роль только для чтения.** Отдельная роль PostgreSQL (`hovanki_analytics`, `SELECT` на нужные таблицы, без `users.email`, `users.password_hash`, `reports.text`) — чтобы запросы для аналитики не могли ничего изменить и не видели лишнего. Подключение — как сейчас, только из VM (RDS без публичного адреса).
- **Агрегаты, а не люди.** Маршруты смотреть только сводно (тепловые карты, средние по многим играм). Конкретный маршрут конкретного человека — только по его обращению (поддержка, спор) и с записью, кто и зачем смотрел.
- **Никаких выгрузок маршрутов** из базы на ноутбуки и в таблицы.
- **Маленькие выборки.** Не показывать агрегат меньше чем по 5 игрокам: по нему можно узнать конкретного человека.

## Примеры запросов

Статистика игрока (то же, что `GET /me/stats`):

```sql
SELECT count(*) AS games,
       sum(distance_meters) / 1000 AS km,
       sum(distance_meters) / nullif(sum(moving_seconds), 0) * 3.6 AS avg_kmh
FROM game_results
WHERE user_id = :user;
```

Баланс: как часто ищущие находят всех, в зависимости от числа игроков:

```sql
SELECT players,
       count(*) AS games,
       avg((hiders_caught + hiders_eliminated = players - seekers)::int) AS seekers_win_rate,
       avg(extract(EPOCH FROM finished_at - zone_started_at) / 60) AS search_minutes
FROM played_games
WHERE finished_at > now() - interval '30 days'
GROUP BY players
ORDER BY players;
```

Удержание D7 зарегистрированных за месяц:

```sql
SELECT date_trunc('week', u.created_at) AS cohort,
       count(*) AS registered,
       count(*) FILTER (WHERE EXISTS (
           SELECT 1 FROM game_results r
           WHERE r.user_id = u.id AND r.started_at >= u.created_at + interval '7 days'
       )) AS played_after_a_week
FROM users u
WHERE u.created_at > now() - interval '60 days'
GROUP BY 1
ORDER BY 1;
```

Средняя скорость прячущихся и ищущих:

```sql
SELECT role, sum(distance_meters) / nullif(sum(moving_seconds), 0) * 3.6 AS avg_kmh, count(*) AS games
FROM game_results
GROUP BY role;
```

Радар: как звучит «в метре» (30 с перед находкой) и «далеко» для пары моделей, телефоны в руке — чтобы поправить пороги полос и поправки за модель ([ADR 0012](adr/0012-nearby-radar.md#отличия-реализации-2026-09-28)):

```sql
SELECT hearer_model, heard_model, anchor,
       sum(readings) AS readings,
       round(sum(rssi_dbm::numeric * readings) / sum(readings), 1) AS mean_dbm
FROM radio_calibration
WHERE hearer_carry = 'IN_HAND' AND heard_carry = 'IN_HAND' AND anchor IN ('CATCH', 'FAR')
GROUP BY 1, 2, 3
HAVING sum(readings) >= 100
ORDER BY 1, 2, 3;
```

Сколько на самом деле съедает карман у каждой модели (сверить с `ProximityRules.POCKET_OFFSET_DB`):

```sql
SELECT heard_model,
       round(sum(rssi_dbm::numeric * readings) FILTER (WHERE heard_carry = 'IN_HAND')
             / nullif(sum(readings) FILTER (WHERE heard_carry = 'IN_HAND'), 0)
           - sum(rssi_dbm::numeric * readings) FILTER (WHERE heard_carry = 'IN_POCKET')
             / nullif(sum(readings) FILTER (WHERE heard_carry = 'IN_POCKET'), 0), 1) AS pocket_db
FROM radio_calibration
WHERE anchor = 'CATCH' AND hearer_carry = 'IN_HAND'
GROUP BY 1
HAVING sum(readings) FILTER (WHERE heard_carry = 'IN_POCKET') >= 100;
```

1. Отказы заявок `TOO_FAR` / `NO_LOCATION`, раскрытия по причинам и их длительность — чтобы настраивать пороги GPS ([ADR 0001](adr/0001-stack.md#честная-игра)).

6. Радар и задания: фишки игры в `played_games`, раскрытия `RADAR_OFF`, отказы `NOT_NEARBY`, задания по видам; просмотр `radio_calibration` в админке, чтобы править пороги радара без SQL ([roadmap](roadmap.md)).
