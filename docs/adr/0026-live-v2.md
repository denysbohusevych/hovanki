# ADR 0026. Живой канал v2: protobuf-дельты по UDP, без Caddy

- **Статус:** Accepted (в коде шаги 1–4 плана: кодек в `:shared`, WebSocket v2, сервер без Caddy, UDP на сервере и на Android; всё за выключенными флагами `LIVE_V2` и `LIVE_UDP`, на телефонах ещё не пробовали)
- **Дата:** 2026-10-14
- **Автор:** Denys Bohusevych (черновик — Claude Code, тред «Радикальные оптимизации сервера»)

Решение Denys 14.10.2026: «Будем создавать V2…», Caddy убрать, «давай также UDP делать». Детали ниже — предложение
треда. Как это устроено побайтно — [спецификация](../live-v2/spec.md), что делать в приложении —
[client.md](../live-v2/client.md), на сервере — [server.md](../live-v2/server.md), по шагам —
[plan.md](../live-v2/plan.md).

## Контекст

Цель — 30 000 игроков одновременно на одном t3.micro (2 vCPU, 1 ГБ). Это 10 000 синхронизаций в секунду. Бюджет на
синхронизацию:

- ≤ 85 мкс CPU;
- ≤ 22 КБ памяти на игрока всего;
- ≤ 500 байт в каждую сторону.

Сейчас (замеры 14.10, разбор треда «Радикальные оптимизации сервера» от 14.10.2026 (вне репозитория)):

- **CPU.** Сокет v1 стоит ~440 мкс на сервере и ~120 мкс в Caddy.
- **Трафик.** Снимок JSON — 6,5 КБ у ботов стенда, ~10,6 КБ в настоящей игре с радаром. Из них около 1 КБ меняется
  от синхронизации к синхронизации, и это в основном `lastSeenMillis`.
- **Сжатие сокета** (permessage-deflate) ужимает до сотен байт, но держит ~220 КБ zlib на сокет. Мы его выключили
  (`NoSocketCompression`).
- **Caddy** держит ~110 КБ на WebSocket: два буфера по 32 КБ и три горутины.
- **Сеть прода** (64 Мбит/с базово) с такими снимками кончается на 2–4 тыс. игроков.

Вывод разбора: без бинарных дельт и без Caddy 30k не получится, сколько ни оптимизируй игру. ADR 0015 так и оставил:
«Потом: … дельты, CBOR — только если трафик покажет». Трафик показал.

## Решение

1. **Меняется только живой канал.** Команды остаются HTTPS + JSON v1: их мало, они редкие, а менять их — переписать
   половину приложения без выигрыша.
2. **Живая сессия открывается по HTTPS** (`POST /api/v2/live/open`) токеном игры. Сервер выдаёт id сессии, два
   случайных ключа AES-128-GCM и адрес UDP. Рукопожатия по UDP нет: TLS уже проверил сервер и передал ключи.
3. **Транспорт — UDP на 443, запасной — бинарный WebSocket** на том же 443/tcp. Одна живая сессия ездит по любому из
   них и не теряет базу дельт. Последний запасной путь — v1 как есть.
4. **Сообщения — protobuf (proto3)**, схема `live_v2.proto` — единственный источник правды. Классы генерирует Square
   Wire 7.1 в `:shared`.
   - Wire, а не kotlinx-serialization-protobuf: у kotlinx protobuf всё ещё экспериментальный, он идёт от кода, а
     не от схемы, пишет proto2 и **падает на незнакомом значении перечисления**. Это ломает совместимость вперёд.
     Wire хранит незнакомые поля и значения.
   - Риск Wire с плагином `com.android.kotlin.multiplatform.library` снят 14.10: JVM и Android собираются и
     проходят тесты. Фреймворк iOS проверит сборка на Mac.
5. **Состояние режется на секции, ходят только изменения** относительно состояния, которое телефон подтвердил.
   - Сервер помнит 64-битные хеши секций последних отправленных состояний, телефон — сами состояния (до 8).
   - Потеря, перестановка и повтор любого сообщения не ломают состояние: следующий обмен его чинит.
   - Изменения игры приходят push-ем сразу, а не «толчок, потом запрос».
6. **Телефон собирает из состояния тот же `GameSnapshot`, что даёт v1.** Экраны, `GameSessionManager` и правила
   приложения не меняются. Сервер в v2.0 режет состояние прямо из снимка v1 этого игрока, поэтому видимость
   совпадает по построению.
7. **Редкие большие структуры** (настройки с правилами, доска, задания, перки, вместимость, большая игра) едут
   внутри секций как JSON v1. Их схемы не дублируются в `.proto` и развиваются по правилам v1. На трафик это почти
   не влияет: они приходят раз за сессию.
8. **Шифрование UDP — AES-128-GCM**, по ключу на направление, nonce — номер пакета, заголовок — AAD. Окно повторов
   на 64 пакета, ключ не дольше часа и не больше 2^20 пакетов.
   - AES-GCM, а не ChaCha20-Poly1305: на Android он есть с API 10, а ChaCha — только с API 28 (у нас minSdk 26).
   - На iOS AES-GCM даёт CryptoKit через маленький мост Swift: в публичном CommonCrypto GCM нет.
9. **Caddy уходит.**
   - TLS держит Tomcat (`server.ssl.bundle` из PEM с перечитыванием без рестарта).
   - Сертификат получает lego по DNS-01 через DuckDNS (таймер systemd): порт 80 не нужен.
   - UDP принимает `DatagramChannel` JDK в той же JVM, без Netty.
   - Край на Netty для 443/tcp (шаг 1б) — только если замер покажет, что TLS-соединение Tomcat дороже ~20 КБ.
10. **Флаги сервера `LIVE_V2` и `LIVE_UDP`** — на весь сервер, выключены по умолчанию, включает админ. Без них всё как
    сегодня.
11. **Платформа (ADR 0005).** Общие части канала (подтверждения, время, чат, ошибки, закрытие) лежат вне состояния
    игры. Номера полей 20–29 в `Up` и `Down` оставлены под другие виды игр.

## Что отвергли и почему

| вариант | почему нет |
|---|---|
| Оставить JSON, сжимать каждый кадр без словаря (как gzip у опроса) | ~2 КБ на синхронизацию: в 4 раза больше бюджета, и CPU на сжатие (20–30 % в профиле) |
| Сжатие сокета со словарём (permessage-deflate) | ~220 КБ zlib на сокет вне кучи: убило контейнер на 900 игроках |
| CBOR | экспериментальный, по умолчанию падает на незнакомом ключе, компактный только с ручными метками, схему писать руками |
| kotlinx-serialization-protobuf | см. решение 4; запасной вариант |
| QUIC (HTTP/3 или свой поверх QUIC) | на Android нужна сторонняя библиотека, на iOS датаграммы QUIC — с iOS 16; на сервере — Netty QUIC с нативной частью. Тяжело ради того, что даёт свой UDP с ключом из HTTPS |
| DTLS | DTLS 1.3 нет ни на iOS (там до 1.2), ни в Bouncy Castle; на Android своего DTLS нет |
| ChaCha20-Poly1305 | на Android только с API 28 |
| Своё шифрование на чистом Kotlin | нет проверенной реализации; в криптографии своё — это риск |
| Оставить Caddy, `stream_buffer_size 4KiB` | всё равно ~86 КБ на сокет и ~120 мкс на синхронизацию |
| Сразу край на Netty для TCP | ~500 строк своего прокси. Сначала замерить Tomcat с TLS: после v2 постоянных TCP-соединений мало |
| Несколько JVM или контейнеров на одной машине | делят те же 2 vCPU; игры в памяти одного процесса |
| Дельты в JSON (JSON Patch) | байты и CPU JSON остаются; протобаф на тех же данных в разы меньше |

## Последствия

- **Нужен релиз приложения.** Старые приложения работают на v1, сервер держит оба протокола.
- **Ещё один источник правды** — `.proto`. Правила его изменения — спека, §15.
- **Отлаживать труднее:** бинарно и зашифровано. Нужны:
  - декодер `Up`/`Down` в отладочной сборке и в e2e (печать секций);
  - метрики сервера по транспортам и закрытиям.
- **Деплой:**
  - токен DuckDNS на машине;
  - порт 443/udp в группе безопасности;
  - настройки ядра (conntrack, буферы UDP);
  - откат на Caddy — профилем compose.
- **iOS:** мост Swift (CryptoKit), который собирается только на Mac. Без моста приложение работает по WebSocket v2.
- **Безопасность.** UDP-сервер — новая поверхность. Не отвечать на неподтверждённые пакеты, ограничивать ответы на
  новый адрес, RESET меньше вопроса (спека, §16).
- **Приватность** не меняется: те же данные, в памяти, с теми же сроками.
- **Выигрыш по оценке:**
  - трафик ÷20–70 (~150–300 байт вместо 6,5–10,6 КБ на синхронизацию);
  - CPU — без JSON, Spring и Caddy на пути синхронизации;
  - память — один UDP-сокет на всех вместо ~110 КБ Caddy и ~60 КБ Tomcat на игрока.

  Цифры подтвердит стенд на шагах 2–4.

## Отличия реализации

Шаг 2 плана (14.10.2026) уточнил спецификацию там, где черновик молчал или был неудобен. Спецификация уже исправлена;
здесь — что поменялось и почему.

- **Полное состояние (база 0) не шлёт пустых секций.** Телефон накладывает его на пустое состояние
  (`LiveStates.EMPTY`), так что пустая секция ничего не меняет, а лобби из 10 игроков становится 1,8 КБ вместо 2,7 КБ
  JSON.
- **`order` в дельте — только когда нужен.** Телефон сам выводит порядок: старый без удалённых, новые в конце. Сервер
  шлёт `order`, только если так получится не то, что в снимке v1. В полном состоянии `order` есть всегда.
- **Подтверждённое телефоном состояние сервер не выбрасывает** из своих 8, даже когда отправил после него много
  новых: иначе после серии потерь пришлось бы слать полное состояние.
- **Точность в дециметрах — вверх с допуском** `ceil(m×10 − 1e-6)`: 4,2 м не превращаются в 43 дм из-за двоичной
  дроби.
- **Одно сообщение чата уходит всегда**, даже если оно одно больше лимита байтов: иначе чат встал бы навсегда.
- **`LiveAead` хранит ключ в себе:** `seal(nonce, aad, plaintext)` без ключа в параметрах. Ключ не ходит по коду, а
  платформа держит его в своём объекте (`Cipher` JDK, `SymmetricKey` CryptoKit).
- **Окно повторов** принимает номера не дальше 63 назад от самого большого (64 номера вместе с ним).

Шаг 3a (сервер с WebSocket v2, 14.10.2026; подробно — [server.md](../live-v2/server.md), §4.7):

- **Чат и состояние в push — разными `Down`**, чат первым. Push чата без состояния снимка на телефоне не выпускает:
  его время не говорит, что состояние телефона верно.
- **Push без нового не уходит:** состояние то же, что в последнем отправленном `Down`.
- **WebSocket с чужой сессией** закрывается кодом 4410 (открыть новую), а не 4401: годный токен не кончает игру.
- **404 из игры, пока игра есть,** — это ушедший игрок: сессия закрывается как `CLOSE_SESSION_REJECTED`.
- **Частота открытий** считается в памяти рядом с сессиями, без новых настроек `RateLimiter`.
- **Push не отмечает игрока «на связи»:** снимок собирается без касания `lastSeen` (разделение стенда, PR #90).

Шаг 3b (приложение на WebSocket v2, 14.10.2026; подробно — [client.md](../live-v2/client.md), §10):

- **Шов — `LiveSocket`,** а не отдельный `LiveTransport`: UDP встанет за него же, отдавая целые `Down`.
- **Один `Up` в пути,** push сам `Up` не вызывает; в лобби и на итогах `Up` раз в 10 с.
- **Новая сессия до срока — по монотонным часам телефона,** и старая закрывается до открытия новой.
- **Выбор транспорта в e2e — на весь прогон** (`-Pe2e.transport=v2ws`), а не `BotTransport` у бота.

Шаг 4 (UDP, 16.10.2026; подробно — [server.md](../live-v2/server.md), §4.8, [client.md](../live-v2/client.md), §11):

- **Проверяется и первый адрес сессии,** и ответ на непроверенный адрес не несёт состояния вовсе: проще, чем мерить
  дельту под предел «втрое больше полученного», а цена — один круг в начале сессии и после смены сети.
- **UDP забирает сессию у WebSocket** свежим `Up` с проверенного адреса: так телефон возвращается на UDP.
- **На сервере один `DatagramChannel` с двумя потоками,** а не два сокета с `SO_REUSEPORT`; порт открывается, когда
  включён `LIVE_UDP`.
- **Телефон ждёт ответа 1,5 с,** второй потерянный `Up` подряд берёт новый порт, третий уводит ту же сессию на
  WebSocket v2 на 10 минут или до смены сети. Ошибка UDP-сокета — потеря, а не обрыв.
- **UDP пока только на Android:** iPhone просит `ws`, пока нет моста CryptoKit.
