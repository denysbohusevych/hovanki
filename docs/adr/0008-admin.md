# ADR 0008. Админка: роли, модерация и инструменты оператора

- **Статус:** Proposed (черновик-план, в коде не реализовано)
- **Дата:** 2026-09-28
- **Автор:** Denys Bohusevych (черновик — Claude Code)

> **План, а не описание кода.** Сегодня у сервера нет ролей и административных маршрутов: жалобы лежат в таблице `reports`, к которой можно подойти только через psql, а полное состояние игр отдаёт только Spring-профиль `e2e`. Документ описывает, что нужно администратору, модератору и разработчику, как это защищено, какие данные добавляются и в каком порядке делается. Метрики, логи, алерты и доступ к actuator — [ADR 0007](0007-observability.md); здесь — то, что требует действий над данными и игроками.

## Контекст

- Roadmap («Аккаунты: до публикации»): «кто разбирает жалобы — человек и хотя бы SQL-запрос к `reports`; затем админ-инструменты, баны, фильтр слов». Магазины требуют от приложения с пользовательским контентом (чат) не только жалобы и блокировки — они уже есть — но и **действия модерации**: убрать нарушителя, ответить на жалобу. Без этого ревью в App Store (правило 1.2) и Google Play (UGC policy) можно не пройти.
- Разработчику нужно разбирать инциденты на проде («игра зависла», «не приходят письма», «утечка памяти») инструментами, которые не рискуют данными, а не через SSH и psql в рабочей базе.
- Ограничения: сервер один, база в RDS, персональных данных минимум, всё под GDPR — доступ администратора к персональным данным тоже обработка, ему нужны обоснование и аудит. Команда — один-два человека, второй домен и фронтенд-тулчейн заводить не хочется.
- В репозитории уже есть всё для интерфейса: Compose Multiplatform, Koin, `AccountApi` и `SocialApi` в `:clientCore`, e2e-боты, Maestro. Web-фронтенда нет.
- `DebugController` профиля `e2e` — прототип «полного состояния игры», но без аутентификации и с координатами, поэтому в проде его нет и не будет ([`DebugEndpointAbsentTest`](../architecture.md#api)).

## Решение коротко

| Вопрос | Решение |
|---|---|
| Кто | Три роли в `users.role`: `PLAYER` (по умолчанию), `MODERATOR` (жалобы, баны, карточка игрока), `ADMIN` (всё, плюс игры, режим обслуживания, настройки, персональные данные). Роль выдаётся только на машине (SQL или скрипт), не через API |
| Где живёт | Тот же Spring-сервер: маршруты `/api/v1/admin/**`, `AdminController`, сервисы в пакете `admin/`; параметр `AuthenticatedAdmin` по образцу `AuthenticatedUser` |
| Доступ | Аккаунтный токен + роль; для админских маршрутов сессия не старше 24 часов («войди заново»); свой лимит запросов; каждый вызов — строка в `admin_audit` |
| Интерфейс | Шаг 1 — API и рецепты `curl`/HTTPie и SQL; шаг 4 — вкладка «Модерация» в самом приложении, видна только модераторам; web-админка — только если станет нужна |
| Что видно из игр | Сводка без координат: фаза, игроки, возраст последнего `sync`, заявки, здания. Координаты в проде не видит никто, даже администратор |
| Данные | Миграция `V3__admin.sql`: `users.role`, `bans`, `admin_audit`, статус у `reports`, `problem_reports`; сроки хранения — в таблицу ADR 0004 |
| Инструменты оператора | Свой actuator-эндпоинт `hovanki` на management-порту (режим обслуживания, активные игры, флаги) для `hovanki-update.sh`; те же действия — в admin API для приложения |

## 1. Кто и что ему нужно

Три персоны:

- **Разработчик и оператор** (сейчас — автор проекта): жив ли сервер, какая версия, сколько игр и игроков, ошибки за последний час, JVM и база (всё это — Grafana, ADR 0007); уровни логов на лету; состояние конкретной игры по жалобе «зависла»; завершить или удалить сломанную игру; режим обслуживания перед деплоем; включить или выключить правило зданий и лимиты без релиза; дамп памяти при утечке.
- **Модератор**: очередь жалоб с контекстом (текст, отправитель, игра, повторные жалобы на того же человека); действия — закрыть без последствий, замутить чат на N дней, забанить аккаунт на N дней или навсегда, разбанить; история действий по игроку; отчёты «Сообщить о проблеме» от игроков.
- **Поддержка и GDPR**: найти аккаунт по нику или email (точное совпадение, с аудитом); увидеть, что о нём хранится (профиль, дата регистрации, подтверждён ли email, число сессий, друзей и групп — координат и чата в базе нет вовсе); отозвать все сессии («украли телефон»); удалить аккаунт по подтверждённому запросу владельца, который не может войти (самообслуживание в приложении есть); выдать выгрузку данных (ст. 15 GDPR) — JSON профиля, друзей и групп.

| Задача | Инструмент | Шаг |
|---|---|---|
| Здоровье, нагрузка, ошибки, статистика | Grafana ([ADR 0007](0007-observability.md)) | 0–1 там |
| Уровни логов, метрики точечно, дампы | actuator на management-порту через SSH-туннель | 1 |
| Список игр, сводка игры, завершить или удалить игру | `GET /admin/games`, `GET /admin/games/{id}`, `POST .../finish`, `POST .../delete` | 1 |
| Режим обслуживания, флаги | `GET`/`PUT /admin/settings` и actuator-эндпоинт `hovanki` | 1 |
| Жалобы, баны, мут | `/admin/reports`, `/admin/users/{id}/bans` | 2 (API), 4 (UI) |
| Карточка игрока, поиск, сессии, удаление, выгрузка | `/admin/users/**` | 3 (API), 4 (UI) |
| Отчёты «Сообщить о проблеме» | `/admin/problems` | 3 |
| Аудит | `GET /admin/audit` | 1 |

## 2. Роли и доступ

- `users.role text NOT NULL DEFAULT 'PLAYER'` (`PLAYER`, `MODERATOR`, `ADMIN`). В протоколе — `UserProfile.role` со значением по умолчанию `PLAYER`: приложение знает, показывать ли «Модерацию»; решает всё равно сервер.
- **Выдача роли — только на машине**: `deploy/hovanki-admin.sh grant <ник> MODERATOR|ADMIN` (обёртка над psql из compose, пишет и строку аудита) или `UPDATE users SET role = …` в консоли базы. API для смены ролей нет — нет пути повышения прав из приложения.
- **Роль — типом параметра контроллера**, как сегодня `AuthenticatedUser` и `AuthenticatedUser?` кодируют обязательность аккаунта: `AuthenticatedModerator` пускает `MODERATOR` и `ADMIN`, `AuthenticatedAdmin` — только `ADMIN`; оба несут `userId`, `role` и `tokenHash`. `AdminArgumentResolver`: тот же Bearer-аккаунтный токен → `AccountService.authenticate` → роль из `users` (одно чтение, кеш на 60 секунд) → без нужной роли 403 `FORBIDDEN` с новым `ErrorReason.ADMIN_REQUIRED`. Добавлять значения `ErrorReason` безопасно: у `ApiError.reason` есть значение по умолчанию ([совместимость протокола](../architecture.md#совместимость-протокола)).
- **Свежесть сессии.** Для `/admin/**` сессия должна быть создана не раньше 24 часов назад (`account_sessions.created_at`), иначе 401 `SESSION_EXPIRED` и приложение просит войти заново. Для одного-двух человек это дёшево заменяет второй фактор; пароль администратора — длинный, из менеджера паролей. Отдельный аккаунт только для модерации — по желанию.
- **Лимит** `admin: 600 запросов в час на пользователя` — интерфейсу не мешает, скрипт с украденным токеном режет.
- **Аудит.** Каждый вызов `/admin/**`, успешный или отклонённый — строка `admin_audit(admin_user_id, action, target_user_id, target_game_id, details, created_at)`; `details` без персональных данных: id, вид и срок бана, причина как enum, короткая заметка модератора. Для мутаций — в той же транзакции. Просмотр карточки игрока (чтение персональных данных) — тоже аудит: подотчётность по GDPR. В логах админские действия — INFO с id администратора и цели; это единственное место, где id пользователя допустим в логах ([ADR 0007, раздел 3](0007-observability.md#3-логи-сервера)).
- Опционально позже: allowlist IP на `/api/v1/admin/*` в Caddy (Caddyfile вместо однострочника `reverse-proxy`) — когда появится постоянный IP или VPN.

## 3. Данные: миграция `V3__admin.sql`

```sql
ALTER TABLE users ADD COLUMN role text NOT NULL DEFAULT 'PLAYER'
    CHECK (role IN ('PLAYER', 'MODERATOR', 'ADMIN'));

-- Баны и муты. Уходят вместе с аккаунтом (CASCADE): см. открытый вопрос об обходе бана удалением аккаунта.
CREATE TABLE bans (
    id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    text        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    kind       text        NOT NULL CHECK (kind IN ('CHAT', 'ACCOUNT')),
    reason     text        NOT NULL CHECK (reason IN ('SPAM', 'ABUSE', 'CHEATING', 'OTHER')),
    note       text,                 -- короткая заметка модератора, без данных третьих лиц
    created_by text        REFERENCES users (id) ON DELETE SET NULL,
    created_at timestamptz NOT NULL,
    expires_at timestamptz,          -- NULL: навсегда
    revoked_at timestamptz,
    revoked_by text        REFERENCES users (id) ON DELETE SET NULL
);
CREATE INDEX bans_user_active ON bans (user_id) WHERE revoked_at IS NULL;
CREATE INDEX bans_expires_at ON bans (expires_at);

-- Жалоба получает состояние; текст остаётся, как был.
ALTER TABLE reports ADD COLUMN status text NOT NULL DEFAULT 'OPEN'
    CHECK (status IN ('OPEN', 'DISMISSED', 'ACTIONED'));
ALTER TABLE reports ADD COLUMN resolved_by text REFERENCES users (id) ON DELETE SET NULL;
ALTER TABLE reports ADD COLUMN resolved_at timestamptz;
ALTER TABLE reports ADD COLUMN ban_id bigint REFERENCES bans (id) ON DELETE SET NULL;
CREATE INDEX reports_open ON reports (created_at) WHERE status = 'OPEN';

-- Журнал действий администраторов. target_* без внешних ключей: запись живёт дольше аккаунта,
-- а id удалённого аккаунта ни к кому больше не ведёт.
CREATE TABLE admin_audit (
    id             bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    admin_user_id  text        REFERENCES users (id) ON DELETE SET NULL,
    action         text        NOT NULL,
    target_user_id text,
    target_game_id text,
    details        jsonb       NOT NULL DEFAULT '{}',
    created_at     timestamptz NOT NULL
);
CREATE INDEX admin_audit_created_at ON admin_audit (created_at);

-- «Сообщить о проблеме» из приложения (ADR 0007, 7.1): текст игрока и последние строки его лога.
CREATE TABLE problem_reports (
    id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     text        REFERENCES users (id) ON DELETE CASCADE,   -- NULL: гость
    game_id     text,
    app_version text        NOT NULL,
    platform    text        NOT NULL,
    text        text        NOT NULL,
    log_tail    text        NOT NULL,
    status      text        NOT NULL DEFAULT 'OPEN' CHECK (status IN ('OPEN', 'CLOSED')),
    created_at  timestamptz NOT NULL
);
CREATE INDEX problem_reports_created_at ON problem_reports (created_at);
```

Сроки хранения (дописать в таблицу [ADR 0004](0004-accounts-friends-chat.md#11-сроки-хранения-и-gdpr), чистит `DataRetention`):

| Данные | Сколько |
|---|---|
| Баны | Пока действуют; истёкшие и отозванные — ещё 1 год (доказательство при споре), с аккаунтом — сразу |
| Аудит администраторов | 1 год |
| Отчёты «Сообщить о проблеме» | 90 дней, как жалобы |

## 4. Admin API

Маршруты под `/api/v1/admin` — константы в `ApiRoutes`, DTO — `Admin.kt` в `:shared`, чтобы приложение и боты пользовались теми же типами. Токен — аккаунтный, роль — в колонке.

| Метод | Путь | Роль | Что |
|---|---|---|---|
| GET | `/admin/overview` | MOD | Версия и uptime сервера, игр по фазам, игроков онлайн, открытых жалоб и отчётов, активных банов, режим обслуживания — первый экран |
| GET | `/admin/games` | ADMIN | Игры: id, фаза, игроков, создана, последняя активность, состояние зданий. **Без join-кода** (иначе администратор входит в чужие лобби) и без центра зоны |
| GET | `/admin/games/{gameId}` | ADMIN | Сводка: настройки без центра зоны (радиус, тайминги), игроки (имя, роль, статус, возраст последнего `sync`, счётчики точек, раскрыт ли и почему), заявки со статусами и голосами. Чата нет: текст чата виден только через жалобы |
| POST | `/admin/games/{gameId}/finish` | ADMIN | Принудительно `FINISHED` (новый чистый `Game.forceFinish(now)`): игроки видят итоги |
| POST | `/admin/games/{gameId}/delete` | ADMIN | Удалить из реестра: игроки получают 404 → «на сервере её больше нет» |
| GET, PUT | `/admin/settings` | ADMIN | `maintenance` (создание игры и вход по коду отвечают 409 `WRONG_STATE` с новым `ErrorReason.MAINTENANCE`; идущие игры продолжаются), `buildings` (on/off), `rateLimits` (on/off). Живут в памяти: после перезапуска — значения из `application.yaml` и окружения, они и есть правда |
| GET | `/admin/reports?status=OPEN&before=` | MOD | Очередь жалоб: текст, отправитель (ник и `userId`, или гость), жалобщик, игра, время, сколько открытых жалоб на этого отправителя за 90 дней, его активные баны |
| POST | `/admin/reports/{id}/dismiss` | MOD | Закрыть без последствий |
| POST | `/admin/reports/{id}/action` | MOD | Закрыть и создать бан одним действием: вид, срок, причина, заметка |
| GET | `/admin/problems?status=OPEN` | MOD | Отчёты «Сообщить о проблеме»; `POST .../{id}/close` |
| GET | `/admin/users?nickname=` / `?id=` / `?email=` | MOD; по email — ADMIN | Точный поиск и карточка: id, ник, дата регистрации, подтверждён ли email (сам адрес — только ADMIN), язык, сессий, друзей, групп, жалоб на него и от него, баны. Каждый просмотр — аудит `USER_VIEWED` |
| POST | `/admin/users/{id}/bans` | MOD | Бан: `kind` CHAT или ACCOUNT, до когда или навсегда, причина, заметка; ACCOUNT отзывает все сессии |
| POST | `/admin/users/{id}/bans/{banId}/revoke` | MOD | Снять |
| POST | `/admin/users/{id}/sessions/revoke` | ADMIN | «Выйти везде» по просьбе владельца |
| POST | `/admin/users/{id}/delete` | ADMIN | Удалить аккаунт тем же путём, что `AccountService.delete`, без пароля, с аудитом — только по проверенному запросу владельца |
| GET | `/admin/users/{id}/export` | ADMIN | JSON-выгрузка (профиль, друзья, группы, заявки) для запроса по ст. 15 — отдать владельцу |
| GET | `/admin/audit?before=` | ADMIN | Журнал |

Ошибки — обычный `ApiError`; новые причины на существующих кодах: `ADMIN_REQUIRED` (403), `ACCOUNT_BANNED` (403, при входе, создании игры и входе по коду с аккаунтом; в `message` — до когда), `CHAT_MUTED` (403 на сообщение), `MAINTENANCE` (409). Старые клиенты покажут общий текст, новые — точный.

## 5. Как действуют баны

- **ACCOUNT.** При бане удаляются все `account_sessions` пользователя: следующий запрос получает 401 и приложение выходит из аккаунта. `login` проверяет активный бан (одно чтение `bans` при входе) → 403 `ACCOUNT_BANNED`. `POST /games` и `/games/join` с аккаунтом — та же проверка (запрос к базе там уже есть: `playerName`). Гостевой вход по коду не запрещаем: у гостя нет идентификатора, и мы не храним IP. Так и записываем в правила сообщества: бан действует на аккаунт.
- **CHAT.** `BanCache` держит в памяти множество замученных `userId`: обновляется по расписанию раз в минуту (активных мутов мало, один запрос к `bans`) и сразу при действии модератора — сервер один. Поэтому `GameService.sendChat` проверяет `BanCache.isMuted(game.userIdOf(playerId))` под блокировкой игры без обращения к базе; правило «база — не под блокировкой игры» соблюдено. Гостей не мутим (нет id). Ответ — 403 `CHAT_MUTED`; приложение показывает «чат недоступен до …».
- Идущая игра забаненного продолжается: выкинуть игрока из партии нельзя без вреда остальным. За читерство в идущей игре администратор может завершить игру — редкий случай.
- Срок: `expires_at` проверяется при чтении; истёкшие баны лежат до ретенции.

## 6. Интерфейс

| Вариант | За | Против |
|---|---|---|
| A. Только API, `curl` и psql | Ничего строить | Модератору без терминала нельзя; ошибки в руках |
| B. Вкладка «Модерация» в приложении (Compose, роли MOD и ADMIN) | Весь стек уже есть: Koin, `AdminApi` в `:clientCore`, `TestTags`, Maestro, боты; модератор работает с телефона; ничего не хостим | Телефон — плохое место для больших таблиц и логов; код админки в публичной сборке (безвредно: решает сервер; строки видны при разборе APK) |
| C. Web-админка (Compose for Web/Wasm с DTO из `:shared` или Thymeleaf в сервере) | Большой экран; можно дать ссылку | Новый таргет или HTML в Spring; хостинг за Caddy, cookie-сессии, CSRF — новый класс проблем безопасности |
| D. Compose Desktop | Большой экран, тот же Kotlin | Раздавать и обновлять приложение администраторам; с телефона нельзя |

**Выбор: B для модерации, Grafana для цифр, туннель и actuator для оператора; A остаётся всегда — API первичен.** C — если появится модератор без нашего приложения или таблицы на сотни строк. Разбор «зависшей игры» на проде — `GET /admin/games/{id}` из терминала: это задача разработчика, не интерфейса.

Экраны «Модерации» (показываются, когда `UserProfile.role != PLAYER`: пункт в профиле или пятая вкладка `MainScreen`):

- **Жалобы**: карточки (текст, автор, игра, когда, «ещё N жалоб на него»), кнопки «Закрыть» и «Действие»; действие — полноэкранная панель, как везде (Maestro не видит отдельных окон): мут или бан, срок 1, 7, 30 дней или навсегда, причина, заметка.
- **Игрок**: карточка по нику или из жалобы; баны с «Снять»; для ADMIN — «Выйти везде», «Удалить аккаунт» с подтверждением.
- **Отчёты о проблемах**: текст игрока, версия, хвост лога; «Закрыть».
- **Сводка** (ADMIN): игр по фазам, игроков онлайн, версия сервера, переключатель режима обслуживания.

Ключевые элементы — с `TestTags`, флоу `moderation.yaml` в `e2e/maestro/`.

## 7. Инструменты оператора

- **Actuator на management-порту 8081** ([ADR 0007, раздел 6](0007-observability.md#6-деплой-health-и-доступ-разработчика)): `loggers` (поднять `app.hovanki` до DEBUG на полчаса), `metrics/{name}`, `threaddump`, `heapdump` (содержит координаты и токены: только на машину, удалить после), `env` со скрытыми секретами, `scheduledtasks`, `health` с деталями только здесь.
- **Свой эндпоинт `@Endpoint(id = "hovanki")`** там же: `GET /actuator/hovanki` → `{ version, activeGames по фазам, playersOnline, maintenance, flags }`, `POST /actuator/hovanki` → `{ maintenance: true }`, `{ buildings: false }`. Без токена — порт доступен только с loopback машины. Admin API (раздел 4) показывает и меняет то же самое для приложения; источник правды один — `ServerSettings` в памяти.
- **Обновление без обрыва игр.** `hovanki-update.sh`: новый образ есть → `POST /actuator/hovanki {maintenance: true}` (новые игры не создаются, вход по коду закрыт, идущие продолжаются) → ждать `activeGames` без `finished` = 0, не дольше 2 часов → `docker compose up -d server` (новый сервер стартует без режима обслуживания) → в журнал время и сколько ждали. Закрывает первую половину пункта roadmap; сохранение игр при перезапуске — отдельная задача.
- **Флаги на лету** (`buildings`, `rateLimits`, `maintenance`) — в памяти, сбрасываются перезапуском: постоянная конфигурация живёт в `application.yaml` и окружении, флаги — для «выключить на час, пока Overpass лежит».
- **`docs/admin.md`** (новый документ): как получить токен (`curl` на `/accounts/login`), выдать роль, посмотреть игру, забанить, закрыть жалобу, открыть туннель, поменять уровень логов, включить режим обслуживания; кто имеет доступ и где лежат учётные данные.

## 8. Тесты и e2e

- `AdminApiTest` (MockMvc): без роли 403 `ADMIN_REQUIRED`; `MODERATOR` не может `finish`; сессия старше 24 часов → 401; каждый вызов — строка аудита; бан → сессии отозваны → `login` 403 `ACCOUNT_BANNED`; мут → `sendChat` 403 `CHAT_MUTED`, после `revoke` снова можно; `reports/{id}/action` → бан и `status = ACTIONED`; `maintenance` → создание игры 409, `sync` идущей игры работает.
- `DataRetention`: истёкшие баны через год, старый аудит, старые отчёты о проблемах.
- E2E `ModerationTest`: бот-спамер пишет в чат, второй бот жалуется, бот-модератор (роль выдана прямо в `TestPostgres` хелпером `E2eServer`) видит жалобу в `/admin/reports`, мутит на 10 секунд → спамер получает `CHAT_MUTED`, потом снова пишет; бан аккаунта → вход по коду с аккаунтом отказан, гость входит; режим обслуживания → новая игра не создаётся, идущая доигрывается. Наблюдатель `/api/v1/debug/**` не меняется.
- Maestro `moderation.yaml` на Android: открыть «Модерацию», закрыть жалобу.
- `DebugEndpointAbsentTest` продолжает держать e2e-эндпоинты вне прода; админские маршруты в проде есть, но за ролью — это закрепляет отдельный тест «без роли — 403».

## 10. Чего не делаем

- Не выдаём роли через API и не делаем «первого администратора» через регистрацию: только на машине.
- Не показываем координаты в проде никому: «разбор после игры» из roadmap будет функцией для игроков той игры, не административной.
- Не читаем чужие чаты: текст виден только в жалобе — то, что игрок сам прислал модератору.
- Не строим web-админку и не заводим фронтенд-тулчейн, пока хватает телефона и терминала.
- Не делаем shadow-ban, автобаны и фильтры на машинном обучении: ручная модерация с аудитом.
- Не храним IP-адреса и не баним по IP.

## Последствия

- Протокол: новые поля и причины с дефолтами (`UserProfile.role`, `ErrorReason.ADMIN_REQUIRED`, `ACCOUNT_BANNED`, `CHAT_MUTED`, `MAINTENANCE`), новые маршруты `/admin/**`; старые клиенты не ломаются, но показывают общие тексты ошибок.
- Новые данные со сроками хранения (`bans`, `admin_audit`, `problem_reports`) — таблица ADR 0004 дополняется, `DataRetention` чистит.
- Аккаунт с ролью — цель для атаки: длинный пароль, свежая сессия для админских маршрутов, аудит, лимит; при желании — отдельный аккаунт для модерации.
- Магазины: политика пользовательского контента выполняется; в правила сообщества записать срок реакции на жалобу (например, 24 часа).
- Таблица API в architecture.md и рецепт «Как добавить админский маршрут» — при реализации.
