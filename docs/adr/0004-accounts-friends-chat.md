# ADR 0004. Аккаунты, друзья, группы и чат

- **Статус:** Accepted (принято)
- **Дата:** 2026-09-26
- **Автор:** Denys Bohusevych (черновик — Claude Code)

## Контекст

До этого решения в Hovanki не было пользователей:
- личность игрока — случайный `PlayerId` и токен на одну игру, имя вводится каждый раз;
- всё хранится в памяти сервера, базы нет;
- на стартовом экране есть поле «Адрес сервера».

Нужно:
- регистрация и вход, чтобы играть с одними и теми же людьми;
- друзья и группы-«компании» с приглашением в игру;
- чат внутри игры;
- один сервер без ручного ввода адреса;
- то, без чего аккаунты нельзя выпускать: удаление аккаунта, сброс пароля, модерация, лимиты, бэкапы, приватность.

Ограничения:
- **Одна VM с 1 ГБ памяти** (`t3.micro`, [deploy.md](../deploy.md)), один экземпляр сервера.
- **Старые версии приложения живут долго.** Протокол меняется только обратно совместимо ([architecture.md](../architecture.md#совместимость-протокола)).
- **GDPR.** Email, ник и сообщения — персональные данные: храним минимум и знаем, когда удаляем.
- **Игры остаются в памяти.** Сервер авторитетен и отвечает на опрос раз в 3 секунды. Опрос не должен зависеть от базы.

## Решение коротко

| Вопрос | Решение |
|---|---|
| Где хранить аккаунты | PostgreSQL 17 в Amazon RDS, в том же регионе, отдельно от VM сервера; миграции Flyway, доступ через `JdbcClient` |
| Как входить | Ник + email + пароль. Аккаунт работает сразу; email подтверждается 6-значным кодом из письма, когда удобно. «Забыли пароль» — тоже код |
| Токены | Два вида: аккаунт-токен (в БД только SHA-256) и игровой токен (как раньше, в памяти) |
| Гости | Без аккаунта можно только войти по коду в чужую игру. Вошедший по коду в свою же игру получает своего игрока обратно |
| Друзья и группы | Заявка по точному нику или по id из игры, без поиска. Группа — владелец и до 30 друзей |
| Приглашения и чат | В памяти вместе с игрой. Доставка — тем же опросом, что и игра |
| Ошибки | Новое поле `ApiError.reason` с default, `ErrorCode` не меняется |
| Модерация | Блокировка и жалоба на сообщение. Жалоба хранится 90 дней |
| Сервер в приложении | Один, задаётся при сборке. Поля адреса больше нет |

## 1. Хранилище: PostgreSQL в Amazon RDS

Аккаунты должны переживать перезапуск сервера, а игры, как и раньше, — нет.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Amazon RDS for PostgreSQL в том же регионе** | база не зависит от VM сервера: переживает её потерю и пересоздание; бэкапы с восстановлением на любую секунду последних 7 дней (на Free plan AWS — суток), обновления и шифрование делает AWS; память VM целиком у сервера | ещё ~$17 в месяц (`db.t4g.micro` и 20 ГБ gp3) — примерно столько же, сколько вся VM |
| PostgreSQL в контейнере на той же VM | ничего не стоит сверх VM | бэкапы, обновления и восстановление — наши скрипты; база делит 1 ГБ памяти с сервером; пропадает вместе с VM, а бэкапы на той же VM — вместе с ней |
| SQLite-файл | почти не ест память, один файл | один писатель, свои инструменты бэкапа на горячую, в тестах и проде разные драйверы; при переезде на несколько экземпляров сервера — переписывать |
| Neon, Supabase | бесплатные тарифы | внешний сервис; бесплатная база засыпает без запросов, и первый вход после паузы ждёт её пробуждения; данные пользователей у третьей стороны |
| Firebase Auth / Cognito | готовые вход и письма | внешний сервис со своими SDK в приложении, данные пользователей у третьей стороны, привязка к вендору |

**Решение: RDS for PostgreSQL 17, `db.t4g.micro`, Single-AZ, во Франкфурте, рядом с VM сервера** ([deploy.md](../deploy.md#база-rds)). Сначала база жила в контейнере на той же VM. Её вынесли в RDS до первого релиза: данные аккаунтов не должны зависеть от одной машины, а свои скрипты бэкапа и восстановления — это код, который надо поддерживать и проверять.

- Без публичного адреса: подключаться может только VM сервера (группы безопасности). TLS с проверкой сертификата (`sslmode=verify-full` и сертификаты RDS на VM).
- Сервер ходит под своей ролью `hovanki` — владельцем только своей базы, а не под администратором RDS.
- Бэкапы — автоматические, 7 дней (пока аккаунт AWS на Free plan — 1 день, больше он не даёт), восстановление на любую секунду (point-in-time recovery). Это и страховка перед миграциями: база возвращается на момент до обновления сервера.
- Пул Hikari — 5 соединений: `db.t4g.micro` выдерживает намного больше, но серверу больше не нужно.
- Схема — миграции Flyway в `server/src/main/resources/db/migration`. Миграции только дописываются, применённые никогда не правятся.
- Код сервера от места базы не зависит: адрес и пароль — `SPRING_DATASOURCE_*`. Переехать на другой PostgreSQL (контейнер, VPS, другой облачный) — дамп, восстановление и новый адрес.

**Доступ к данным: `JdbcClient`, а не JPA или jOOQ.**

| Вариант | Почему нет (пока) |
|---|---|
| JPA / Hibernate | запросы простые, а специфичные для PostgreSQL (`ON CONFLICT`, блокировки строк `FOR NO KEY UPDATE`, удаление по срокам хранения) всё равно были бы нативным SQL. Ленивые загрузки и persistence context прячут, какой SQL и когда выполняется, а с блокировками это важно. В Kotlin сущностям нужны open-классы, конструкторы без параметров и `var`; id-обёртки (`@JvmInline value class UserId`) — через конвертеры. Hibernate добавляет десятки МБ памяти и секунды старта. Генерация схемы не нужна: схему ведёт Flyway |
| jOOQ | типобезопасный SQL — хорош для большой схемы и сложных запросов. Но нужна генерация кода из схемы при сборке (живая база или разбор миграций, плюс configuration cache Gradle), а на 9 таблиц и простые запросы выигрыш мал: каждый запрос и так выполняется в тестах на настоящем PostgreSQL |
| Exposed | своё описание таблиц повторяет схему Flyway; свои транзакции рядом со Spring |

`JdbcClient` (Spring JDBC) — SQL как есть, именованные параметры, маппинг строк руками, транзакции Spring. Цена — SQL в строках: опечатку ловят тесты, а не компилятор. Весь SQL — в тонких `*Repository.kt`, поэтому переход на jOOQ позже (например, для админки со сложными запросами) затронет только их.

**Что где живёт.** В базе — аккаунты, сессии, коды из писем, друзья, заявки, блокировки, группы, жалобы. В памяти, как и раньше, — игры, координаты, чат и приглашения: они живут не дольше игры. Опрос игры (`sync`) в базу не ходит, поэтому недоступная база не останавливает идущие игры. Не работают только вход, создание игры и вход в неё с аккаунтом.

**Тесты.** `TestPostgres` поднимает встроенный PostgreSQL 17 (`io.zonky.test:embedded-postgres`, бинарники из Maven Central, без Docker) или, если задан `HOVANKI_TEST_DATABASE_URL`, создаёт свежую базу на уже запущенном сервере и удаляет её в конце. Второй путь быстрее там, где PostgreSQL уже есть, например в облачной сессии Claude Code (переменную выставляет SessionStart-хук).

## 2. Вход: ник, email и пароль

| Вариант | Почему нет (пока) |
|---|---|
| Sign in with Apple / Google | нужны настроенные аккаунты разработчика и SDK в приложении. App Store требует Sign in with Apple, если есть вход через Google. Хорошее дополнение позже, но не единственный способ |
| Номер телефона и SMS | SMS стоят денег, и их накручивают мошенники (SMS pumping) |
| Ссылка из письма (magic link) | нужны universal links / App Links и свой домен. Код из письма вводится в том же приложении и работает, даже если письмо открыто на компьютере |
| Вход только по коду из письма, без пароля | письмо на каждый вход: упираемся в лимиты SMTP (Gmail — ~500 писем в день) и в задержки доставки |

**Решение:** ник + email + пароль. Аккаунт работает сразу после регистрации, email подтверждается кодом из письма позже, когда удобно. «Забыли пароль» — тоже код.

- **Ник** — 3..20 символов: буквы любого алфавита, цифры, `_ . -`. Уникален без учёта регистра: ключ — NFKC + lowercase, поэтому `Ｄｅｎｙｓ` и `denys` — один ник. Ник — это и имя в игре.
- **Пароль** — 8..64 символа и не больше 72 байт UTF-8: BCrypt не видит того, что дальше. Хэш — BCrypt (cost 10) из `spring-security-crypto`, без Spring Security filter chain.
- **Вход** по email или по нику. Любая ошибка, включая несуществующий логин, даёт один и тот же ответ `WRONG_CREDENTIALS`. Для несуществующего логина всё равно считается BCrypt, чтобы время ответа не выдавало аккаунт.
- **Коды из писем** — 6 цифр:
  - в базе хранится хэш;
  - код живёт 15 минут, на него есть 5 попыток;
  - новый код заменяет старый.
- **Сброс пароля.** Запрос кода всегда отвечает 204: по ответу нельзя узнать, есть ли такой email. Код сброса одновременно подтверждает email. После сброса все сессии отзываются.
- **Подтверждение email необязательно.** Сначала аккаунт без подтверждения мог только подтвердить email, выйти или удалиться (403 `EMAIL_NOT_VERIFIED` на остальном), а через 7 дней удалялся. Это решение пересмотрели до первого релиза: друг должен играть через минуту после установки, а не после письма, которое может прийти в спам. Теперь:
  - код уходит письмом при регистрации, а ввести его можно когда угодно: карточка на вкладке «Играть» и профиль;
  - всё остальное работает и без него: игры, друзья, группы, приглашения, чат;
  - подтверждённый email доказывает, что адрес доходит до владельца: сброс пароля придёт туда же;
  - неподтверждённые аккаунты больше не удаляются, это обычные аккаунты.
- **Чужой email при регистрации.** Кто-то может зарегистрироваться с чужим адресом: владелец адреса получит письмо с кодом («если это были не вы, просто проигнорируйте») и в любой момент может забрать аккаунт через «Забыли пароль» — код сброса приходит ему и подтверждает адрес. Так же адрес с опечаткой: до подтверждения его можно исправить, иначе сброс пароля не дойдёт.
- **Смена email** — только пока он не подтверждён (смена подтверждённого — в [roadmap](../roadmap.md)) и только с текущим паролем. Неподтверждённый аккаунт теперь живёт долго, и тот, кто украл сессию, иначе мог бы сменить адрес на свой и забрать аккаунт через сброс пароля.
- **Письма** уходят через SMTP (`JavaMailSender`) после коммита транзакции, на небольшом пуле потоков. Тексты — на en, ru и uk, язык — тот, что был в приложении при регистрации.

Известная цена: регистрация отвечает «email занят» и тем самым показывает, что адрес зарегистрирован. Смягчено лимитом регистраций на IP.

## 3. Два вида токенов

| | Игровой токен | Аккаунт-токен |
|---|---|---|
| Что даёт | играть за одного игрока в одной игре | всё, что связано с аккаунтом: профиль, друзья, группы, входящие; создать игру или войти в неё под своим ником |
| Где на сервере | в памяти, вместе с игрой | в `account_sessions`, только SHA-256 |
| Сколько живёт | пока игра на сервере | пока не выйти, не сменить или не сбросить пароль, не удалить аккаунт; 180 дней без использования |
| Где на устройстве | `SecureStore`, ключ `session` ([ADR 0002](0002-session-storage.md)) | `SecureStore`, ключ `account` |

Оба передаются как `Authorization: Bearer <token>`: игровые маршруты принимают только игровой, аккаунт-маршруты — только аккаунтный. Создание игры и вход в неё принимают необязательный аккаунт-токен.

Почему не один токен и не JWT:
- игровой токен и все игровые маршруты остаются как были, поэтому старые версии приложения работают без изменений;
- игровые запросы идут каждые 3 секунды и не должны зависеть от базы;
- аккаунт-токен отзывается одной строкой в базе, а JWT до истечения срока отозвать нельзя без чёрного списка — той же базы.

401 на любом аккаунт-запросе значит «сессии больше нет», и приложение выходит из аккаунта. Неверный пароль при смене пароля или удалении даёт 403, а не 401.

## 4. Гости и перезаход

- **Гость** (без аккаунта) может только войти по коду в чужую игру — как раньше. Так друг друга может позвать в игру человек, который ещё не зарегистрировался. Создать игру, завести друзей и группы в новом приложении можно только с аккаунтом (подтверждать email для этого не нужно).
- Сервер ещё принимает создание игры без аккаунта: так работают старые сборки. Обязательный аккаунт для создания игр — в [roadmap](../roadmap.md), когда старые сборки уйдут.
- `PlayerView.userId` заполнен у игроков с аккаунтом и `null` у гостей. В лобби и итогах у гостя значок «гость»: гость может назваться чужим ником, и значок это показывает.
- **Перезаход.** Пользователь с аккаунтом, который входит по коду в игру, где он уже есть, получает своего игрока обратно в любой фазе, а старые токены этого игрока отзываются. Это переустановка приложения или второй телефон. Старый телефон получает 401 и выходит из игры с сообщением, что игра больше недоступна.
- **Повтор входа гостя.** Гостя сервер не узнаёт, поэтому вход по коду несёт id, который приложение придумало для этого нажатия (`JoinGameRequest.requestId`, случайный UUID). Если ответ потерялся и гость нажал «Войти» ещё раз, приложение шлёт тот же id и получает того же игрока, а не второго рядом с тем, кем никто не играет. Id работает только из того же приложения и только до перезапуска: вернуться в игру с другого телефона гость по-прежнему не может.

## 5. Друзья, блокировки, группы

- **Заявка в друзья** — по точному нику (без учёта регистра) или по `userId` игрока из лобби или итогов. Поиска по началу ника и по email нет: перебрать пользователей нельзя. Встречная заявка сразу делает людей друзьями. Лимиты: 500 друзей, 100 исходящих заявок.
- **Блокировка:**
  - удаляет дружбу и заявки в обе стороны;
  - убирает заблокированного из групп того, кто заблокировал;
  - заявки и приглашения от заблокированного молча не доходят. Для отправителя это выглядит как успех: его заявка хранится и видна ему как исходящая, но заблокировавший её не видит и принять не может. При разблокировке такие заявки удаляются — для отправителя это выглядит как отказ;
  - сообщения заблокированного в чате скрывает приложение, по `userId`. Сервер чат не фильтрует: иначе опрос игры ходил бы в базу, а у остальных игроков чат одинаковый.
- **Группа («компания»):**
  - название 1..40 символов, до 30 участников, до 20 своих групп;
  - участников добавляет и удаляет владелец, только из своих друзей;
  - участник может выйти сам;
  - если уходит владелец (или удаляет аккаунт), группа переходит самому давнему участнику; ушёл последний — группа удаляется;
  - «Играть с группой» может нажать любой участник: создаётся игра, и всем приходят приглашения.

## 6. Приглашения — в памяти

- Пригласить может любой игрок с аккаунтом, пока игра в лобби: своих друзей или всю свою группу. Приглашать можно только друзей (`NOT_FRIENDS`), но участники группы друзьями пригласившего быть не обязаны. Кто уже в игре или с кем есть блокировка, тот молча пропускается.
- Приглашение живёт 30 минут или пока игра в лобби. Принять его — это обычный вход по коду с аккаунт-токеном: отдельного протокола нет.
- `InviteRegistry` держит приглашения в памяти, как и сами игры. Перезапуск сервера теряет игру, и приглашение в неё всё равно было бы бесполезным.
- Входящие (приглашения и заявки в друзья) приложение опрашивает раз в 10 секунд, пока открыт главный экран. Push-уведомления (FCM, APNs) требуют проекта Firebase, ключей APNs и хранения токенов устройств — это следующий шаг ([roadmap](../roadmap.md)).

## 7. Чат — в памяти игры

- **Каналы:** `ALL` видят все, `SEEKERS` — только водящие, `HIDERS` — только прячущиеся. Игрок выбирает «Всем» или «Команде», канал команды сервер берёт из его роли. В лобби ролей ещё нет, поэтому там только `ALL`.
- **Сообщение** — 1..300 символов. Управляющие символы и невидимые символы направления текста (ими можно сделать так, чтобы сообщение читалось не так, как написано) вырезаются. Не больше 5 сообщений за 10 секунд на игрока.
- **Хранение:** последние 200 сообщений в объекте `Game`, удаляются вместе с игрой (через 30 минут после конца).
- **Доставка** — тем же опросом, что и игра. Клиент присылает курсор `SyncRequest.chatAfter` (последний известный `seq`), сервер кладёт в `GameSnapshot.chat` не больше 100 новых сообщений, которые этот игрок может видеть. Отправка сразу возвращает снимок с новыми сообщениями. Старые клиенты не присылают курсор и чат не получают.
- **После конца игры** приложение продолжает опрос, пока открыт экран итогов: там тоже можно переписываться.
- WebSocket или SSE не нужны: задержка до 3 секунд для игрового чата незаметна, а транспорт спрятан за `GameConnection` и меняется отдельно ([ADR 0001](0001-stack.md)).

## 8. Ошибки: `ApiError.reason`

Старые версии приложения знают только `ErrorCode`, поэтому новых кодов нет. Точная причина — новое поле `ApiError.reason: ErrorReason? = null`: у старых клиентов оно игнорируется, а неизвестное значение у новых читается как `null`.

| `reason` | `code` | HTTP |
|---|---|---|
| `NICKNAME_TAKEN`, `EMAIL_TAKEN`, `LIMIT_REACHED`, `BLOCKED_BY_YOU` | `WRONG_STATE` | 409 |
| `INVALID_NICKNAME`, `INVALID_EMAIL`, `INVALID_PASSWORD`, `INVALID_GROUP_NAME`, `INVALID_MESSAGE` | `BAD_REQUEST` | 400 |
| `WRONG_CREDENTIALS`, `ACCOUNT_REQUIRED`, `NOT_FRIENDS`, `NOT_GROUP_OWNER`, `NOT_GROUP_MEMBER` | `FORBIDDEN` | 403 |
| `CODE_EXPIRED`; неверный код — без `reason` | `INVALID_CODE` | 422 |
| `SESSION_EXPIRED` | `UNAUTHORIZED` | 401 |
| `USER_NOT_FOUND` | `NOT_FOUND` | 404 |
| `TOO_MANY_REQUESTS` | `WRONG_STATE` | 429 и `Retry-After` |

## 9. Модерация

- **Блокировка** (раздел 5) — первая линия: каждый сам убирает человека из своей игровой жизни.
- **Жалоба на сообщение** копирует в таблицу `reports` текст, ник и `userId` автора, id игры и номер сообщения. Сама игра к этому времени может быть уже удалена. Запись в базу идёт после снятия блокировки игры: опрос других игроков её не ждёт. Жалоба хранится 90 дней.
- Жалобы разбирают модераторы в админке: запрет чата, бан, сброс ника ([ADR 0008](0008-admin.md)). Фильтр слов — в [roadmap](../roadmap.md). App Store и Google Play требуют для пользовательского контента жалобы, блокировку и контакт для обращений: первые два есть, контакт указывается в правилах сообщества.

## 10. Лимиты

`RateLimiter` в памяти (сервер один), время — из `Clock`.

| Что | Лимит |
|---|---|
| Вход | 10 неудач на логин и 30 на IP за 15 минут |
| Регистрация | 20 на IP в час |
| Письма | 1 в минуту и 5 в час на аккаунт |
| Сброс пароля | 3 в час на email и 10 на IP |
| Заявки в друзья, приглашения | 30 в час |
| Жалобы | 10 в час |
| Сообщения в чате | 5 за 10 секунд на игрока (в `Game`) |

IP клиента за Caddy сервер берёт из `X-Forwarded-For` (`server.forward-headers-strategy: native`).

## 11. Сроки хранения и GDPR

| Данные | Где | Сколько |
|---|---|---|
| Аккаунт: ник, email, хэш пароля, язык | PostgreSQL (RDS) | до удаления аккаунта |
| Сессии (хэши токенов) | PostgreSQL | до выхода; 180 дней без использования |
| Коды из писем (хэши) | PostgreSQL | 15 минут, стираются ежедневной очисткой |
| Друзья, блокировки, группы | PostgreSQL | до удаления аккаунта |
| Заявки в друзья | PostgreSQL | 90 дней |
| Жалобы (с текстом сообщения) | PostgreSQL | 90 дней |
| Игры, координаты, чат, приглашения | память сервера | пока есть игра; итоги игр и маршруты (с согласия) — с [ADR 0007](0007-game-history-and-routes.md#5-сроки-хранения-и-gdpr) |
| Бэкапы базы | RDS (автоматические, в том же регионе) | 7 дней (на Free plan AWS — 1 день); ручные снимки — пока их не удалить |

- **Удаление аккаунта** требует пароль. Каскад стирает сессии, коды, друзей, заявки, блокировки и членство в группах; свои группы переходят другим участникам. В идущей игре ник остаётся до конца игры, это имя игрока. Из автоматических бэкапов данные уходят, когда кончается их срок (не больше 7 дней); ручные снимки RDS делаются только для обслуживания и удаляются после него.
- **Логи.** Сервер не пишет в лог токены, пароли, коды, email, текст чата и координаты. Исключение — локальная разработка: отправитель писем `log` печатает код в консоль с предупреждением «DEV ONLY».
- **На устройстве** — только токены и профиль в `SecureStore` ([ADR 0002](0002-session-storage.md)). Координаты и чат на устройстве не хранятся.
- Email виден только его владельцу (`UserProfile`). Остальным — `UserSummary` (id и ник).

## 12. Один сервер

- Поля «Адрес сервера» больше нет. Сборки без debug ходят на `BuildConstants.SERVER_URL` (Gradle-свойство `hovanki.serverUrl`). Сборка падает, если адрес пустой или не https.
- Debug-сборки ходят на машину разработчика или на `LaunchOptions.server`.
- Сохранённая игра или аккаунт с другого сервера отбрасываются.

Почему: аккаунты, друзья и группы живут на одном сервере, и игроки разных серверов друг друга не видят. Поле адреса было нужно для тестов через туннель; для них остаются debug-сборки и параметры запуска.

## Последствия

- Сервер не стартует без PostgreSQL. С `HOVANKI_MAIL_SENDER=smtp` (так в `compose.yaml`) он не стартует и без настроек SMTP. Порядок деплоя описан в [deploy.md](../deploy.md).
- База в RDS — отдельный счёт, примерно столько же, сколько VM ([deploy.md](../deploy.md#сколько-стоит)). Зато база переживает VM, а бэкапы и восстановление — забота AWS, не наших скриптов.
- Регистрация от доставки писем не зависит: аккаунт работает и без подтверждения. От неё зависят подтверждение email и сброс пароля. Письма с Gmail или без своего домена могут попадать в спам. Для магазинов нужен свой домен и сервис рассылки (Amazon SES и т. п.) с SPF и DKIM.
- Старые сборки создают игры как гости и не получают чата и приглашений.
- Перезапуск сервера по-прежнему теряет игры, а вместе с ними чат и приглашения. Аккаунты, друзья и группы переживают перезапуск.
- Тестам сервера и e2e нужен PostgreSQL: встроенный или по `HOVANKI_TEST_DATABASE_URL`.
- Для магазинов нужны политика конфиденциальности, правила сообщества, контактный email, веб-страница удаления аккаунта (Google Play), ответы о приватности (App Store Connect) и Data safety (Play Console).
