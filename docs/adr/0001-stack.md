# ADR 0001. Выбор стека: Kotlin Multiplatform + Compose Multiplatform

- **Статус:** Accepted (принято)
- **Дата:** 2026-09-25
- **Автор:** Denys Bohusevych

## Контекст и требования

Делаем уличную игру в прятки для Android и iOS: сужающаяся зона, обмен геоданными через сервер, позже — определение близости игроков по Bluetooth (первая версия работает только на геолокации). Все игроки находятся на улице, прятаться в зданиях запрещено.

Требования, которые определяют выбор стека:

- Одна кодовая база на две платформы: поддерживать два отдельных приложения слишком дорого.
- Прямой доступ к системным API: геолокация (в том числе в фоне), BLE-сканирование и вещание, фоновые сервисы.
- Тонкая настройка поведения на iOS, где фоновые режимы BLE и геолокации сильно ограничены.
- Общая логика (зона, фильтрация RSSI, учёт точности GPS) должна быть написана один раз и вести себя одинаково на обеих платформах.

## Решение: Kotlin Multiplatform + Compose Multiplatform

Пишем приложение на Kotlin Multiplatform (KMP), UI делаем на Compose Multiplatform. Общий код занимает большую часть проекта, платформенными остаются только геолокация, BLE и фоновые сервисы.

Почему это подходит именно нам:

- **Прямой доступ к нативу без мостов.** На Android это обычный Kotlin/JVM со всеми Android API. На iOS Kotlin/Native вызывает CoreLocation и CoreBluetooth напрямую, без сериализации и асинхронных каналов.
- **Один язык на весь проект.** Логика, UI, платформенные реализации и сервер (Spring Boot на Kotlin) пишутся на Kotlin. Модели сообщений между клиентом и сервером общие.
- **Платформенный код изолирован.** Через expect/actual описываем общий интерфейс (например, `LocationProvider`, `ProximityScanner`), а реализации под каждую платформу лежат отдельно.
- **Производительность.** На обеих платформах нативный код, без JS-движка и без прослойки между логикой и системой.
- **Постепенность.** Если какой-то экран на iOS понадобится сделать на SwiftUI, это можно сделать точечно, не трогая остальное приложение.

## Почему не другие варианты

Альтернативы рабочие, но каждая проигрывает либо в доступе к системным API, либо в объёме поддержки.

| Вариант | Доступ к GPS/BLE | Языки в проекте | Главная причина отказа |
|---|---|---|---|
| KMP + Compose (выбран) | Напрямую, без мостов | Kotlin (+ минимум Swift при необходимости) | — |
| Flutter | Через плагины и platform channels | Dart + Kotlin + Swift | Тонкая настройка фонового BLE и GPS уходит в нативный код на двух других языках |
| React Native | Через Turbo Modules / JSI | JS/TS + Kotlin + Swift | Ещё один слой между кодом и системой, сложнее отладка натива |
| Два нативных приложения | Полный | Kotlin + Swift | Две кодовые базы, вся логика пишется и тестируется дважды |
| Ядро на Rust/C++ | Нет, нужны биндинги к системным API | Rust + Kotlin + Swift | Нет тяжёлых вычислений, которые оправдали бы дополнительный язык и интероп |

Flutter — ближайшая альтернатива: у него больше готовых библиотек и быстрее старт. Мы выбираем KMP, потому что основные риски проекта в фоновом поведении BLE и геолокации на iOS, и там прямой доступ важнее экосистемы.

## Риски и ограничения

Большинство рисков связаны с ограничениями платформ, а не с выбором фреймворка; любой стек столкнётся с ними.

- **BLE в фоне на iOS.** Свёрнутый iPhone вещает в урезанном виде, Android его практически не видит. При этом iPhone видят друг друга, проблемна только связка «iPhone прячется, Android ищет». BLE переносим на этап после MVP и для этой связки закладываем fallback на расстояние по GPS.
- **Точность близости.** RSSI даёт погрешность в несколько метров, поэтому показываем «горячо / тепло / холодно» со сглаживанием, а не метры.
- **Фоновая геолокация.** Работает с заблокированным экраном в кармане. iOS требует фоновый режим location; если раунд стартует из открытого приложения, хватает разрешения «При использовании», Android — foreground service с типом location.
- **Сборка iOS.** Нужен Mac с Xcode. Swift-only API (без Obj-C совместимости) вызываем через небольшую Swift-обёртку.
- **Экосистема.** Библиотек под KMP меньше, чем под Flutter. Для нашего набора задач готовые решения есть, недостающее дописываем через expect/actual.
- **Батарея.** Постоянный GPS в фоне (а позже и BLE) заметно расходует заряд; частоту обновления координат делаем настраиваемой.
- **GDPR.** Геоданные — персональные данные: явное согласие, хранение только на время игры и удаление после.

## Предлагаемый стек

| Задача | Решение | Где живёт |
|---|---|---|
| UI | Compose Multiplatform | Общий код |
| Асинхронность | kotlinx.coroutines + Flow | Общий код |
| Сеть (HTTP-опрос) | Ktor Client | Общий код |
| Сериализация сообщений | kotlinx.serialization | Общий модуль клиента и сервера |
| BLE | Kable (после MVP) | Общий код, фоновые нюансы — платформенный |
| Геолокация | expect/actual: FusedLocationProvider (Android), CLLocationManager (iOS) | Платформенный |
| DI | Koin | Общий код |
| Сервер | Spring Boot на Kotlin, REST: клиент раз в несколько секунд отправляет позицию и в ответе получает состояние игры, сервер управляет зоной и состоянием игры | Отдельный модуль |
| Карта | MapLibre через maplibre-compose, векторные тайлы на базе OpenStreetMap (провайдер тайлов — на этапе прототипа) | Общий код |
| Сканер QR | expect/actual: CameraX + ML Kit (Android), AVFoundation (iOS) | Платформенный |
| Коды находки (TOTP) | Своя реализация на Kotlin (HMAC-SHA1), одна и та же на клиенте и сервере | Общий модуль клиента и сервера |

WebSocket в MVP не используем: координаты и так уходят раз в несколько секунд, расписание зоны клиент получает заранее, а задержка событий в 3–5 секунд для игры незаметна. HTTP-опрос устойчивее к обрывам мобильной связи и надёжнее работает в фоне на iOS. Транспорт в общем коде спрятан за интерфейсом `GameConnection`, поэтому при появлении мгновенных функций (чат, живое отслеживание) его можно заменить на WebSocket или SSE без изменений в остальном приложении.

## Находка игрока

Находка подтверждается сканированием QR-кода с телефона прячущегося, а не кнопкой «нашёл». Отсканировать код можно только стоя рядом, поэтому это доказательство реальной встречи.

Код меняется каждые 20–30 секунд (TOTP). При старте игры сервер выдаёт каждому прячущемуся секретный ключ. Приложение генерирует из ключа и текущего времени короткий код и показывает его в QR вместе с ID игрока. Сервер пересчитывает код со своей стороны. Заранее сфотографировать и переслать код бесполезно, а генерация работает без интернета.

Заявка на находку:

1. Ищущий нажимает «нашёл» и выбирает игрока.
2. Сервер проверяет расстояние по GPS: игроки дальше 30–50 м (с учётом accuracy) — заявка отклоняется.
3. Прячущемуся приходит экран «Покажи код» с таймером 60 секунд и кнопкой «Оспорить».
4. Код показан — находка засчитана. Нет реакции до конца таймера — засчитана автоматически. Оспорил — спор (см. «Честная игра»).

Молчание не помогает: не показал код — всё равно пойман.

Запасной вариант: прячущийся называет 4 цифры того же TOTP-кода голосом, ищущий вводит их вручную (камера не фокусируется, разбит экран).

После MVP: автоматическое подтверждение по BLE (сильный сигнал несколько секунд + нажатие ищущего), QR остаётся основным способом. NFC не используем: iPhone не эмулирует NFC-метку для обычных приложений, связка iPhone ↔ Android не заработает.

## Точность GPS

GPS в городе — подсказка, а не судья. На открытом месте телефон даёт 3–10 м, но у высоких домов сигнал отражается от стен и точка может прыгнуть на 20–30 м, в том числе внутрь здания. Операторы самокатов (Bolt, Tier) по той же причине проверяют парковку камерами и визуальным позиционированием, а не только GPS.

Правила для всех проверок:

- Никаких решений по одной точке: только по нескольким замерам подряд (15–30 секунд).
- Точки с accuracy хуже 20 м в проверках не используются.
- Определение «игрок в здании» — мягкий сигнал: попадание в контур здания из OSM плюс ухудшение сигнала. На Android дополнительно смотрим уровень сигнала спутников через `GnssStatus`, на iOS такого API нет, остаётся только accuracy.
- Границы зоны проверяются с запасом на погрешность.
- При создании игры подсказываем, если зона сильно застроена: лучше всего игра работает в парках и районах с невысокой застройкой.

## Честная игра

В реальном времени судьи нет: хост тоже играет. Поэтому подозрительное поведение не наказывается, а раскрывает игрока — ищущие видят его последнюю точку. Ложное срабатывание стоит дёшево, а жульничество теряет смысл.

| Ситуация | Реакция системы |
|---|---|
| Похоже, в здании дольше минуты | Позиция раскрывается ищущим |
| Нет обновлений координат 30–60 с (выключен GPS, интернет, смахнуто приложение) | Ищущим показывается последняя известная точка |
| Подмена GPS | `isMock()` на Android, `isSimulatedBySoftware` на iOS, отсев невозможных скоростей на сервере |
| Выход за зону | Предупреждение и таймер на возврат; не вернулся — выбывает (уверенность высокая, решение автоматическое) |
| Спор о находке | Голосование игроков, не участвующих в споре |

**Споры о находке.** Голосуют все, кто не участвует в споре, одним нажатием в приложении. Если за минуту голосов нет, действует правило по умолчанию: по GPS игроки были ближе 30–50 м — находка засчитана, дальше — нет. Спорящие на время разбора замораживаются.

**Разбор после игры.** В конце раунда всем показываются треки движения игроков на карте: кто сидел в здании или срезал за зоной, видно всей компании.

**Судья-наблюдатель** — опциональная роль для больших игр: видит всех на карте и разбирает споры. Игра от этой роли не зависит.

**После MVP:** репутация для публичных лобби — жалобы от разных игроков из разных игр снижают рейтинг, затем временный запрет на публичные игры.

## Отличия реализации от ADR

Решение в силе; ниже — где код отличается от формулировок выше.

- **expect/actual vs интерфейсы.** expect/actual используется только для мелкой платформенной «склейки». Платформенные сервисы — обычные интерфейсы в `commonMain` с реализациями в `androidMain`/`iosMain`, которые связываются через Koin: так их проще подменять фейками в тестах. Имена из ADR (`LocationProvider`, `ProximityScanner`) сохранены.
- **Карта.** Пока вместо MapLibre — заглушка на Canvas (`ZoneRadar`). MapLibre (maplibre-compose) подключим, когда выберем провайдер тайлов.
- **Сканер QR.** `CatchCodeScanner` — заглушка; ручной ввод 4 цифр кода работает и является полноценным способом подтверждения.
- **BLE.** Не начат, переносится на этап после MVP (`ProximityScanner` сейчас — no-op).
- **Пороги.** Диапазоны из ADR зафиксированы конкретными значениями по умолчанию в `GameRules` (`shared/.../protocol/Settings.kt`): дистанция находки 40 м, период кода 30 с, 4 цифры, окно решений 20 с и минимум 3 точки, раскрытие при молчании через 45 с, таймеры кода и голосования по 60 с.

Что из ADR ещё не сделано — в [roadmap](../roadmap.md).
