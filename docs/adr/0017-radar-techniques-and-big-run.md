# ADR 0017. Техники радара, большой прогон трёх телефонов и отчёт в админке

- **Статус:** Accepted (шаг 1 реализован 2026-09-29: прогон на сервере; 2026-09-30 — шаг 2: модули `:radar` и `:device`, шаг 3: каналы и хосты, шаг 4: чоканье, тени и карточки, шаг 7: сценарий большого прогона и чек-лист, шаг 5: режимы, GATT и UWB для двух iPhone в карманах — вслепую, прогон на телефонах впереди; шаг 6 отложен)
- **Дата:** 2026-09-29
- **Автор:** Denys Bohusevych (черновик — Claude Code)
- **Пересматривает:** [ADR 0016](0016-iphone-overflow-radar.md) — «Чего не делаем» и «Исследование», п. 4 и 6 (GATT, будить экран уведомлениями, фоновое аудио, Wi-Fi Aware, Multipeer); [ADR 0012](0012-nearby-radar.md) — «калибровку касанием» из «Отличий реализации». **Дополняет:** [radio-lab.md](../radio-lab.md) (журнал и прогон переезжают на сервер), [ADR 0008](0008-admin.md) (вкладка «Радиолаба» в админке).

> **План.** Как устроить радар, чтобы каждую идею можно было включить, измерить и выбросить, не трогая остальные. Как три телефона (два iPhone и Android) проходят один большой прогон по часам сервера и сразу отдают журналы на сервер. Как сервер сводит данные и показывает отчёт в админке. При принятии статус меняется на Accepted, по мере этапов добавляются «Отличия реализации».

## Контекст

Радар собран из нескольких способов, и почти каждый держится на догадке о поведении iOS или Android. Лаборатория ([radio-lab.md](../radio-lab.md)) проверяет догадки по одной: один телефон, Мак, экспорт журнала руками после каждого опыта. Выход 1 подтвердил маску overflow и «замёрзший» жетон; остальное впереди.

Решения владельца (2026-09-29):

1. **Пересмотреть отвергнутое.** Проверить всё, кроме ультразвука; отдельно — пару «два iPhone в карманах», в том числе по UWB.
2. **Один большой прогон:** два iPhone и Android одновременно, шаги по часам сервера, журналы сразу уходят на сервер.
3. **Сервер копит и сводит** данные всех прогонов, отчёт — в админке.
4. **Ритуал «чокнуться телефонами»** (калибровка касанием) — проверить, даёт ли он что-то.
5. **Карман — не радио:** где телефон, определяют другие датчики.

Что нашлось, пока писался план:

- **Реклама Android-прячущегося, похоже, не уходит в эфир.** UUID сервиса (18 байт) и service data со 128-битным UUID (22 байта) — это 40 байт, а обычная реклама вмещает 31. `startAdvertising` в таком случае отвечает `ADVERTISE_FAILED_DATA_TOO_LARGE` (код 1). На телефоне ещё не проверено: первый запуск на Android покажет в журнале `adv failed code 1`. У ботов радио ненастоящее, поэтому e2e этого не видит. (Шаг 3: `AdBudget` считает эти байты, симулятор эфира отказывает так же, раскладка в игре заменена — «Отличия реализации».)
- **Core Haptics замолчал при блокировке с причиной 1** (выход 1). По заголовку CoreHaptics это `audioSessionInterrupt` — прервана аудиосессия, — а не `applicationSuspended` (2), на которое рассчитывало исследование ADR 0016. Приложение при этом не спало: дыр в тиках нет. Значит, двигатель стоит попробовать держать своей аудиосессией или перезапускать после прерывания. Журнал будет писать имя причины, а не число.

## Решение коротко

1. **Два новых модуля с платформенным кодом:** `:radar` — всё, что между телефонами (Bluetooth, GATT, UWB, Wi-Fi Aware); `:device` — телефон сам по себе (карман, движение, датчики, вибрация, режимы экрана и фона). Чистые правила, которые считает и сервер, и разбор журналов — в `:shared`; лаборатория — в `:clientCore/lab`.
2. **Каждая идея — «техника»:** id, вид, требования, статус и **заранее записанный критерий**, при котором её оставляем. Техники либо **дополняют** друг друга (каналы: в итоге останется несколько), либо **конкурируют** (сглаживание, карман, вибрация: останется одна).
3. **Пишется всё:** каждое действие и каждое показание каждой техники, сырые кадры эфира, жизнь приложения, датчики, батарея. Журнал v2.
4. **Прогон живёт на сервере:** админ создаёт его в админке, телефоны входят по коду, шаги меняются по часам сервера у всех сразу, пульт — в админке, журналы уходят на сервер каждые 5 секунд.
5. **Сервер хранит сырые журналы 90 дней** и считает отчёт: покрытие по парам и каналам, карточки техник против критериев, «что было бы без техники X», калибровки, расстояния. Сквозная сводка по всем прогонам — по моделям телефонов.
6. **Всё за флагом сервера `RADIO_LAB`** (выключен по умолчанию): только тестовые телефоны прогона, никаких координат, отчёт только админам.

Новые модули — по правилам AGP 9 из `CLAUDE.md` (`com.android.kotlin.multiplatform.library`, блок `kotlin { android { … } }`).

**Почему карман не в `:radar`.** Где телефон, решают акселерометр, гравитация, датчик приближения и свет, а не эфир. Радару нужен только ответ (`Carry`): для поправки за тело и чтобы выбрать, какой вибрацией бить. Поэтому `:radar` не зависит от `:device`; их связывает тот, кто ими пользуется: игра или лаборатория. Лаборатория проверяет оба модуля вместе.

Один модуль на область, а не Gradle-модуль на каждую технику: десяток KMP-модулей с iOS-таргетами — это медленная сборка и лишняя возня с фреймворком. Границы держат пакеты (`radar/channel/overflow/`, `radar/link/gatt/` …) и тест, который проверяет, что техники не импортируют друг друга.

## 2. Техники

### 2.1 Что такое техника

```kotlin
interface Technique {
    val id: String               // "ble.overflow", "gatt.link", "uwb.ni", "pulse.core_haptics", "calib.touch"
    val kind: TechniqueKind      // CHANNEL, LINK, RANGING, MODE, PULSE, CARRY, SMOOTHING, CALIBRATION, INFERENCE
    val status: TechniqueStatus  // LAB, CANDIDATE, GAME
    fun available(device: DeviceCaps): Availability  // чип, ОС, разрешение, entitlement, фоновый режим
}
```

- **Статусы:** `LAB` — только в лаборатории; `CANDIDATE` — в прогонах всегда, в играх — только если сервер разрешил; `GAME` — в игре у всех. Выброшенная техника удаляется из кода и остаётся строкой на «кладбище» этого ADR — с цифрами, за что.
- **Каталог** (`RadarCatalog`, `DeviceCatalog`) — список техник платформы. Игра и лаборатория берут из него, что включить; по имени техники не знает никто.
- **Критерий записан до замеров** (§2.3). Отчёт сверяет с ним каждую технику: «оставить», «выбросить» или «мало данных».
- **Разрешение для игр** — одна настройка сервера «кандидаты, разрешённые в играх» в админке (список id), вместо отдельного `ServerFeature` на каждую идею. Хост в лобби техник не выбирает: это транспорт, а не правило игры (как в ADR 0016).

### 2.2 Каналы и хосты

**Канал** — формат жетона в эфире: что положить в рекламу, какие кадры слушать, как разобрать кадр в жетон. Это общий Kotlin, проверяемый тестами на JVM.

**Хост** — один на платформу: Android, iOS, JVM-симулятор для ботов, Мак. Он владеет рекламой и сканером, собирает **одну** рекламу из вкладов всех включённых каналов и знает правила ОС:

- iOS: одна реклама на приложение; в фоне её не начать и не изменить; имя и данные в фоне не уходят, UUID уходят в маску overflow;
- Android: обычная реклама — до 31 байта, больше — через наборы рекламы (advertising sets), если телефон их умеет.

Не влезает или конфликтует — хост пишет в журнал раскладку байт и что отброшено. Принятые кадры он раздаёт декодерам каналов.

Вслепую на iOS пишется только хост, один раз; каналы проверяются в облаке. JVM-хост — это симулятор эфира с правилами ОС: новый канал сразу честно ведёт себя у ботов, без ручной правки `bot/Radio.kt`.

**Вывод на сервере** (новое): `infer.witness` — «свидетель». A и B друг друга не слышат, но оба громко слышны C: значит, оба рядом с C, а значит, и друг с другом. Может закрыть пару «два iPhone в карманах», когда рядом есть третий телефон. Чистая функция; проверяется на данных прогона — у трёх телефонов как раз треугольник.

## 3. «Чокнуться телефонами»: калибровка касанием

ADR 0012 оставил её вариантом для моделей, которых нет в `radio_calibration`, и её не сделали. Теперь это техника `calib.touch`.

- **Как:** двое касаются телефонами. В этот момент расстояние — ноль, и RSSI каждого направления — «ноль» этой пары. Разница с тем, что пара должна слышать вплотную по своим моделям, — поправка пары на игру.
- **Как поймать момент без кнопки:** удар в акселерометре у обоих телефонов в пределах ±150 мс по часам сервера плюс пик RSSI пары в ту же секунду. Кнопка «чокнулись» — запасной вариант и истина для проверки детектора.
- **В прогоне:** в начале каждая пара чокается трижды (повторяемость), спинами и торцами (ориентация); в конце — ещё раз (дрейф). Потом — дорожка расстояний (§6).
- **Отчёт:** ошибка полосы против истины для `calib.none`, `calib.model` и `calib.touch`; разброс трёх касаний; дрейф. Оставляем, если с касанием ошибка полосы меньше хотя бы на 10 процентных пунктов, а три касания расходятся не больше чем на 6 dB. Иначе — на кладбище, с цифрами.
- **В игре** это был бы ритуал в лобби («чокнитесь с соседом»). Как он будет выглядеть, решаем после цифр.

## 4. Журнал v2: пишем всё

Схема [radio-lab.md §4.1](../radio-lab.md#41-что-пишется) остаётся. В каждое событие добавляются `run` (id прогона), `seq` (номер события на устройстве, чтобы выгрузка не давала дублей) и `tech` (id техники). Новые виды:

| `k` | Что |
|---|---|
| `frame` | сырой кадр нашего формата: у Android — байты записи скана в hex; у iOS — словарь рекламы: имя, UUID сервисов, UUID маски, service data и данные производителя в hex, мощность, connectable |
| `air` | чужие кадры раз в секунду: сколько каких (iBeacon, маски, прочее Apple) и биты чужих масок — для раскладки V1 |
| `adv` | вдобавок полная раскладка рекламы, её бюджет в байтах и что не влезло |
| `link` | GATT: подключение, отключение с ошибкой, запись, notify, `readRSSI` |
| `range` | UWB: расстояние, направление, состояние (идёт / приостановлено / снято) и причина |
| `aware` | Wi-Fi Aware: сопряжение, соединение, отчёт о связи |
| `audio` | прерывания и смены маршрута аудиосессии |
| `haptic` | вдобавок причина остановки двигателя именем |
| `shadow` | ответ техники в тени → состояние. Пишет телефон, и только `carry.v2` (`tech`, `state`, `reason`); сглаживания и калибровки в тени не идут — отчёт пересчитывает их из `rx` |
| `touch` | найденное касание: пара, время, RSSI, сила удара. Не событие журнала: его считает отчёт (`LabReport.touches`) из `impact` двух телефонов и `rx`; телефон пишет `impact` и `mark` с `action = touch` |
| `step` | смена шага прогона (от сервера) |
| `net` | сеть и выгрузка: отправлено, ответ, очередь |
| `thermal` | температурное состояние телефона |

Ещё два вида шага 4: `impact` (удар акселерометра: `peak`, `ago`) и `mark` кнопки «Чокнулись с …» (`action = touch`) — сырьё для касания. Своих кадров пишется всё. Чужих — только счётчики и биты, одним событием в секунду: в городе их сотни в секунду. Координат по-прежнему нет: у `gps` только точность и возраст. Разбор (`:shared/lab`) читает и v1, и v2.

Объём: 50–150 событий в секунду на телефон, около 5 КБ/с после gzip. Час прогона на трёх телефонах — порядка 100 МБ сырых данных на сервере.

## 5. Прогон на сервере

### 5.1 Вход

1. Админ в «Радиолабе» создаёт прогон: название, сценарий (из каталога в `:shared`), метки устройств (`A`, `B`, `droid`, по желанию `mac`), причину. Получает код из 6 символов и QR.
2. Телефон (debug-сборка): Lab → «Войти в прогон» → код или QR. Он отправляет метку, модель, ОС, сборку и commit, возможности (Bluetooth: наборы рекламы и их число, LE Coded; UWB; Wi-Fi Aware; разрешения).
3. Сервер отвечает токеном устройства (живёт с прогоном), **секретом радара на прогон** (жетоны меняются, как в игре, и сервер знает, чей жетон) и планом.
4. Часы — как сейчас (`GET /api/v1/time`, 5 запросов, берётся с меньшим RTT), раз в минуту. Сервер вдобавок ставит время приёма на каждую пачку.

Мак входит тем же кодом: `run.sh --lab --run <код>`.

### 5.2 План и пульт

- **Сценарий** — шаги. У шага длительность или «до кнопки»; для каждого устройства — какие техники включены, текст для человека («A — в карман спереди, B — на стол экраном вверх») и **истина для отчёта**: расстояние в каждой паре, где каждый телефон, что делает человек. Отметки ставятся сами.
- Все идут по плану сервера: `GET /api/v1/lab/runs/{id}/state` раз в 2 с (шаг, когда начался, какой следующий). Техники переключаются в одну и ту же миллисекунду по часам сервера; расхождение — только ошибка часов.
- **Пульт** — страница прогона в админке (на ноутбуке или телефоне): шаг, указания каждому, обратный отсчёт, «Дальше», «Повторить шаг», «Пауза». Те же кнопки — на любом телефоне прогона. Телефоны с экраном звучат и вибрируют на переходе, заблокированным приходит уведомление.
- Проверка сценария из `LabRunScript` («заблокированный шаг не меняет рекламу») переезжает в `:shared` и проверяется для каждого устройства.

### 5.3 Выгрузка

- Каждые 5 с — пачка (JSONL, gzip) `POST /api/v1/lab/runs/{id}/events` с `seq` от и до. Сервер подтверждает; повтор безвреден.
- Нет сети — пачки ждут в памяти (тот же кольцевой буфер) и уходят позже. «Экспорт» в «Поделиться» остаётся запасным путём.
- iOS в фоне: приложение живо (GPS или режим), выгрузка идёт. Если iOS всё-таки приостановила его, это видно по тикам, а пачки уйдут, когда приложение проснётся.

### 5.4 Живой вид

Пока идёт прогон, админка показывает по каждому устройству: пачка сколько секунд назад, сдвиг часов, состояние приложения, Bluetooth, батарею, шаг; по каждой паре и каналу — слышно ли за последние 10 с и медиану RSSI. Если что-то не пишется, это видно сразу, на улице, а не вечером.

## 7. Сервер: хранение и отчёт

**Таблицы** (новая миграция; всё удаляется вместе с прогоном, `ON DELETE CASCADE`):

| Таблица | Что |
|---|---|
| `lab_runs` | прогон: название, сценарий и его версия, кто создал (сотрудник), время создания, начала и конца, состояние |
| `lab_devices` | устройство прогона: метка, модель, ОС, сборка, commit, возможности, хеш токена, время входа и последней пачки |
| `lab_chunks` | сырые пачки: устройство, `seq` от и до, время от и до, число событий, время приёма, тело (gzip) |
| `lab_reports` | отчёт прогона (JSON) и версия разбора |

**Пределы:** до 8 устройств на прогон; вход и выгрузка — до 24 часов после создания; до 300 МБ сырых данных на прогон; `RateLimiter` на устройство. Флаг `RADIO_LAB` выключен — маршрутов нет (404).

**Сроки:** сырые пачки хранятся 90 дней после конца прогона (`DataRetention`); отчёты и сквозные сводки — без срока: в них метки, модели и числа, персональных данных нет.

**Отчёт** считает чистая функция из `:shared/lab` вне потока запроса (как `HistoryWriter`): понемногу во время прогона — для живого вида, целиком — после «Завершить». Разделы:

1. **Покрытие:** по шагам, для каждой пары «кто вещает и в каком состоянии → кто слушает и в каком» и для каждого канала — показаний в секунду, RSSI (медиана, p80, min, max), самая длинная пауза и что в это время было с приложением.
2. **Карточки техник:** критерий из §2.3 → «оставить», «выбросить» или «мало данных», с цифрами.
3. **Без X:** полосы по всем каналам против полос без канала X — в скольких процентах секунд они совпадают и где X был единственным.
4. **Калибровка и чоканье** (§3).
5. **Расстояния:** RSSI и метры UWB против отметок — по парам, каналам и месту телефона.
6. **Карман:** классификаторы против разметки.
7. **Вибрация:** попытки, результаты, причины остановки, отметки «почувствовал».
8. **Батарея и нагрев** по устройствам и блокам.
9. **Маска:** кадры, качество разбора, чужие биты.

**Сквозная сводка** по всем прогонам: пара моделей × канал × место телефона × расстояние → распределение RSSI. Отсюда — предложения для порогов полос и `POCKET_OFFSET_DB`. Сами правила по-прежнему меняются отдельным PR с тестом.

**Админка** — вкладка «Радиолаба», только для роли admin: список прогонов, создание, пульт и живой вид, отчёт, скачивание сырых журналов (с причиной и записью в журнал аудита; для `:e2e:lab merge`), удаление (с причиной). Таблицы и простые полосы SVG строятся через DOM: `textContent`, без `innerHTML` и без чужих хостов, как вся админка.

## 8. Приватность и безопасность

- Прогон создаёт админ, телефоны входят по коду. Экран лаборатории есть только в debug-сборках; release и preview в прогоны не входят.
- **Координат нет нигде**: у `gps` только точность и возраст, как сейчас. Нет аккаунтов, чата и игроков. Жетоны — жетоны прогона (от его секретов), не игровые.
- RSSI, жетоны, сырые кадры и данные датчиков лежат на сервере в таблицах лаборатории и видны только админам в отчёте, игрокам — никогда. Это новое исключение из правила «RSSI никому» в `CLAUDE.md`. Когда появится код, туда добавится: «журналы лаборатории — только тестовые телефоны прогона, без координат, 90 дней, только админам».
- Адреса Android и идентификаторы iOS хешируются с солью прогона.
- Каждый маршрут админки — с `Staff`, ролью admin, причиной и `AuditLog` в той же транзакции ([ADR 0008](0008-admin.md)).
- Из настоящих игр журнал на сервер не уходит. Если это понадобится — отдельное решение: только игры, где все игроки — телефоны прогона.

## Отличия реализации

### Шаг 1 (2026-09-29)

Шаг 1 из §9 сделан ([radar-run.md](../radar-run.md), §1): протокол `:shared/protocol/Lab.kt` и `:shared/lab`, сервер (`server/.../lab/`, `LabController`, `LabAdminController`, миграция V11), телефон (`clientCore/.../lab/`, карточка «Server run» в Lab), вкладка «Радиолаба» в админке, `e2e` (`LabBot`, `LabRunTest`, `run.sh --lab --run`). Чем код отличается от текста выше:

- Миграция — `V11__radio_lab.sql` (не V10: V10 занята). Имя админа в `lab_runs` только `created_by_name`, без id пользователя; через год (как в журнале аудита) `DataRetention` его стирает.
- **Жетон радара выдаёт сервер** при входе (`radarToken`, 8 hex, уникален в прогоне): телефон вещает его как жетон прячущегося и пробы. Вращения жетонов, как в игре, пока нет; проба по-прежнему может менять свой жетон, `adv` пишет, что вещалось, так что сведение сопоставляет и их.
- **Повторный вход = новое устройство:** телефон, вошедший снова с той же меткой (перезапуск), получает новую строку `lab_devices` и новый жетон; старая строка хранит свои пачки. Метки в прогоне не уникальны, устройств до 8 (с повторными входами).
- **Маршруты админа работают и с выключенным флагом** (иначе нельзя ни включить фишку из админки, ни прочесть старый отчёт); маршруты телефона при выключенном — 404, и вход, и токен.
- **Выгрузка:** тело — строки журнала как есть (`application/x-ndjson`, можно `Content-Encoding: gzip`), границы пачки — в запросе (`seqFrom`, `seqTo`, `count`, `tFrom`, `tTo`), не в JSON. Сервер хранит пачку сжатой сам. Ответ `ackedSeq` — только то, что хранится; повторная пачка с тем же `seqFrom` записи не добавляет, а телефон досылает хвост новой пачкой. Пределы: 4 МБ на пачку (до и после распаковки), 5000 событий, 300 МБ (сжатых) на прогон, `RateLimiter` на устройство и на IP входа.
- **Льготное время выгрузки** (в плане его не было): законченный прогон ещё 30 минут (`hovanki.lab.upload-grace`) берёт последние пачки, и каждая пересчитывает отчёт. Без него телефоны, дописывающие журнал после конца плана, получали бы `LAB_RUN_CLOSED`, и «всё выгружено» не достигалось бы. Закрытый (законченный или старше окна входа) прогон отвечает `WRONG_STATE` + `LAB_RUN_CLOSED`.
- **План считают одинаково и сервер, и телефон** (`LabRunPlan`, `:shared`): `NEXT` на «создан» запускает шаг 0, потом переходит к следующему, на последнем — завершает; `REPEAT` начинает шаг заново; `PAUSE`/`RESUME` сдвигают начало на длину паузы; любое действие — `revision + 1`. Шаг с временем кончается сам по часам сервера, но сервер сохраняет это, когда на прогон кто-то смотрит (опрос телефона, страница админа, пачка). Конец прогона — только по ответу сервера: телефон, досчитавший до конца сам, держит последний шаг и сразу переспрашивает.
- Пульт админа: действие, что-то меняющее, пишется в `AuditLog` (`LAB_RUN_CONTROL`), пустое — нет; действия телефонов не пишутся. Создание, скачивание сырых журналов (`POST .../raw`, ответ — zip, по файлу на устройство, пишется потоком) и удаление (`POST .../delete`, 204, вместе с устройствами, пачками и отчётом) — `LAB_RUN_CREATE`, `LAB_RUN_DOWNLOAD`, `LAB_RUN_DELETE`. Удаление — `POST`, как остальные маршруты админки с причиной.
- **Отчёт** считает `LabReportWriter` вне потока запроса, когда прогон стал «закончен» любым способом, и заново на каждую пачку в льготное время и на «Завершить»; хранится как JSON (`lab_reports`, версия 1). Событий читается не больше 500 000 на прогон (`hovanki.lab.max-report-events`): у большего в отчёте устройства и одна строка о том, что сводить надо на компьютере. Жетон, который не принадлежит ни одному устройству прогона, в отчёте и в живом виде — просто `?`: он может быть чужой игры рядом, а отчёт живёт дольше журналов. События с временем вне окна прогона отбрасываются и считаются в проблемах.
- **Живой вид** — в памяти (`LabLive`): показания за 30 с, пары «кто → кого, канал», слышно за 10 с и медиана RSSI; прогон, от которого 10 минут ничего не приходило, забывается.
- **Телефон:** `LabRunFollower` опрашивает состояние раз в 2 с, вход и выход идут на процессном скоупе, так что закрытие панели не обрывает последнюю выгрузку. ### Шаг 3 (2026-09-30)

Шаг 3 из §9 сделан ([radar-run.md](../radar-run.md), §3): каналы, хосты, симулятор эфира, журнал `frame`/`air`/`adv`. Чем код отличается от текста выше и что решено по дороге:

- **Раскладка Android-прячущегося в игре меняется на `scan_response`.** В плане (§2.3, radar-run.md §3) стояло «в игре не меняем, решит прогон». Прежняя раскладка — UUID сервиса (18 байт) и service data со 128-битным UUID (22 байта) в одном пакете — это 40 байт против 31 у обычной рекламы; `startAdvertising` отвечает на неё `ADVERTISE_FAILED_DATA_TOO_LARGE` на каждом телефоне (это контракт API, а не причуда модели), то есть Android-прячущиеся в эфир не выходили. Честный симулятор эфира не пропускает такую рекламу, e2e-сценарии радара упали бы, а раскладка, которая не может работать, — не базовая линия для сравнения. Поэтому в игре теперь `ble.service_data.scan_response`: UUID сервиса в рекламе (18 байт), жетон service data в ответе на скан (22 байта). Поля те же там, где их ищут слушатели: фильтр по UUID сервиса срабатывает, service data приходит в ответе на скан, а Android и CoreBluetooth склеивают рекламу и ответ в одну запись. Прогон сравнивает её с `bare` (service data без списка UUID, 22 байта) и `mfr` (данные производителя, 24 байта). Формат жетона и протокол игры не менялись; старые сборки Android в эфир не выходили вовсе, так что совместимость ломать нечему.
- **Пакеты и граница.** `app.hovanki.radar` — корень (модель, техника, каталог, фасад `HostProximityRadio`, `OsRules`, `AdBudget`); `app.hovanki.radar.channel.<id>` — по пакету на канал (`servicedata`, `name`, `ibeacon`, `overflow`); `app.hovanki.radar.host` — хосты (`AndroidAirHost`, `IosAirHost`, `JvmAirHost` с `SimulatedAir`); `app.hovanki.radar.lab` — эфир лаборатории на хосте. Правило `ModuleBoundariesTest` стало таким: пакет канала импортирует только корень и `:shared`; `host` и `lab` могут (как и корень) импортировать каналы — каталог их перечисляет, хосты и лаборатория запускают, — но не друг друга; корень не импортирует ни `host`, ни `lab`. Поэтому `AirHost` — интерфейс корня: его берёт фасад.
- **Статусы.** Канал `ble.overflow` остаётся `LAB`: ADR 0016 (за флагом `OVERFLOW_RADAR`) не реализован, игра его не вещает. Каналы игры — `ble.service_data.scan_response`, `ble.name`, `ble.ibeacon` и `ble.ibeacon.region` — `GAME` (регион — потому что радио iOS с ADR 0012 всегда мониторило регион маяка игры: вход будит заблокированный iPhone прячущегося; поведение не меняем, а лаборатория может его выключить шагом без региона); `.bare`, `.mfr` — `LAB`. Игра берёт из каталога `RadarCatalog.game` для любой платформы: каждый телефон вещает то, что его платформа может отправить (Android — service data, iPhone — имя, ищущий — iBeacon), а слушает всё. В §2.3 канал ranging называется `ble.ibeacon.ranging`; в коде его id — `ble.ibeacon` (ranging и чтение сырого iBeacon Apple — один канал), регион — `ble.ibeacon.region`.
- **iBeacon ищущего на iPhone теперь с фиксированной измеренной мощностью −59 дБм** (`AdPart.IBeacon.measuredPower`, как у Android), раньше `peripheralDataWithMeasuredPower(nil)` брал калибровку телефона. На разбор не влияет (жетон в major/minor, дистанция считается по сырому RSSI), зато кадр одинаков на обеих платформах.
- **Протокол игры не менялся.** Поле `tech` есть только в `RadioSighting` (значение по умолчанию — пустая строка) и в журнале лаборатории (`rx`, `frame`, `adv`); `NearbySighting` в протоколе то же, что было.
- **`.mfr` — 24 байта, не 26.** Заголовок поля 2 + id компании 2 + UUID 16 + жетон 4. Число в §2.3 исправлено; тест `AdBudget` считает `2 + 2 + 16 + 4`. Id компании — `0xFFFF` (зарезервирован для тестов Bluetooth SIG), пока у игры нет своего.
- **Хосты и помощники.**
  - `AirHost` (корень): `caps`, `refresh()`, `run(channels, token, role, trace): Flow<AirFrame>`. Хост сам собирает рекламу и сам слушает; каналы только говорят, что положить и как разобрать.
  - `AdPlan` собирает рекламу из вкладов каналов (UUID сервиса, который нужен двум каналам, один раз), убирает то, чего платформа отправить не может (`dropped` с причиной), и пишет в журнал `start`/`stop`/`failed`/`dropped` по каналу с раскладкой байт (`AdBudget.layout`: `adv 18 (uuid128 18) + rsp 22 (svcdata 22)`). Общий для `AndroidAirHost`, `IosAirHost` и симулятора. `AirTally` считает всё, что слышит хост: кадр, который разобрал канал, — целиком в `frame`, остальные — счётом в `air` раз в секунду, события региона — в `scan`.
  - **Android вписывается в бюджет по частям с конца:** без локального имени (Android не может назвать одну рекламу, не переименовав телефон: `dropped`, «no local name on android»), потом часть за частью с конца, пока оба пакета не влезут в 31 байт; каждая отброшенная часть — `dropped` с раскладкой. Прежняя раскладка в этом случае уходит в эфир одним UUID без данных, и это видно в журнале, а не молчанием телефона.
  - **`scan_response` и `bare` различают свои кадры по списку UUID:** первый разбирает кадр, где UUID игры в списке, второй — где его в списке нет, а service data есть; иначе один кадр читался бы обоими и `frame` не говорил бы, какая раскладка дошла. Фильтр Android по UUID сервиса ищет только в списке, поэтому хост ставит на каждый интерес `Service` два фильтра: `setServiceUuid` и `setServiceData(uuid, пусто)`. iPhone `bare` не слышит: его скан всегда с фильтром по UUID сервиса, а без фильтра в фоне не слышит ничего никто — это и есть цена 18 байт, которую прогон измеряет (Android и Мак `bare` слышат).
  - **Правила ОС в симуляторе** (`OsRules`, чистые функции в `commonMain`; `SimulatedAir` на JVM даёт эфир, `JvmAirHost` — хост бота). Отправка: *Android* — без имени, оба пакета в 31 байт, иначе `adv failed code 1` и в эфире ничего; iBeacon — данные производителя Apple. *iPhone на экране* (и Мак) — service data и данные производителя никогда; iBeacon вещает один; один 128-битный UUID лежит в пакете, остальные уходят в область overflow, имя урезается до места, оставшегося рядом с ним (8 символов рядом с 128-битным UUID). *iPhone в фоне* — без имени, данных и iBeacon; каждый UUID сервиса становится битом маски (данные производителя Apple `01` + 16 байт); реклама, начатая на экране, в фоне не меняется (`skipped_background`). Приём: *Android и Мак* слышат всё, что подошло под фильтр, сырым (данные Apple тоже); *iPhone* — только кадры, в чьём списке UUID есть фильтр, и, на экране, биты overflow как UUID (сырую маску не видит никогда); iBeacon — только ranging'ом, на экране и в фоне; iPhone в фоне слушателем не получает UUID из области overflow. Регион iOS входит на первом же маяке и выходит через 30 с после последнего. Не моделируется: склейка повторов фонового скана iPhone, частота скана, троттлинг сканера Android. Телефон с выключенным Bluetooth не вещает и не слышит; сигнал — как раньше у ботов (логарифмическая модель, шум 2 dB, −12 dB за карман).

### Шаг 4 (2026-09-30)

Шаг 4 из §9 сделан ([radar-run.md](../radar-run.md), §4): чоканье, три сглаживания, три калибровки, свидетель, «без X», карточки техник и классификатор `carry.v2` в тени. Всё считается по журналам чистыми функциями; в игре, протоколе и `RadarSmoother`/`ProximityRules` ничего не менялось. Чем код отличается от текста выше и что решено по дороге:

- **Решения шага (контракт).**
  1. **Сглаживание и калибровка пересчитываются в отчёте из `rx`**, а не тенятся на телефоне (§2.3 и так говорит «пересчётом по журналам»): один проход по показаниям даёт все варианты. В тени телефон пишет только то, что требует сырого потока датчиков: `carry.v2` (события `shadow`) и `impact` для детектора касания. Поэтому `shadow` в журнале — только у `carry.v2`, а не «сглаживание или классификатор», как в таблице §4.
  2. **Касание ищет отчёт**, не телефон: ему нужны удары обоих. Кнопка «Чокнулись с …» пишет `mark` (`by = user`, `action = touch`, `label = "touch <пара>"`, пара — `RunStep.pairKey` двух меток): это истина. События `touch` из §4 — строки отчёта (`LabReport.touches`), в журнал их никто не пишет.
  3. **Истина полосы — расстояние пары**: из `RunStep.distances` сценария для отрезка шага либо из ручной отметки с `distance`. `LabBandTruth`: BURNING ≤ 1,5 м, HOT ≤ 4 м, WARM ≤ 15 м, дальше NONE — числа ADR 0012 («RSSI — не метры») в метрах, догадки плана. Полоса «мимо на одну» считается отдельно от «мимо»: критерий §3 («на 10 процентных пунктов») — про долю точных секунд.
  4. **Опорное значение касания — −40 дБм** (`Calibrations.TOUCH_REFERENCE_DBM`, два телефона спина к спине: догадка до прогона). Поправка направления = опорное − RSSI направления при касании (медиана по касаниям). `calib.model` берёт свои показания в 1 м по паре моделей вместо таблицы `radio_calibration` на сервере (у отчёта нет базы), об этом сказано в KDoc.
  5. **Свидетель (`infer.witness`):** в секунду, когда A и B не слышат друг друга (полоса пары NONE в обе стороны), а C слышит и A, и B не тише HOT (полоса пары — громкое из двух направлений), пара A|B выводится как WARM; сверяется с истиной пары A|B (верно, если расстояние ≤ 15 м).
  6. **Пакеты:** всё в `app.hovanki.shared.lab`, кроме сглаживаний: они кандидаты для игры и лежат в `app.hovanki.shared.rules` (`Smoothing.kt`) рядом с `RadarSmoother`.
  7. **Id техник в отчёте:** `smooth.ema`, `smooth.p80`, `smooth.rate`, `calib.none`, `calib.model`, `calib.touch`, `carry.v1` (монитор, события `carry`), `carry.v2` (тень), `infer.witness` и id каналов из `tech` показаний (у журналов до шага 3 нет `tech`, канал — `api/via`, как в `directions`).
- **Опорное значение `calib.model` — −60 дБм в 1 м** (`ONE_METER_REFERENCE_DBM`, ADR 0012 §1.1), показание считается «в метре», если пара была в пределах ±0,25 м от метра (`ONE_METER_TOLERANCE_M`).
- **Ручная отметка с `distance`** действует на каждую пару отмечающего устройства до следующей такой отметки этого устройства или второго телефона пары, а также до конца отрезка, в котором сделана (вне отрезков — до начала следующего). Отметки самого прогона (`by = run`) в расчёт не идут: их расстояние — наименьшее из шага, а `LabDistances` и так знает все расстояния шага по парам.
- **Детектор касания** (`TouchDetector`): два удара разных телефонов в пределах ±150 мс по часам сервера (время удара — `t − ago`), пик RSSI не дальше ±1 с от ударов: не тише самого громкого показания направления за предыдущие 20 с минус 3 дБ **и** не ниже медианы этих 20 с плюс 6 дБ (`PEAK_RISE_DB`; при менее чем трёх показаниях для медианы — только первое правило; моменты у уже найденных касаний пары в «предыдущие 20 с» не входят, иначе три касания подряд прячут друг друга). Не чаще одного касания пары в секунду. Отметка — не вход: касание «подтверждено», если отметка пары в пределах ±2 с; отметки без найденного касания — `missedTouches` (отметки одной пары в пределах 2 с — одно касание: нажали оба).
- **Сглаживания** (`rules/Smoothing.kt`): `smooth.ema` — сам `RadarSmoother`; `smooth.p80` — 80-й процентиль показаний за 2,5 с, дальше `ProximityRules.bandFor` с гистерезисом; `smooth.rate` — уровень EMA плюс 3 дБ · log2(показаний в секунду за последние 3 с / 2 в секунду), не больше ±6 дБ. Все три держат правила игры вокруг уровня (гистерезис, сигнал гаснет через `SIGNAL_TTL_MILLIS`), полоса меняется только на показании, и отчёт отвечает на любую секунду двоичным поиском.
- **`calib.model` и `calib.touch` оцениваются на том прогоне, на котором измерены** (лучший случай): они говорят, сколько калибровка может дать в лучшем случае; держится ли она, скажут вторая половина прогона или следующий прогон.
- **Карточки** (`TechniqueCards`), что выбрано сверх контракта:
  - слушатель «на экране» в шаге — тот, у кого ≥ 90 % событий шага с состоянием приложения — `active`/`screen_on`; расстояние пары для карточки — на середине шага;
  - для `carry` согласие с истиной: `in_pocket` — только `in_pocket`, `in_hand` — только `in_hand`, любая другая истина («не карман») — всё, кроме `in_pocket` и `none`;
  - `calib.model`, как и `calib.touch`, остаётся, если точных секунд не меньше, чем у `calib.none`, плюс 10 п. п.; `calib.none` остаётся, если ни одна не прошла (карточка есть, в контракте её не было);
  - `smooth.*`: остаётся лучшая по доле точных секунд при `calib.none` (при равенстве — раньше в списке: `ema`), остальные — «выбросить»;
  - свидетель: остаётся, если выведенных пар·с с расстоянием (`right + wrong`) ≥ 10 и верных ≥ 80 %; иначе — «мало данных» с числами;
  - `carry.v1` против `carry.v2`: карточки только когда в отчёте есть ответы хотя бы одного из них, «остаётся» лучший, когда у обоих ≥ 60 с с истиной; `carry.v1` на равенстве остаётся;
  - у журналов без `tech` в `rx` карточек каналов нет (по `api/via` критерий не проверить); в отчёте `LabReportDirection.tech` (новое поле с умолчанием) и колонка «Техника».
- **`carry.v2`** (`CarryClassifier`, `:device`, [radio-lab.md §7.3](../radio-lab.md#73-что-пишем-чтобы-решить)): экран горит и не погашен датчиком приближения → в руке; иначе «темно» = экран выключен либо погашен датчиком при `near`; `inactive` и фон iOS считаются темнотой; люксы не используются, пишутся для лаборатории. Входит в карман, когда темно и было движение за последние `MOVE_WINDOW_MILLIS` = 10 с (`std` ≥ `MOVE_STD` = 0,03 g или ходьба/бег) либо ориентация вертикальная, вверх ногами или наклон; в кармане остаётся, пока темно; «плашмя» и `std` < `TABLE_STD` = 0,03 g дольше `TABLE_MILLIS` = 60 с → неизвестно; экраном вниз при `near` — неизвестно сразу; без движения и ориентации — состояние не меняется. Все пороги — догадки плана.
- **Удар** (`ImpactDetector`, `app.hovanki.device.lab`): отклонение модуля от 1 g не меньше 0,6 g (`IMPACT_G`) начинает кандидата, сильнейший в окне 150 мс (`PEAK_MILLIS`) побеждает, не чаще одного в 300 мс (`MIN_GAP_MILLIS`). `impact` пишет `peak` и `ago` — сколько мс назад на часах датчиков (не устройства) был удар: детектор отвечает через 150 мс после него, отчёт ставит удар в `t − ago`.
- **Датчики:** акселерометр Android — `SENSOR_DELAY_GAME` (около 50 Гц), iOS — `deviceMotionUpdateInterval = 0,02` (вслепую, на iPhone не проверялось; было 0,1 с). `Gravity` и `Orientation` переехали в корень `app.hovanki.device` (их читает `CarryClassifier`), в `app.hovanki.device.lab` остались `typealias`.
- **Отчёт** (`LabReport`, версия остаётся 1, все новые поля с умолчаниями): `touches`, `touchSpreads`, `missedTouches`, `calibrations` (без `calib.none`: у него нулевые поправки), `bands` (пусто, если нигде нет расстояния), `without`, `witness` (`null` меньше чем с тремя телефонами), `cards`, `LabReportCarry.tech`, `LabReportDirection.tech`. `LabMerge.carryMatricesByTech()` даёт матрицы кармана обоих классификаторов; `LabMerge.techOf(rx)` — канал показания. Админка показывает всё это разделами: карточки сразу после проблем, потом чоканье, калибровки, полосы против расстояний, «без канала», свидетель; карман — по матрице на пару (метка, техника).

**Чего в шаге 4 нет.** Ни одна цифра не из настоящих телефонов: пороги удара, касания, `carry.v2`, полос и карточек — догадки, пока нет прогона. Сценария с чоканьем в плане прогона (шаг 7) нет: отчёту хватает отметок и `RunStep.distances`, что уже есть в шагах. Нет сглаживания в игре: `smooth.p80` и `smooth.rate` — только кандидаты, а `carry.v2` в игру не входит (`CarryMonitor` остался). `AndroidLabProbes` (50 Гц) не собирался в облаке (нет Android SDK), `IosLabProbes` (50 Гц) и iOS-часть — вслепую. Проверено: тесты на придуманных журналах (см. [radar-run.md](../radar-run.md), §4).

### Шаг 7 (2026-09-30)

Шаг 7 из §9 сделан ([radar-run.md](../radar-run.md), §7): сценарий `LabRunScripts.BIG_RUN` (`big_run`, версия 1) и чек-лист в [radio-lab-tests.md](../radio-lab-tests.md#большой-прогон-big_run-100-мин). Что решено по дороге:

- **Все шаги по таймеру.** 107 шагов, 6412 с (≈ 107 мин): прогон идёт сам от начала до конца, как `radio`. Шагов «до кнопки» нет даже в подготовке: блок 0 длится 10 минут, а пульт переходит раньше «Дальше», когда живой вид зелёный. Не удался шаг — «Повторить», нужно время — «Пауза». Id шагов начинаются с номера блока (`b0_`…`b8_`): по ним отчёт и тест узнают блок.
- **Мак — по желанию.** Метка `mac` в сценарии есть, но Мак назван только там, где он неподвижно лежит и слушает: подготовка, стол (в центре треугольника, 0,6 м до каждого; в первом шаге он вещает как прячущийся) и дорожка расстояний (у стоящего, 0,5 м). Прогон без Мака — тот же сценарий, метку просто никто не берёт; в остальных шагах Мак, если есть, тих и слушает (он слушает всегда).
- **Истина — на шаг, поэтому «сходятся и расходятся» — шаги с постоянным расстоянием.** Блок 4: 1, 5, 15, 5, 1 м на каждую технику, `droid` — свидетель на земле ровно посередине (половина расстояния пары до каждого). Блок 5: два прохода по 1, 3, 5, 10, 20, 40 м в руке и обратно в кармане: в первом стоит `A`, а `B` и `droid` уходят вместе (0,3 м друг от друга), во втором стоят `A` и `B`, уходит `droid` — так у каждой пары все шесть расстояний в руке и в кармане, а у пары `A|droid` — дважды. В первом проходе `droid` — ищущий (ranging iPhone по расстоянию), во втором — прячущийся (скан CoreBluetooth по расстоянию). Мини-игра — те же точки от 40 до 1 м и обратно. Расстояний нет там, где оно меняется внутри шага: касания и уход прячущегося.
- **Касание — один шаг на одно касание.** Отметки пары в пределах 2 с отчёт считает одним касанием (шаг 4), поэтому «три касания» блока 1 — три шага по 33 с на пару (спинами, торцами, спинами), блок 8 — шаг в 60 с на пару. Место и действие касающихся — «рука», «стоит»; действие `touch` в истину шага не ставится: так называется отметка кнопки, и отметка прогона выглядела бы касанием.
- **Заблокированный iPhone не меняет рекламу**, поэтому шаг сразу после заблокированного (блокировка — фаза `LOCK` или `LOCKED`) рекламу iPhone не меняет: телефон ещё в кармане, когда шаг начинается. Такие шаги — «достать и разблокировать» (`b2_a_unlock`, `b3_unlock`, `b4_*_unlock`, `b7_unlock`) либо шаги с той же рекламой (второй проход блока 5, начало блока 6). Это правило — тест, а не валидатор: валидатор не знает, какая метка — iPhone.
- **Вибрация (блок 3):** на каждый способ два шага: заблокированный в кармане с пульсом (`pulse = true`, `droid` с iBeacon в 1 м — «горячо») и шаг теста вибрации (тест лаборатории, отдельный от прогона: указание говорит его запустить и отметить «почувствовал 1–4»). В шаге теста пульс выключен: иначе удары пульса мешали бы считать удары серий. `mode.proximity_screen` — это `screenOff = true`, отдельного id в `techniques` нет: и так понятно, и шаг после заблокированного может его включить, не меняя рекламу.
- **Id шага 5 названы заранее:** `mode.audio`, `mode.notification_wake`, `pulse.core_haptics.audio`, `gatt.link`, `uwb.ni` и из каталога §2.3 — `mode.live_activity` (UWB в фоне без неё не работает) и `pulse.live_activity`, плюс `pulse.core_haptics` как имя нынешнего пульса лаборатории. `PhoneSetup.techniques` и так принимает любые id, телефон пишет незнакомые в журнал и пропускает, так что сценарий не придётся переписывать к шагу 5. Мини-игра включает всех кандидатов сразу; из конкурирующих пульсов телефон играет первый сработавший.
- **Каналы на стол:** три раскладки `droid` по одной, имя iPhone, потом все каналы разом — у iPhone все семь, у `droid` каналы игры и маска: три его раскладки вместе в 31 байт не влезают. Заблокированные `A` и `B` на столе слушают все семь каналов, так что заблокированный iPhone против трёх раскладок Android — отдельные шаги. Перед регионом `droid` 135 с без iBeacon: регион должен опустеть.
- **`wifi.aware` не входит:** шаг 6 отложен, в блоке 0 нет сопряжения, ни одного шага с ним.

**Не проверено:** сам прогон. Длительности (33 с на касание, 35 с на точку дорожки, 60–120 с на заблокированные шаги) — догадки; расстояния — то, что указания просят отмерить, отчёт им верит. Проверено: `LabRunScriptTest`, `:shared:jvmTest`, `:server:test`, `:e2e:unitTest`, e2e `LabRunTest`.

### Шаг 5 (2026-09-30)

Шаг 5 из §9 сделан вслепую ([radar-run.md](../radar-run.md), §5): режимы `mode.audio`, `mode.notification_wake`, `mode.live_activity`, пульс `pulse.core_haptics.audio`, связь `gatt.link` и UWB `uwb.ni`. Код написан весь, но iOS-часть ни разу не собиралась, Android-часть собирается только в CI; прогон на двух iPhone впереди, шаги владельца — в [iosApp/README.md](../../iosApp/README.md#радиолаба-live-activity-и-фоновые-режимы). Что решено:

- **Решения шага (контракт).**
  1. **Лаборатория включает любую технику по id через `LabController.setTechniques`:** каналы — радио стенда (как раньше), `mode.*` — `BackgroundModes` (`:device`), `gatt.link` — `GattLink` (`:radar`, `link/`), `uwb.ni` — `PrecisionRadio.range` с устройствами прогона, `pulse.*` — чем бьёт пульс лаборатории. Незнакомый id пишется в `note` и пропускается, как раньше; то, чего нет у телефона (режим, UWB, связь), пишется один раз (`mode … unavailable`, `range unsupported`, `link failed`) и пропускается. `DeviceCatalog` не понадобился: id режимов — `ModeIds`, пульсов — `LabController.PULSE_KINDS`, всё вместе — `LabController.LAB_TECHNIQUES`.
  2. **Токены UWB ходят через прогон на сервере:** телефон шлёт свой (`POST /api/v1/lab/runs/{runId}/uwb`, `LabUwbTokenRequest`, до 512 символов base64), состояние прогона перечисляет токены по меткам (`LabRunStateView.uwbTokens`, новое поле с умолчанием). Токен — архив `NIDiscoveryToken` (`NSKeyedArchiver`, secure coding), base64; не персональный, живёт с прогоном (`lab_devices.uwb_token`, V12, удаляется с прогоном), в журнал не пишется. У метки один токен — того устройства, что прислал последним (телефон, вошедший в прогон заново, — новая строка устройства).
  3. **GATT-связь:** каждый телефон с `gatt.link` держит сервис `RadarService.LINK_UUID` с характеристикой `LINK_TOKEN_UUID` (чтение, запись, notify; 4 байта жетона), рекламирует его, сканирует и подключается к каждому найденному (не больше `MAX_LINKS` = 5), читает жетон, подписывается, пишет свой раз в `WRITE_MILLIS` = 5 с, читает RSSI раз в `RSSI_MILLIS` = 3 с, переподключается после разрыва (`RECONNECT_MILLIS` = 2 с на Android; iOS держит запрос `connect` без тайм-аута). Без сопряжения и шифрования. Жетон связи — тот, что вещает радио стенда.
  4. **Live Activity (заход 2):** сторона Kotlin готова и собирается без таргета владельца; Swift — файлы, которые владелец добавляет в Xcode (расширение `HovankiLive` и класс-хост в приложении). Приложение находит хост по имени во время запуска (`NSClassFromString` в `ContentView.swift`), поэтому собирается и работает без него, а `mode.live_activity` тогда `unavailable`.
  5. **Фоновые режимы `audio` и `nearby-interaction` и `NSSupportsLiveActivities`** добавляет в Info.plist только Debug-сборки `debug-info-plist.sh` (как локальную сеть); `NSNearbyInteractionUsageDescription` — в `Info.plist` и `InfoPlist.xcstrings` (текст сам по себе в release ничего не включает).
  6. **Android:** `gatt.link` написан (`android.bluetooth`: сервер и клиент); режимы и UWB недоступны (`NoopBackgroundModes`, `NoopPrecisionRadio`): `uwb.jetpack` ждёт железа (§2.3).
- **Один партнёр на iPhone в `uwb.ni`.** У `NISession` один токен, а ранжирует она с одним партнёром; парные токены (по сессии на каждую пару) потребовали бы менять протокол: каждое устройство публиковало бы токен для каждого другого. Поэтому iPhone держит одну «домашнюю» сессию, её токен уходит в прогон, а ранжирует он с первым по метке из остальных; прочие пишутся в `range` как `config` с ошибкой. Двум iPhone шага 5 этого хватает; с тремя A и B ранжируют друг с другом, а C (выбравший A) — нет. Сессию после восстановимой ошибки (`sessionFailed`, `resourceUsageTimeout`) радио создаёт заново один раз через 2 с — с новым токеном, который телефон снова отдаёт в прогон; конец приостановки и тайм-аут партнёра запускают ту же конфигурацию снова, как советует Apple.
- **`mode.notification_wake` — очередь на 10 минут вперёд, а не цикл в приложении.** Цикл в приостановленном приложении спит вместе с ним, поэтому уведомления (раз в 20 с, без звука) ставятся заранее триггерами по времени на 10 минут вперёд — 30 в очереди, в пределах лимита iOS в 64; цикл только доливает очередь и пишет `notification_sent`, когда уведомлению пора.
- **`identifier_changed` — по жетону:** когда новый id читает жетон, который был у молчащего старого, это тот же телефон с новым адресом (обе ОС меняют его примерно раз в 15 минут без соединения); старый id забывается.
- **В `gatt.link` подключаются обе стороны пары,** не «назначенный партнёр» из плана §5.2: так не нужен выбор ведущего, а отчёт читает оба направления. RSSI есть только у подключившейся стороны (`CBPeripheralManager` и `BluetoothGattServer` его не читают).
- **Таргет виджета не входит в закоммиченный проект:** `preview.yml` подписывает всё одним профилем, и расширение без своего профиля уронило бы сборку TestFlight. Swift-файлы в репозитории, таргет живёт в локальном проекте владельца.
- **`mode.audio` — только лаборатория.** Беззвучное фоновое аудио App Review (правило 2.5.4) не любит; для игры это отдельное решение по итогам прогона.
- **Игра не ранжирует:** `GameSessionManager` получает прежний `PrecisionRadio` (`NoopPrecisionRadio`), у лаборатории — свой (Koin, квалификатор `lab.precision`: `IosPrecisionRadio` с `LabRangeTrace` на iOS, `NoopPrecisionRadio` на Android). Сервер пар UWB в игре по-прежнему не назначает.
- **Пульс — цепочка «первое, что сработало».** Шаг может назвать несколько `pulse.*` сразу (мини-игра блока 7): бьёт первый из списка §2.3 (`core_haptics`, `core_haptics.audio`, `live_activity`, `impact`, `notify_silent_sound`, `notify`), который есть у телефона, после первой ошибки — следующий, до конца шага. `pulse.live_activity` — Core Haptics при включённой `mode.live_activity`. Без `pulse.*` — как раньше (первый вид, который не уведомление).
- **Журнал** ([radio-lab.md §4.1](../radio-lab.md#41-что-пишется), схема остаётся 2): `link` {`action`, `peer` (хеш), `token`, `rssi`, `error`}, `range` {`action`, `peer` (метка), `m`, `deg`, `error`}, `mode` {`mode`, `event`, `reason`}; `net` с `action = uwb`; вид `audio` из §4 не заведён: прерывания и маршрут — события `mode` режима `mode.audio`. В тесте вибрации на iPhone пять групп (добавилась `core_haptics_audio` второй). В карточке прогона лаборатории — строка «link: N peers · range: X m to B».

**Не проверено:** всё на телефонах. Собирается ли iOS-часть (`IosBackgroundModes`, Core Haptics на аудиосессии, `IosGattLink`, `IosPrecisionRadio`, Swift-файлы), уживаются ли два `CBPeripheralManager` в одном приложении, держит ли `mode.audio` Core Haptics на блокировке, будит ли запись GATT заблокированный iPhone, ранжирует ли UWB с Live Activity, когда оба заблокированы, — вопросы прогона (блоки 3 и 4 `big_run`). Все числа (20 с, 5 с, 3 с, 2 с, 5 связей) — догадки. Проверено на JVM: `LabTechniquesTest`, `LabRunFollowerTest`, тесты `link/`, `UwbTechniqueTest`, `BackgroundModesTest`, серверный `LabApiTest`, e2e `LabRunTest`.

### Шаг 6 отложен (2026-09-30)

Решение владельца по исследованию рынка: `wifi.aware` не строим, пока не изменится одно из двух ниже. Цифры (источники: Apple «App Store support», Telemetry Deck, форумы Apple Developer, Statcounter; оценки помечены):

- **iOS не помеха.** iOS 26 стоит на 79 % активных iPhone (Apple, 7 июня 2026; 86 % у моделей последних 4 лет), у Telemetry Deck на конец августа 86,6 % плюс 3,3 % на iOS 27; кривая повторяет iOS 18 с отставанием в 2–3 пункта. Wi-Fi Aware нужен iPhone 12 и новее — по оценке около 85 % активных iPhone. Итого техника доступна на 75–80 % iPhone сейчас и около 90 % через год.
- **Помеха — Android и смешанные пары.** Связь iPhone ↔ Android требует Wi-Fi Aware 4.0 с NAN Pairing (`isAwarePairingSupported()`, API 34+): в 2025 году это умел только Galaxy S25, а подтверждённо работающих пар iPhone–Android нет (ветки форума Apple 790195 и 801289 закрыты без решения; на сентябрь 2026 — «не подтверждено»). Доля Android с Wi-Fi Aware нигде не публикуется.
- **Доля пар.** Техника дала бы только пары iPhone–iPhone. При доле iOS 36 % в Украине, 31 % в Польше и 28 % в Германии (Statcounter, август 2026) это 8–13 % всех пар игроков, а с iOS 26 и iPhone 12+ у обоих — **5–8 % пар сейчас, 6–10 % через год**.
- **Трение:** платный Apple Developer Program и заявка на entitlement `com.apple.developer.wifi-aware` (на бесплатном аккаунте capability недоступна), ручное сопряжение на каждую пару, работает только при запущенном приложении, симулятора нет.

Вернуться к технике — не раньше конца 2027 и только если появится подтверждённая связь iPhone–Android или опубликованная доля Android с Aware 4.0. Дешёвая проверка, если захочется: один прогон в радиолабе на двух iPhone 12+ и Galaxy S25 с критерием остановки «пара iPhone–Android не устанавливает data path». Строка каталога остаётся, статус «отложена»; в код техника не входит.

## Последствия

- В debug-сборке много нового кода. Release не меняется: техники не из `GAME` выключены, экрана лаборатории нет.
- На боевом сервере — маршруты лаборатории за флагом и порядка 100 МБ данных на большой прогон, хранятся 90 дней.
- Выбрасываем по записанным заранее критериям, а не по ощущениям; «кладбище» хранит, за что.
- Некоторые техники при переходе в игру потянут вопросы App Store: фоновая аудиосессия (2.5.4), фоновый режим Nearby Interaction, Wi-Fi Aware (entitlement).

## Открытые вопросы

- Какие телефоны: модель и iOS второго iPhone (для UWB нужен 11+ не SE, для Wi-Fi Aware — 12+ на iOS 26), модель и версия Android (UWB, Wi-Fi RTT, Android 16).
- Multipeer — точно на кладбище (поведение описано в документации)?
- Мини-игра в прогоне — без настоящей `Game`. Нужна ли позже настоящая игра с журналами на сервере?
