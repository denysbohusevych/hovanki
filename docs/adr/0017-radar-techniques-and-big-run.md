# ADR 0017. Техники радара, большой прогон трёх телефонов и отчёт в админке

- **Статус:** Accepted (шаг 1 реализован 2026-09-29: прогон на сервере; шаг 2 — 2026-09-30: модули `:radar` и `:device`; шаги 3–7 — план, в коде их нет)
- **Дата:** 2026-09-29
- **Автор:** Denys Bohusevych (черновик — Claude Code)
- **Пересматривает:** [ADR 0016](0016-iphone-overflow-radar.md) — «Чего не делаем» и «Исследование», п. 4 и 6 (GATT, будить экран уведомлениями, фоновое аудио, Wi-Fi Aware, Multipeer); [ADR 0012](0012-nearby-radar.md) — «калибровку касанием» из «Отличий реализации». **Дополняет:** [radio-lab.md](../radio-lab.md) (журнал и прогон переезжают на сервер), [ADR 0008](0008-admin.md) (вкладка «Радиолаба» в админке).

> **План.** Как устроить радар, чтобы каждую идею можно было включить, измерить и выбросить, не трогая остальные. Как три телефона (два iPhone и Android) проходят один большой прогон по часам сервера и сразу отдают журналы на сервер. Как сервер сводит данные и показывает отчёт в админке. При принятии статус меняется на Accepted, по мере этапов добавляются «Отличия реализации».

## Контекст

Радар собран из нескольких способов, и почти каждый держится на догадке о поведении iOS или Android. Лаборатория ([radio-lab.md](../radio-lab.md)) проверяет догадки по одной: один телефон, Мак, экспорт журнала руками после каждого опыта. Выход 1 подтвердил маску overflow и «замёрзший» жетон; остальное впереди.

Решения владельца (2026-09-29):

1. **Пересмотреть отвергнутое.** Проверить всё, кроме ультразвука; отдельно — пару «два iPhone в карманах», в том числе по UWB.
2. **Один большой прогон:** два iPhone и Android одновременно, шаги по часам сервера, журналы сразу уходят на сервер.
3. **Сервер копит и сводит** данные всех прогонов, отчёт — в админке.
4. **Ритуал «чокнуться телефонами»** (калибровка касанием) — проверить, даёт ли он что-то.
5. **Карман — не радио:** где телефон, определяют другие датчики.

Что нашлось, пока писался план:

- **Реклама Android-прячущегося, похоже, не уходит в эфир.** UUID сервиса (18 байт) и service data со 128-битным UUID (22 байта) — это 40 байт, а обычная реклама вмещает 31. `startAdvertising` в таком случае отвечает `ADVERTISE_FAILED_DATA_TOO_LARGE` (код 1). На телефоне ещё не проверено: первый запуск на Android покажет в журнале `adv failed code 1`. У ботов радио ненастоящее, поэтому e2e этого не видит.
- **Core Haptics замолчал при блокировке с причиной 1** (выход 1). По заголовку CoreHaptics это `audioSessionInterrupt` — прервана аудиосессия, — а не `applicationSuspended` (2), на которое рассчитывало исследование ADR 0016. Приложение при этом не спало: дыр в тиках нет. Значит, двигатель стоит попробовать держать своей аудиосессией или перезапускать после прерывания. Журнал будет писать имя причины, а не число.

## Решение коротко

1. **Два новых модуля с платформенным кодом:** `:radar` — всё, что между телефонами (Bluetooth, GATT, UWB, Wi-Fi Aware); `:device` — телефон сам по себе (карман, движение, датчики, вибрация, режимы экрана и фона). Чистые правила, которые считает и сервер, и разбор журналов — в `:shared`; лаборатория — в `:clientCore/lab`.
2. **Каждая идея — «техника»:** id, вид, требования, статус и **заранее записанный критерий**, при котором её оставляем. Техники либо **дополняют** друг друга (каналы: в итоге останется несколько), либо **конкурируют** (сглаживание, карман, вибрация: останется одна).
3. **Пишется всё:** каждое действие и каждое показание каждой техники, сырые кадры эфира, жизнь приложения, датчики, батарея. Журнал v2.
4. **Прогон живёт на сервере:** админ создаёт его в админке, телефоны входят по коду, шаги меняются по часам сервера у всех сразу, пульт — в админке, журналы уходят на сервер каждые 5 секунд.
5. **Сервер хранит сырые журналы 90 дней** и считает отчёт: покрытие по парам и каналам, карточки техник против критериев, «что было бы без техники X», калибровки, расстояния. Сквозная сводка по всем прогонам — по моделям телефонов.
6. **Всё за флагом сервера `RADIO_LAB`** (выключен по умолчанию): только тестовые телефоны прогона, никаких координат, отчёт только админам.

Новые модули — по правилам AGP 9 из `CLAUDE.md` (`com.android.kotlin.multiplatform.library`, блок `kotlin { android { … } }`).

**Почему карман не в `:radar`.** Где телефон, решают акселерометр, гравитация, датчик приближения и свет, а не эфир. Радару нужен только ответ (`Carry`): для поправки за тело и чтобы выбрать, какой вибрацией бить. Поэтому `:radar` не зависит от `:device`; их связывает тот, кто ими пользуется: игра или лаборатория. Лаборатория проверяет оба модуля вместе.

Один модуль на область, а не Gradle-модуль на каждую технику: десяток KMP-модулей с iOS-таргетами — это медленная сборка и лишняя возня с фреймворком. Границы держат пакеты (`radar/channel/overflow/`, `radar/link/gatt/` …) и тест, который проверяет, что техники не импортируют друг друга.

## 2. Техники

### 2.1 Что такое техника

```kotlin
interface Technique {
    val id: String               // "ble.overflow", "gatt.link", "uwb.ni", "pulse.core_haptics", "calib.touch"
    val kind: TechniqueKind      // CHANNEL, LINK, RANGING, MODE, PULSE, CARRY, SMOOTHING, CALIBRATION, INFERENCE
    val status: TechniqueStatus  // LAB, CANDIDATE, GAME
    fun available(device: DeviceCaps): Availability  // чип, ОС, разрешение, entitlement, фоновый режим
}
```

- **Статусы:** `LAB` — только в лаборатории; `CANDIDATE` — в прогонах всегда, в играх — только если сервер разрешил; `GAME` — в игре у всех. Выброшенная техника удаляется из кода и остаётся строкой на «кладбище» этого ADR — с цифрами, за что.
- **Каталог** (`RadarCatalog`, `DeviceCatalog`) — список техник платформы. Игра и лаборатория берут из него, что включить; по имени техники не знает никто.
- **Критерий записан до замеров** (§2.3). Отчёт сверяет с ним каждую технику: «оставить», «выбросить» или «мало данных».
- **Разрешение для игр** — одна настройка сервера «кандидаты, разрешённые в играх» в админке (список id), вместо отдельного `ServerFeature` на каждую идею. Хост в лобби техник не выбирает: это транспорт, а не правило игры (как в ADR 0016).

### 2.2 Каналы и хосты

**Канал** — формат жетона в эфире: что положить в рекламу, какие кадры слушать, как разобрать кадр в жетон. Это общий Kotlin, проверяемый тестами на JVM.

**Хост** — один на платформу: Android, iOS, JVM-симулятор для ботов, Мак. Он владеет рекламой и сканером, собирает **одну** рекламу из вкладов всех включённых каналов и знает правила ОС:

- iOS: одна реклама на приложение; в фоне её не начать и не изменить; имя и данные в фоне не уходят, UUID уходят в маску overflow;
- Android: обычная реклама — до 31 байта, больше — через наборы рекламы (advertising sets), если телефон их умеет.

Не влезает или конфликтует — хост пишет в журнал раскладку байт и что отброшено. Принятые кадры он раздаёт декодерам каналов.

Вслепую на iOS пишется только хост, один раз; каналы проверяются в облаке. JVM-хост — это симулятор эфира с правилами ОС: новый канал сразу честно ведёт себя у ботов, без ручной правки `bot/Radio.kt`.

**Вывод на сервере** (новое): `infer.witness` — «свидетель». A и B друг друга не слышат, но оба громко слышны C: значит, оба рядом с C, а значит, и друг с другом. Может закрыть пару «два iPhone в карманах», когда рядом есть третий телефон. Чистая функция; проверяется на данных прогона — у трёх телефонов как раз треугольник.

## 3. «Чокнуться телефонами»: калибровка касанием

ADR 0012 оставил её вариантом для моделей, которых нет в `radio_calibration`, и её не сделали. Теперь это техника `calib.touch`.

- **Как:** двое касаются телефонами. В этот момент расстояние — ноль, и RSSI каждого направления — «ноль» этой пары. Разница с тем, что пара должна слышать вплотную по своим моделям, — поправка пары на игру.
- **Как поймать момент без кнопки:** удар в акселерометре у обоих телефонов в пределах ±150 мс по часам сервера плюс пик RSSI пары в ту же секунду. Кнопка «чокнулись» — запасной вариант и истина для проверки детектора.
- **В прогоне:** в начале каждая пара чокается трижды (повторяемость), спинами и торцами (ориентация); в конце — ещё раз (дрейф). Потом — дорожка расстояний (§6).
- **Отчёт:** ошибка полосы против истины для `calib.none`, `calib.model` и `calib.touch`; разброс трёх касаний; дрейф. Оставляем, если с касанием ошибка полосы меньше хотя бы на 10 процентных пунктов, а три касания расходятся не больше чем на 6 dB. Иначе — на кладбище, с цифрами.
- **В игре** это был бы ритуал в лобби («чокнитесь с соседом»). Как он будет выглядеть, решаем после цифр.

## 4. Журнал v2: пишем всё

Схема [radio-lab.md §4.1](../radio-lab.md#41-что-пишется) остаётся. В каждое событие добавляются `run` (id прогона), `seq` (номер события на устройстве, чтобы выгрузка не давала дублей) и `tech` (id техники). Новые виды:

| `k` | Что |
|---|---|
| `frame` | сырой кадр нашего формата: у Android — байты записи скана в hex; у iOS — словарь рекламы: имя, UUID сервисов, UUID маски, service data и данные производителя в hex, мощность, connectable |
| `air` | чужие кадры раз в секунду: сколько каких (iBeacon, маски, прочее Apple) и биты чужих масок — для раскладки V1 |
| `adv` | вдобавок полная раскладка рекламы, её бюджет в байтах и что не влезло |
| `link` | GATT: подключение, отключение с ошибкой, запись, notify, `readRSSI` |
| `range` | UWB: расстояние, направление, состояние (идёт / приостановлено / снято) и причина |
| `aware` | Wi-Fi Aware: сопряжение, соединение, отчёт о связи |
| `audio` | прерывания и смены маршрута аудиосессии |
| `haptic` | вдобавок причина остановки двигателя именем |
| `shadow` | ответ техники в тени: сглаживание или классификатор → полоса или состояние |
| `touch` | найденное касание: пара, время, RSSI, сила удара |
| `step` | смена шага прогона (от сервера) |
| `net` | сеть и выгрузка: отправлено, ответ, очередь |
| `thermal` | температурное состояние телефона |

Своих кадров пишется всё. Чужих — только счётчики и биты, одним событием в секунду: в городе их сотни в секунду. Координат по-прежнему нет: у `gps` только точность и возраст. Разбор (`:shared/lab`) читает и v1, и v2.

Объём: 50–150 событий в секунду на телефон, около 5 КБ/с после gzip. Час прогона на трёх телефонах — порядка 100 МБ сырых данных на сервере.

## 5. Прогон на сервере

### 5.1 Вход

1. Админ в «Радиолабе» создаёт прогон: название, сценарий (из каталога в `:shared`), метки устройств (`A`, `B`, `droid`, по желанию `mac`), причину. Получает код из 6 символов и QR.
2. Телефон (debug-сборка): Lab → «Войти в прогон» → код или QR. Он отправляет метку, модель, ОС, сборку и commit, возможности (Bluetooth: наборы рекламы и их число, LE Coded; UWB; Wi-Fi Aware; разрешения).
3. Сервер отвечает токеном устройства (живёт с прогоном), **секретом радара на прогон** (жетоны меняются, как в игре, и сервер знает, чей жетон) и планом.
4. Часы — как сейчас (`GET /api/v1/time`, 5 запросов, берётся с меньшим RTT), раз в минуту. Сервер вдобавок ставит время приёма на каждую пачку.

Мак входит тем же кодом: `run.sh --lab --run <код>`.

### 5.2 План и пульт

- **Сценарий** — шаги. У шага длительность или «до кнопки»; для каждого устройства — какие техники включены, текст для человека («A — в карман спереди, B — на стол экраном вверх») и **истина для отчёта**: расстояние в каждой паре, где каждый телефон, что делает человек. Отметки ставятся сами.
- Все идут по плану сервера: `GET /api/v1/lab/runs/{id}/state` раз в 2 с (шаг, когда начался, какой следующий). Техники переключаются в одну и ту же миллисекунду по часам сервера; расхождение — только ошибка часов.
- **Пульт** — страница прогона в админке (на ноутбуке или телефоне): шаг, указания каждому, обратный отсчёт, «Дальше», «Повторить шаг», «Пауза». Те же кнопки — на любом телефоне прогона. Телефоны с экраном звучат и вибрируют на переходе, заблокированным приходит уведомление.
- Проверка сценария из `LabRunScript` («заблокированный шаг не меняет рекламу») переезжает в `:shared` и проверяется для каждого устройства.

### 5.3 Выгрузка

- Каждые 5 с — пачка (JSONL, gzip) `POST /api/v1/lab/runs/{id}/events` с `seq` от и до. Сервер подтверждает; повтор безвреден.
- Нет сети — пачки ждут в памяти (тот же кольцевой буфер) и уходят позже. «Экспорт» в «Поделиться» остаётся запасным путём.
- iOS в фоне: приложение живо (GPS или режим), выгрузка идёт. Если iOS всё-таки приостановила его, это видно по тикам, а пачки уйдут, когда приложение проснётся.

### 5.4 Живой вид

Пока идёт прогон, админка показывает по каждому устройству: пачка сколько секунд назад, сдвиг часов, состояние приложения, Bluetooth, батарею, шаг; по каждой паре и каналу — слышно ли за последние 10 с и медиану RSSI. Если что-то не пишется, это видно сразу, на улице, а не вечером.

## 7. Сервер: хранение и отчёт

**Таблицы** (новая миграция; всё удаляется вместе с прогоном, `ON DELETE CASCADE`):

| Таблица | Что |
|---|---|
| `lab_runs` | прогон: название, сценарий и его версия, кто создал (сотрудник), время создания, начала и конца, состояние |
| `lab_devices` | устройство прогона: метка, модель, ОС, сборка, commit, возможности, хеш токена, время входа и последней пачки |
| `lab_chunks` | сырые пачки: устройство, `seq` от и до, время от и до, число событий, время приёма, тело (gzip) |
| `lab_reports` | отчёт прогона (JSON) и версия разбора |

**Пределы:** до 8 устройств на прогон; вход и выгрузка — до 24 часов после создания; до 300 МБ сырых данных на прогон; `RateLimiter` на устройство. Флаг `RADIO_LAB` выключен — маршрутов нет (404).

**Сроки:** сырые пачки хранятся 90 дней после конца прогона (`DataRetention`); отчёты и сквозные сводки — без срока: в них метки, модели и числа, персональных данных нет.

**Отчёт** считает чистая функция из `:shared/lab` вне потока запроса (как `HistoryWriter`): понемногу во время прогона — для живого вида, целиком — после «Завершить». Разделы:

1. **Покрытие:** по шагам, для каждой пары «кто вещает и в каком состоянии → кто слушает и в каком» и для каждого канала — показаний в секунду, RSSI (медиана, p80, min, max), самая длинная пауза и что в это время было с приложением.
2. **Карточки техник:** критерий из §2.3 → «оставить», «выбросить» или «мало данных», с цифрами.
3. **Без X:** полосы по всем каналам против полос без канала X — в скольких процентах секунд они совпадают и где X был единственным.
4. **Калибровка и чоканье** (§3).
5. **Расстояния:** RSSI и метры UWB против отметок — по парам, каналам и месту телефона.
6. **Карман:** классификаторы против разметки.
7. **Вибрация:** попытки, результаты, причины остановки, отметки «почувствовал».
8. **Батарея и нагрев** по устройствам и блокам.
9. **Маска:** кадры, качество разбора, чужие биты.

**Сквозная сводка** по всем прогонам: пара моделей × канал × место телефона × расстояние → распределение RSSI. Отсюда — предложения для порогов полос и `POCKET_OFFSET_DB`. Сами правила по-прежнему меняются отдельным PR с тестом.

**Админка** — вкладка «Радиолаба», только для роли admin: список прогонов, создание, пульт и живой вид, отчёт, скачивание сырых журналов (с причиной и записью в журнал аудита; для `:e2e:lab merge`), удаление (с причиной). Таблицы и простые полосы SVG строятся через DOM: `textContent`, без `innerHTML` и без чужих хостов, как вся админка.

## 8. Приватность и безопасность

- Прогон создаёт админ, телефоны входят по коду. Экран лаборатории есть только в debug-сборках; release и preview в прогоны не входят.
- **Координат нет нигде**: у `gps` только точность и возраст, как сейчас. Нет аккаунтов, чата и игроков. Жетоны — жетоны прогона (от его секретов), не игровые.
- RSSI, жетоны, сырые кадры и данные датчиков лежат на сервере в таблицах лаборатории и видны только админам в отчёте, игрокам — никогда. Это новое исключение из правила «RSSI никому» в `CLAUDE.md`. Когда появится код, туда добавится: «журналы лаборатории — только тестовые телефоны прогона, без координат, 90 дней, только админам».
- Адреса Android и идентификаторы iOS хешируются с солью прогона.
- Каждый маршрут админки — с `Staff`, ролью admin, причиной и `AuditLog` в той же транзакции ([ADR 0008](0008-admin.md)).
- Из настоящих игр журнал на сервер не уходит. Если это понадобится — отдельное решение: только игры, где все игроки — телефоны прогона. **Пересмотрено:** [ADR 0018](0018-field-test-build.md) — полевая сборка на staging пишет журнал в настоящих играх после согласия тестера, экран лаборатории в `preview` — только сотрудникам.

## Отличия реализации

### Шаг 1 (2026-09-29)

Шаг 1 из §9 сделан ([radar-run.md](../radar-run.md), §1): протокол `:shared/protocol/Lab.kt` и `:shared/lab`, сервер (`server/.../lab/`, `LabController`, `LabAdminController`, миграция V11), телефон (`clientCore/.../lab/`, карточка «Server run» в Lab), вкладка «Радиолаба» в админке, `e2e` (`LabBot`, `LabRunTest`, `run.sh --lab --run`). Чем код отличается от текста выше:

- Миграция — `V11__radio_lab.sql` (не V10: V10 занята). Имя админа в `lab_runs` только `created_by_name`, без id пользователя; через год (как в журнале аудита) `DataRetention` его стирает.
- **Жетон радара выдаёт сервер** при входе (`radarToken`, 8 hex, уникален в прогоне): телефон вещает его как жетон прячущегося и пробы. Вращения жетонов, как в игре, пока нет; проба по-прежнему может менять свой жетон, `adv` пишет, что вещалось, так что сведение сопоставляет и их.
- **Повторный вход = новое устройство:** телефон, вошедший снова с той же меткой (перезапуск), получает новую строку `lab_devices` и новый жетон; старая строка хранит свои пачки. Метки в прогоне не уникальны, устройств до 8 (с повторными входами).
- **Маршруты админа работают и с выключенным флагом** (иначе нельзя ни включить фишку из админки, ни прочесть старый отчёт); маршруты телефона при выключенном — 404, и вход, и токен.
- **Выгрузка:** тело — строки журнала как есть (`application/x-ndjson`, можно `Content-Encoding: gzip`), границы пачки — в запросе (`seqFrom`, `seqTo`, `count`, `tFrom`, `tTo`), не в JSON. Сервер хранит пачку сжатой сам. Ответ `ackedSeq` — только то, что хранится; повторная пачка с тем же `seqFrom` записи не добавляет, а телефон досылает хвост новой пачкой. Пределы: 4 МБ на пачку (до и после распаковки), 5000 событий, 300 МБ (сжатых) на прогон, `RateLimiter` на устройство и на IP входа.
- **Льготное время выгрузки** (в плане его не было): законченный прогон ещё 30 минут (`hovanki.lab.upload-grace`) берёт последние пачки, и каждая пересчитывает отчёт. Без него телефоны, дописывающие журнал после конца плана, получали бы `LAB_RUN_CLOSED`, и «всё выгружено» не достигалось бы. Закрытый (законченный или старше окна входа) прогон отвечает `WRONG_STATE` + `LAB_RUN_CLOSED`.
- **План считают одинаково и сервер, и телефон** (`LabRunPlan`, `:shared`): `NEXT` на «создан» запускает шаг 0, потом переходит к следующему, на последнем — завершает; `REPEAT` начинает шаг заново; `PAUSE`/`RESUME` сдвигают начало на длину паузы; любое действие — `revision + 1`. Шаг с временем кончается сам по часам сервера, но сервер сохраняет это, когда на прогон кто-то смотрит (опрос телефона, страница админа, пачка). Конец прогона — только по ответу сервера: телефон, досчитавший до конца сам, держит последний шаг и сразу переспрашивает.
- Пульт админа: действие, что-то меняющее, пишется в `AuditLog` (`LAB_RUN_CONTROL`), пустое — нет; действия телефонов не пишутся. Создание, скачивание сырых журналов (`POST .../raw`, ответ — zip, по файлу на устройство, пишется потоком) и удаление (`POST .../delete`, 204, вместе с устройствами, пачками и отчётом) — `LAB_RUN_CREATE`, `LAB_RUN_DOWNLOAD`, `LAB_RUN_DELETE`. Удаление — `POST`, как остальные маршруты админки с причиной.
- **Отчёт** считает `LabReportWriter` вне потока запроса, когда прогон стал «закончен» любым способом, и заново на каждую пачку в льготное время и на «Завершить»; хранится как JSON (`lab_reports`, версия 1). Событий читается не больше 500 000 на прогон (`hovanki.lab.max-report-events`): у большего в отчёте устройства и одна строка о том, что сводить надо на компьютере. Жетон, который не принадлежит ни одному устройству прогона, в отчёте и в живом виде — просто `?`: он может быть чужой игры рядом, а отчёт живёт дольше журналов. События с временем вне окна прогона отбрасываются и считаются в проблемах.
- **Живой вид** — в памяти (`LabLive`): показания за 30 с, пары «кто → кого, канал», слышно за 10 с и медиана RSSI; прогон, от которого 10 минут ничего не приходило, забывается.
- **Телефон:** `LabRunFollower` опрашивает состояние раз в 2 с, вход и выход идут на процессном скоупе, так что закрытие панели не обрывает последнюю выгрузку. По окончании прогона телефон выключает радио, останавливает лабораторию и досылает журнал. `step` пишется на смене шага и на `REPEAT`, не на паузу. Заблокированный шаг не меняет рекламу; телефон, вошедший посреди такого шага, рекламу включает и просит заблокировать. Карточка сканера QR — внутри панели (320 dp), не на весь экран. Начавшаяся игра прогон покидает. В `composeApp` собирался только `commonMain`: Android и iOS — на машине с SDK и на Маке; iOS-`gzip` (`platform.zlib`) не собирался, без него выгрузка идёт без сжатия.
- **Мак** (`run.sh --lab --run <код>`, `MacServerRun`): входит как `mac` (`Platform.OTHER`), ведёт рекламу по метке шага (прячущийся — `advertise <жетон>`, ищущий — `ibeacon <жетон>`), выгружает журнал и выходит с концом прогона.
- **Каталог планов:** `radio` (версия 2, метки `A`, `mac`: нынешний автоматический прогон) и `e2e` (версия 3, метки `A`, `B`, `droid`, 22 с — для тестов). `MacSetup` убрана: шаг Мака — `PhoneSetup` (прячущийся — реклама, ищущий — iBeacon).
- Разбор ушёл в `:shared/lab` (`LabMerge`, `LabEvents`, `LabLogDevice`, схемы 1 и 2), отчёт — `LabReportBuilder`. `LabCli merge` остался тонкой обёрткой.

**Чего в шаге 1 нет.** Техники — только те, что лаборатория умеет сейчас (Bluetooth на столе, экран, карман, вибрация); ни модулей `:radar`/`:device`, ни каналов и хостов, ни `tech` в событиях, ни видов `frame`, `air`, `link`, `range`, `aware`, `audio`, `shadow`, `touch`, `thermal`, ни чоканья. Отчёт версии 1 — из §7 только «покрытие» (направления по шагам: показаний в секунду, RSSI, самая длинная пауза и что было с приложением), «карман» (истина против сказанного), «вибрация», «батарея» и «маска» в самом простом виде, плюс устройства, сдвиги часов, проблемы и тики; карточек техник, «без X», калибровки, расстояний и сквозной сводки нет. Жетоны прогона не вращаются, как в игре (§5.1, п. 3): один постоянный жетон на устройство. Прогоны с живой игрой не связаны.

### Шаг 2 (2026-09-30)

Шаг 2 из §9 сделан ([radar-run.md](../radar-run.md), §2): два новых KMP-модуля (jvm, android, iosArm64, iosSimulatorArm64; `com.android.kotlin.multiplatform.library`), файлы перенесены `git mv`, поведение игры, лаборатории и ботов не менялось. Чем код отличается от текста выше:

- **Пакеты.** `:radar` — `app.hovanki.radar`: `ProximityRadio` (`RadioSighting`, `RadioApi`, `SightingVia`, `RadioTrace`, `NoopProximityRadio`), `PrecisionRadio`, `AndroidProximityRadio`, `IosProximityRadio`; `app.hovanki.radar.lab`: `LabAir`, `AirFrame`, `ProbeEvent`, `NoopLabAir`, `AndroidLabAir`, `IosLabAir`. `:device` — `app.hovanki.device`: `CarryMonitor`, `ActivityMonitor` с `ActivityClassifier`, `PocketPulse`, `DeviceInfo` и их реализации на Android и iOS; `app.hovanki.device.lab`: `LabProbes`, `LabSensorReading`, `LabBattery`, `LabScreen`, `LabHaptics`, `HapticKind`, `HapticResult` (с no-op двойниками), признаки кармана `CarryFeatures` (`Gravity`, `Orientation`, `MotionWindow`, `MotionFeatures`), `HapticStopReason`, реализации `AndroidLabProbes`/`AndroidLabScreen`/`AndroidLabHaptics` и `IosLabProbes`/`IosLabScreen`/`IosLabHaptics`. Фасада `Radar` и каналов ещё нет: игра по-прежнему видит `ProximityRadio`.
- **Что осталось в `:clientCore`:** `tracking/BackgroundTracker` и `HiderAlerts` (это слежение игры, а не датчики телефона), вся лаборатория `lab/` (журнал, пульт, прогон, выгрузка), `LabFiles` и `LabRadioTrace` (радио игры пишет в `LabLog`, а `:radar` журнала не знает). `:clientCore` зависит от обоих модулей через `api`: их типы — часть его API (`GameSessionManager`, `LabController`). `:radar` и `:device` друг о друге не знают; связывают их игра и лаборатория.
- **Что осталось в `:composeApp`:** привязки Koin (`di/`), `BluetoothPermission` (Compose), «Поделиться» лаборатории — `AndroidLabFiles` (FileProvider) и `IosLabFiles` (`presentShareSheet`) выделены из прежних `AndroidLabPlatform.kt`/`IosLabPlatform.kt` в свои файлы. `RADAR_PERMISSIONS` переехал в `:radar` (`AndroidProximityRadio.kt`, публичный): его проверяет радио и запрашивает `BluetoothPermission`.
- **`IosPocketPulse` без ресурсов Compose:** у `:device` строк нет, тексты уведомления «ищущий рядом» приходят параметром `notificationText: suspend () -> Pair<String, String>`, привязка в `PlatformModule.ios.kt` читает их из `Res.string` в тот же момент, что и раньше (когда уведомление ставится).
- **Разрешения.** Все `<uses-permission>` по-прежнему в манифесте `composeApp` (в `androidApp` их нет). В `:device` добавлен свой манифест только с `VIBRATE` (мотор пульса и тест вибрации), чтобы lint самого модуля его видел; в приложении он и так есть, слитый манифест не меняется.
- **Причина остановки Core Haptics — именем:** `HapticStopReason.name` (`:device`, `commonMain`, тест в `commonTest`) переводит `CHHapticEngineStoppedReason` (`1 audio_session_interrupt`, `2 application_suspended`, `3 idle_timeout`, `4 notify_when_finished`, `5 engine_destroyed`, `6 game_controller_disconnect`, `-1 system_error`, иначе `unknown`); `IosLabHaptics` пишет `engine_stopped: audio_session_interrupt (1)`. `LabController` раскладывает текст на `result` (`engine_stopped`) и `reason` (`audio_session_interrupt (1)`), как в схеме radio-lab.md §4.1; раньше всё шло целиком в `result`, и отчёт остановок с iPhone не считал.
- **Границы — тестом:** `ModuleBoundariesTest` в `jvmTest` каждого модуля читает исходники всех наборов `src/*Main`: файл подпакета `<корень>.<x>` не импортирует `<корень>.<y>` (корень общий), `:radar` не импортирует `app.hovanki.device`, `app.hovanki.client`, `androidx.compose`, `:device` — `app.hovanki.radar`, `app.hovanki.client`, `androidx.compose`, `org.jetbrains.compose.resources`. Сейчас подпакет в каждом один (`lab`), правило про подпакеты — на шаг 3 (`channel/<id>`).
- **Тесты переехали с кодом:** `ActivityClassifierTest` и часть `LabPartsTest` про `CarryFeatures` (`CarryFeaturesTest`) — в `:device` `commonTest`; CI гоняет `:device:iosSimulatorArm64Test` рядом с `:clientCore`.

**Не проверено здесь:** сборка Android (`:radar`, `:device`, `:composeApp`, `:androidApp`) — в облаке нет Android SDK, собирает CI; iOS-приложение и тесты на симуляторе — на Маке. Проверено: `spotlessCheck`, `:shared:jvmTest`, `:radar:jvmTest`, `:device:jvmTest`, `:clientCore:jvmTest`, `:server:test`, `:e2e:unitTest`, метаданные `commonMain` и `iosMain` у `:radar`, `:device`, `:clientCore`, `:composeApp` (это ловит и неразрешённые `platform.*` на iOS), `:e2e:test` (весь набор).

## Последствия

- В debug-сборке много нового кода. Release не меняется: техники не из `GAME` выключены, экрана лаборатории нет.
- На боевом сервере — маршруты лаборатории за флагом и порядка 100 МБ данных на большой прогон, хранятся 90 дней.
- Выбрасываем по записанным заранее критериям, а не по ощущениям; «кладбище» хранит, за что.
- Некоторые техники при переходе в игру потянут вопросы App Store: фоновая аудиосессия (2.5.4), фоновый режим Nearby Interaction, Wi-Fi Aware (entitlement).

## Открытые вопросы

- Какие телефоны: модель и iOS второго iPhone (для UWB нужен 11+ не SE, для Wi-Fi Aware — 12+ на iOS 26), модель и версия Android (UWB, Wi-Fi RTT, Android 16).
