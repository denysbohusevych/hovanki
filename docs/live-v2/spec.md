## 1. Что меняется и что нет

**Меняется только живой канал.** Сейчас это `POST /sync` (опрос) или WebSocket v1 с JSON (ADR 0015). В v2 он
становится бинарными сообщениями `Up` и `Down` по UDP, а запасной путь — бинарный WebSocket. Сервер шлёт только то,
что изменилось с прошлого раза, который телефон подтвердил.

**Не меняется:**

- **Команды.** Создать и войти в игру, роли, старт, поимка, код, голос, настройки, доска, чат-сообщение, пауза, SOS —
  всё как сейчас: HTTPS, JSON v1, те же маршруты и ответы. Ответ команды по-прежнему несёт `GameSnapshot`.
- **Что видит игрок.** Состояние v2 собирается в тот же `GameSnapshot`, что отдаёт v1, поле в поле. Есть два
  исключения, оба без видимой разницы (§10):
  - координаты округлены до 1e-7°, а точность — до 0,1 м вверх;
  - `lastSeenMillis` у игрока «на связи» равен времени ответа.
- **Экраны приложения.** UI получает тот же `GameSnapshot` через тот же `GameConnection`.
- **v1.** Остаётся для старых приложений и как последний запасной путь.
- **Зрители открытой игры** (ADR 0011) остаются на опросе v1.

**Права и видимость те же.** Состояние v2 сервер режет из того же снимка v1, что отдал бы этому игроку
(`LiveSections.fromSnapshot`, см. [server.md](server.md)). Позже оба будут собираться из общих кусков (`LiveView`),
но и тогда одним кодом. Телефон в v2 не может получить ничего, чего не получил бы в v1.

## 2. Слова

| слово | что это |
|---|---|
| живая сессия (live session) | связь одного игрока одной игры с сервером по v2. Открывается по HTTPS, живёт до часа. Одна и та же сессия может ездить по UDP и по WebSocket v2 |
| `Up` | сообщение телефона: точки, кого слышал радар, отчёт телефона, подтверждения. Заменяет `SyncRequest` |
| `Down` | сообщение сервера: ответ на `Up` или push. Несёт изменения состояния, чат, ошибку или закрытие. Заменяет `GameSnapshot`, `Poke`, `Chat`, `Error` v1 |
| push | `Down` без запроса (`reply_to = 0`): игра изменилась. Заменяет `Poke` v1 и сразу несёт изменения |
| состояние (state) | всё, что игрок видит в игре, разрезанное на секции. У каждого состояния есть номер `state_id` |
| секция | часть состояния: игра, настройки, игроки, «я», поимки, радар… Полный список — §9 |
| целая секция | приходит целиком, когда в ней что-то изменилось |
| секция по ключам | список с id (игроки, поимки, контакты радара): приходят только изменённые элементы, удалённые id и порядок |
| дельта | `Down` с изменениями относительно состояния `base_state_id`, которое телефон подтвердил |
| полное состояние | `Down` с `base_state_id = 0`: все секции с нуля |
| датаграмма | один UDP-пакет. Внутри зашифрованное сообщение или кусок сообщения |
| `pn` | номер пакета: свой счётчик у каждой стороны в каждой сессии |

## 3. Как всё идёт

```
Телефон                                            Сервер
   | POST /api/v2/live/open  (HTTPS, токен игры)     |
   |------------------------------------------------>|  новая живая сессия: id, два ключа, адрес UDP
   |<------------------------------------------------|
   | Up{seq=1, ack_state=0, точки}       UDP :443    |
   |------------------------------------------------>|  ack_state=0 → полное состояние
   |<------------------------------------------------|  Down{reply_to=1, state_id=1, base=0, все секции}
   | Up{seq=2, ack_state=1, точки}  через 3 с        |
   |------------------------------------------------>|
   |<------------------------------------------------|  Down{reply_to=2, state_id=2, base=1, только изменения}
   |                         ...                     |  в игре что-то случилось (поимка, глоу, чат)
   |<------------------------------------------------|  Down{reply_to=0 (push), state_id=3, base=1, изменения}
   | Up{seq=3, ack_state=3}                          |
   |------------------------------------------------>|
   |<------------------------------------------------|  Down{reply_to=3, state_id=4, base=3}
```

Порядок транспорта на телефоне:

1. **UDP** на 443 — основной путь.
2. **WebSocket v2** на 443/tcp — если UDP не проходит. Та же живая сессия и те же сообщения, без шифрования поверх
   TLS.
3. **v1** — если сервер выключил v2 или WebSocket v2 тоже не работает. Сначала WebSocket v1, потом опрос.

Подробно — [client.md](client.md), §5.

## 4. Открытие живой сессии

`POST /api/v2/live/open`

- Заголовок `Authorization: Bearer <токен игрока>` — тот же токен игры, что у всех маршрутов игры v1.
- Тело и ответ — JSON (`protocolJson`). Классы `LiveOpenRequest` и `LiveOpenResponse` в `:shared`.

Запрос:

| поле | тип | что |
|---|---|---|
| `appVersion` | String | версия приложения, для метрик |
| `transports` | List<String> = ["udp", "ws"] | что умеет телефон. Неизвестные имена сервер пропускает |

Ответ `200`:

| поле | тип | что |
|---|---|---|
| `sessionId` | String | 8 случайных байт, base64url без `=`. В каждой датаграмме и в адресе WebSocket v2 |
| `upKey` | String | 16 случайных байт, base64: ключ AES-128-GCM для `Up` (телефон → сервер) |
| `downKey` | String | 16 случайных байт, base64: ключ для `Down` (сервер → телефон) |
| `resetToken` | String | 16 байт, base64: так выглядит RESET именно этой сессии (§5.5) |
| `udp` | `LiveUdpEndpoint?` | `host` и `port` (сейчас домен сервера и 443). `null` — UDP выключен (`LIVE_UDP`), только WebSocket v2 |
| `wsPath` | String | `/api/v2/live/ws` |
| `expiresAtMillis` | Long | серверное время, до которого надо открыть новую сессию. Не больше часа от открытия |
| `serverTimeMillis` | Long | часы сервера |

Ошибки (тело — `ApiError`, как в v1):

| ответ | когда | что делает телефон |
|---|---|---|
| `401` | токен не игрока этой игры | `ConnectionEvent.Ended(SESSION_REJECTED)` |
| `404` без `reason` | игры нет | `Ended(GAME_NOT_FOUND)` |
| `404` с `reason = FEATURE_DISABLED` | v2 выключен (`LIVE_V2`) | v1, повторить v2 не раньше чем через 10 минут |
| `429` с `TOO_MANY_REQUESTS` и `Retry-After` | больше `MAX_OPENS_PER_MINUTE` открытий одного игрока | ждать `Retry-After` |

Правила:

- **Ключи случайные** (`SecureRandom`, по 16 байт). Их нет ни в логах, ни в базе, ни в метриках. Каждое открытие —
  новые ключи.
- **Сессий у игрока не больше** `MAX_SESSIONS_PER_PLAYER` (3). Новая закрывает самую старую с `CLOSE_REPLACED`.
- **Старая сессия переходит в новую.** Телефон открывает новую сессию до `expiresAtMillis` (за
  `REOPEN_BEFORE_MILLIS`) и после первого `Down` новой бросает старую. Первый `Down` новой — полное состояние: дельты
  между сессиями не переносятся.
- **Сервер не помнит сессии через рестарт.** После рестарта игр нет, и открытие отвечает `404`, как и v1.

## 5. UDP

Порт: `udp.host:udp.port` из ответа на открытие, сейчас 443. Сервер слушает его на всех адресах машины.

### 5.1. Датаграмма побайтно

Все числа в заголовке — big-endian.

**DATA** — сообщение или его кусок (обе стороны):

| смещение | байт | поле | что |
|---|---|---|---|
| 0 | 1 | `type` | `0x21`: v2, DATA |
| 1 | 8 | `session_id` | id живой сессии |
| 9 | 4 | `pn` | номер пакета отправителя в этой сессии: 1, 2, 3, … |
| 13 | n | шифротекст | полезная нагрузка, зашифрованная AES-128-GCM (§5.2) |
| 13 + n | 16 | `tag` | метка AES-GCM |

**RESET** — сессии нет (только сервер → телефон, без шифрования):

| смещение | байт | поле | что |
|---|---|---|---|
| 0 | 1 | `type` | `0x22`: v2, RESET |
| 1 | 8 | `session_id` | id из датаграммы, на которую это ответ |
| 9 | 16 | `reset_tag` | `HMAC-SHA256(reset_secret, session_id)`, первые 16 байт |

**Другие значения `type`** получатель молча выбрасывает. Старший полубайт `2` — версия протокола: v3 возьмёт `0x3?`.

**Размер:** датаграмма — не больше `MAX_DATAGRAM_BYTES` (1200 байт UDP-нагрузки). Значит, открытый текст — не больше
1200 − 13 − 16 = 1171 байта. 1200 проходит почти везде; QUIC берёт ~1350 по той же причине.

**Полезная нагрузка** (открытый текст):

| байт | что |
|---|---|
| 0 | `kind`: `0x01` — MESSAGE, `0x02` — FRAGMENT |
| MESSAGE, 1… | одно сообщение protobuf: `Up` от телефона, `Down` от сервера. Не больше 1170 байт |
| FRAGMENT, 1–2 | `msg_id`: номер сообщения отправителя (uint16, по кругу) |
| FRAGMENT, 3 | `index`: 0 … `count` − 1 |
| FRAGMENT, 4 | `count`: 2 … `MAX_FRAGMENTS` (64) |
| FRAGMENT, 5… | кусок байт сообщения, не больше 1166 |

### 5.2. Шифрование

- **Алгоритм:** AES-128-GCM, метка 16 байт.
- **Ключ:** `upKey` для датаграмм телефона, `downKey` для датаграмм сервера.
- **Nonce** (12 байт): 8 нулевых байт, затем `pn` (4 байта, big-endian). Ключ у каждого направления свой, поэтому
  одинаковый `pn` в разных направлениях не повторяет пару «ключ, nonce».
- **AAD:** 13 байт заголовка (`type`, `session_id`, `pn`). Подменить заголовок нельзя.
- **Пределы ключа:** не больше 2^20 датаграмм в одну сторону и не дольше часа (`expiresAtMillis`). Это далеко от
  предела AES-GCM, 2^23 пакета на ключ (RFC 9001 §6.6). Сервер закрывает сессию с `CLOSE_REOPEN`, когда ключ подошёл
  к пределу.
- **Где шифруют:**
  - сервер и Android — `javax.crypto` (`AES/GCM/NoPadding`), есть на всех Android с minSdk 26;
  - iOS — CryptoKit `AES.GCM` через мост Swift ([client.md](client.md), §6).

  ChaCha20-Poly1305 не берём: на Android он только с API 28.

### 5.3. Номера пакетов и повторы

- **Номера.** Каждая сторона нумерует свои датаграммы DATA с 1 и прибавляет по одному. Номер не повторяется в сессии,
  даже для повторной отправки.
- **Порядок проверки у получателя:**
  1. найти сессию по `session_id`;
  2. расшифровать — не вышло: выбросить молча;
  3. проверить окно повторов: `pn` больше самого большого виденного, или ниже него не больше чем на 63 и ещё не
     виденный. Иначе выбросить;
  4. отметить `pn` в окне.

  Окно — 64 бита плюс самый большой номер, как в RFC 9147 §4.5.1.
- **Счётчик неудач.** Сервер считает датаграммы, которые не расшифровались. Больше `MAX_AUTH_FAILURES` (1000) за
  сессию — он её закрывает.
- **Порядок сообщений.** Сообщения могут прийти не по порядку или потеряться. Протокол переносит это (§8): сообщения
  не нумеруются для доставки, у каждого `Up` свой `seq`, у каждого состояния свой `state_id`.

### 5.4. Куски

- **Когда резать.** Сообщение больше 1170 байт отправитель режет на куски по 1166 байт. У кусков один `msg_id`, номера
  `index` от 0 до `count − 1`. Каждый кусок — своя датаграмма со своим `pn`.
- **Сборка.** Получатель собирает по `msg_id`. Одновременно держит не больше двух сборок, каждую — не дольше
  `FRAGMENT_TIMEOUT_MILLIS` (2 с). Пропал кусок — пропало сообщение. Повторной отправки кусков нет: протокол
  восстанавливается сам (следующий `Down` придёт относительно того, что телефон подтвердил).
- **Предел.** Больше 64 кусков (74 624 байта) не бывает: сервер должен держать каждое сообщение меньше. Самое большое
  настоящее состояние — около 20 КБ: игра на 60 игроков с доской и заданиями. Если сообщение не влезает, это ошибка
  сервера: метрика `hovanki.live.oversize` и `CLOSE_REOPEN`.

### 5.5. RESET

- **Когда сервер отвечает RESET.** На датаграмму DATA с незнакомым `session_id` (рестарт, сессия истекла), если
  выполнены все три условия:
  - в датаграмме не меньше 41 байта (заголовок + метка + 12) — тогда ответ (25 байт) меньше вопроса и не
    усиливает атаку;
  - на этот адрес не было RESET за последнюю секунду;
  - всего RESET меньше `MAX_RESETS_PER_SECOND` (100) в секунду.
- **`reset_secret`** — 32 байта из настройки `hovanki.live.reset-secret`, переменная окружения
  `HOVANKI_LIVE_RESETSECRET`. Не задана — случайный при старте; тогда телефоны после рестарта не узнают RESET и
  ждут таймаута (§5.7), а это тоже работает.
- **Телефон** сравнивает `reset_tag` с `resetToken` своей сессии за постоянное время. Совпало — сессии больше нет:
  открыть новую по HTTPS (там и выяснится, есть ли ещё игра). Не совпало — выбросить.

### 5.6. Смена адреса

Телефон меняет адрес и порт при переходе Wi-Fi ↔ мобильная сеть, а оператор — при перестройке NAT. Сервер находит
сессию по `session_id`, а не по адресу.

- **Новый адрес.** Датаграмма с другого адреса принимается, только если расшифровалась, прошла окно повторов и её
  `pn` больше всех виденных. Тогда сервер:
  - отвечает уже на новый адрес;
  - кладёт в `Down` 8 случайных байт `path_challenge`;
  - пока адрес не подтверждён, шлёт на него не больше чем втрое больше байт, чем получил с него (RFC 9000 §8).
    Если дельта в этот предел не влезает, `Down` уходит без состояния: только `ack_up` и `path_challenge`.
    Состояние подождёт подтверждения.
- **Подтверждение.** Телефон возвращает те же байты в `path_response` следующего `Up`. С этого момента адрес
  подтверждён, старый забыт.
- **Push** идёт только на подтверждённый адрес.
- **Телефон** при смене сети (Android `NetworkCallback`, iOS смена пути) открывает новый UDP-сокет и продолжает ту же
  сессию со следующим `pn`. Новую сессию открывать не надо.

### 5.7. Сколько и когда

| что | значение | зачем |
|---|---|---|
| `Up` в раунде | как v1: `syncIntervalSeconds` игры (3 с), 1 с, когда радар говорит «рядом» | уходят точки |
| `Up` в лобби и после игры | раз в `IDLE_UP_MILLIS` (10 с) | держит NAT и подтверждения |
| самый большой промежуток между `Up` | `IDLE_UP_MILLIS` (10 с) в любой фазе | NAT мобильных операторов закрывает UDP через 10–200 с, медиана 65 с (Richter, IMC 2016) |
| push | не чаще раза в `PUSH_GAP_MILLIS` (500 мс) на сессию | как `POKE_GAP` v1 |
| `Up`, на которые сервер отвечает | не больше 12 за 5 с на сессию; лишние выбрасываются | как сокет v1 |
| сервер забывает сессию | через `SESSION_IDLE_MILLIS` (60 с) без годного `Up` | телефон, который пропал |
| UDP считается непроходящим | первые 3 `Up` открытия без единого `Down` (по 1,5 с между ними) | уйти на WebSocket v2 |
| UDP сломался в игре | 3 `Up` подряд без `Down` | уйти на WebSocket v2 |
| повторить UDP после ухода на WebSocket | при смене сети или через `UDP_RETRY_MILLIS` (10 минут) | вернуться на дешёвый путь |

### 5.8. Плохие пакеты

- **Не расшифровалось, повтор, короче заголовка, незнакомый `type`** — выбросить молча. Отвечать нельзя: ответ на
  неподтверждённый пакет — это усилитель для чужой атаки.
- **Незнакомый `session_id`** — RESET по правилам §5.5, иначе молчать.
- **Расшифровалось, но protobuf не разбирается** — выбросить и посчитать в `hovanki.live.bad_message`. Сессию не
  закрывать.

## 6. WebSocket v2

Запасной путь, когда UDP не проходит: офисный Wi-Fi, гостиничные сети, часть VPN.

- **Адрес:** `GET wss://<сервер><wsPath>?s=<sessionId>`.
- **Заголовки:**
  - `Authorization: Bearer <токен игрока>`;
  - `Sec-WebSocket-Protocol: hovanki.live.v2` — сервер подтверждает его же.
- **Кадры** бинарные. Один кадр — одно сообщение protobuf: `Up` от телефона, `Down` от сервера. Без своего
  шифрования (его даёт TLS), без `pn` и без кусков. Не больше `MAX_WS_FRAME_BYTES` (128 КБ).
- **Сессия та же.** WebSocket цепляется к уже открытой живой сессии, база дельт не теряется. Пока WebSocket открыт,
  push идёт в него. Когда снова приходит годный UDP, сессия возвращается на UDP (с подтверждением адреса, §5.6), а
  WebSocket закрывается с кодом `1000`.
- **Коды закрытия** (как v1, плюс один):

  | код | значение | `Close.reason` в UDP |
  |---|---|---|
  | 4401 | токен не игрока | `CLOSE_SESSION_REJECTED` |
  | 4404 | игры нет | `CLOSE_GAME_NOT_FOUND` |
  | 4429 | слишком часто | `CLOSE_TOO_MANY` |
  | 4503 | v2 выключен | `CLOSE_FALLBACK_V1` |
  | 4410 | открыть новую сессию по HTTPS (нет такой сессии, истекла, заменена) | `CLOSE_REOPEN`, `CLOSE_REPLACED` |

- **Простой.** Сервер закрывает WebSocket без `Up` дольше `SESSION_IDLE_MILLIS`. Телефон шлёт `Up` не реже
  `IDLE_UP_MILLIS`.

## 7. Сообщения Up и Down

Поля — в [live_v2.proto](../../shared/src/commonMain/proto/live_v2.proto), с комментариями. Здесь правила, которых в схеме не видно.

### 7.1. Up: что кладёт телефон

| поле | правило |
|---|---|
| `seq` | 1, 2, 3, … в живой сессии. Повторная отправка — новый `Up` с новым `seq`. Не сбрасывается при смене транспорта |
| `ack_state` | самый новый `state_id`, который телефон применил. 0 — ничего (сервер пришлёт полное состояние) |
| `time_ms` | `ServerClock.now()` в момент сборки `Up`. От него считаются все `t_ms` |
| `fixes` | все точки из `LocationOutbox`, которые сервер ещё не подтвердил, старые первыми, до 100. Остаются в очереди, пока не придёт `Down` с `ack_up ≥ seq` этого `Up`. Повторная точка серверу не вредит: `LocationTrack` выбрасывает точку не новее последней |
| `sightings` | кого радар услышал с прошлого `Up`, до 200. Ровно один раз, даже если `Up` пропал: как и в v1, старый сигнал радара ничего не стоит |
| `device` | отчёт телефона (`DeviceReport`), когда он отличается от последнего подтверждённого. Повторяется в каждом `Up`, пока не придёт `ack_up ≥ seq` того `Up`, где он изменился. Нет поля — без изменений |
| `chat_after` | курсор чата, как `SyncRequest.chatAfter`. Нет поля — телефон без чата |
| `path_response` | эхо последнего `Down.path_challenge` (только UDP) |
| `full` | у телефона нет базы, которую просит сервер (§8.3): прислать полное состояние |

**Что делает сервер с `Up`:**

1. **Устаревший `Up`.** `seq` не больше самого большого обработанного: учесть только `ack_state` и `path_response`,
   точки и отчёт не применять, не отвечать. Такой `Up` обогнали: у следующего те же точки и отчёт.
2. **`device`.** Пришёл — запомнить в сессии. Сервер хранит последний отчёт сессии и передаёт его игре с каждым
   `Up`, как v1 передаёт `SyncRequest.device` с каждым опросом. Так правила, которые ждут отчёт не реже 20 с
   (`DEVICE_REPORT_TTL_MILLIS`), работают без изменений.
3. **Синхронизация.** `GameService.sync` с теми же данными, что v1 (`samples`, `chatAfter`, `nearby`, `device`).
   Тот же замок, те же правила, тот же `lastSeen`.
4. **Ответ.** `Down` с `reply_to = seq`, `ack_up = seq` и дельтой относительно базы (§8.2).

### 7.2. Down: что кладёт сервер

| поле | правило |
|---|---|
| `reply_to` | `seq` того `Up`, на который ответ. 0 — push |
| `ack_up` | самый большой обработанный `seq` |
| `server_time_ms` | всегда |
| `state_id`, `base_state_id`, `state` | §8. `state_id = 0`: состояния в этом `Down` нет |
| `chat`, `chat_push`, `chat_more` | §11 |
| `error` | `Up` с `seq = reply_to` отказан, сессия жива (§13) |
| `close` | сессия кончилась (§13). После `close` сервер по этой сессии больше ничего не шлёт |
| `path_challenge` | §5.6 |

## 8. Состояние и дельты

### 8.1. Номера состояний

- **Счётчик.** У живой сессии свой счётчик `state_id`: 1, 2, 3, … Каждый `Down` с состоянием берёт следующий номер,
  ответ это или push.
- **Новое состояние.** `state_id = N` с `base_state_id = B` означает: состояние N — это состояние B плюс секции этого
  `Down`. `B = 0` — с нуля.
- **Номера только растут.** Телефон показывает состояние с самым большим номером, какое у него есть. Пришло состояние
  старше показанного (UDP переставил пакеты) — телефон его сохраняет (§8.3), но не показывает.

### 8.2. Что хранит сервер

Сервер хранит на сессию:

- **Последние отправленные состояния** — до `SERVER_STATES_KEPT` (4) штук. Подтверждённое (`acked`) не выкидывается,
  пока оно подтверждённое: выкидывается самое старое из остальных. Так серия push без ответа не скатывается в полные
  состояния. Не содержимое, а 64-битный хеш каждой
  секции, а в секциях по ключам — хеш каждой части каждого элемента и хеш списка id по порядку.
- **`acked`** — самый большой номер, который телефон подтвердил (`Up.ack_state`), если он ещё среди хранимых. Подтверждение меньше уже известного (`Up` пришёл позже другого) его не уменьшает.

Как сервер собирает `Down`:

1. **База.** `base = acked`. Подтверждения нет, или его номер уже выпал из хранимых, или `Up.full` — `base = 0`.
2. **Текущее состояние.** Собрать секции для этого игрока (`LiveView`) и закодировать каждую.
3. **Что изменилось.** В `Down` идёт каждая секция, хеш которой отличается от хеша в базе. В секции по ключам —
   только изменённые части элементов, удалённые id и порядок (§8.5). При `base = 0` идут все секции, кроме тех, что
   равны своему нулю (телефон применяет полное состояние к пустому, §8.6), все элементы и порядок каждой секции по
   ключам.
4. **Пустая дельта.** Ничего не изменилось относительно базы, и последнее отправленное состояние — сама база:
   `Down` без состояния (`state_id = 0`). Иначе — новое состояние, даже пустое. Пустое означает «как база», и
   телефон применяет его поверх базы. Без этого правила телефон мог бы остаться на более новом push, которого сервер
   уже не держит в правде.
5. **Запомнить.** Новые хеши — как состояние с новым номером, самое старое из хранимых выкинуть.

Хеш — xxHash64 закодированных байт секции (или части элемента). Хеши есть только на сервере, телефон их не
считает. Случайное совпадение у 64-битного хеша на практике невозможно (2^-64 на сравнение).

### 8.3. Что хранит телефон

- **Состояния.** Последние `CLIENT_STATES_KEPT` (8): номер → все секции. Секции хранятся уже разобранными, а не
  байтами.
- **Применение `Down` с состоянием:**
  - `base_state_id = 0` — новое состояние с нуля;
  - база есть среди хранимых — копия базы плюс секции `Down`;
  - базы нет — `Down` выбросить и в следующем `Up` поставить `full = true`.
- **Подтверждение.** `ack_state` следующего `Up` — самый большой номер среди применённых.
- **Новая сессия** (новое открытие) — все состояния забыть.

### 8.4. Целые секции

- **В дельте.** Секция есть — заменить ею старую целиком. Секции нет — без изменений.
- **«Пусто» и «нет».** У каждой целой секции значение «пусто» выражено её полями: `MeSection.radar_on = false`,
  `CountsSection.shown = false`, пустой список. Секция никогда не «удаляется».

### 8.5. Секции по ключам

`PlayersSection`, `CatchesSection`, `RadarSection`. У каждой три поля:

| поле | что |
|---|---|
| `upsert` | новые и изменённые элементы |
| `remove` | id, которых больше нет |
| `order` | все id в порядке v1. В полном состоянии всегда. В дельте — когда правило телефона (п. 3 ниже) дало бы другой порядок; если порядок получается сам, сервер может его не слать |

Как применять:

1. **Удалить** элементы из `remove`.
2. **Для каждого элемента из `upsert`:**
   - id новый — элемент как есть; отсутствующая часть = её ноль (для игрока: `roster` есть всегда, `presence` —
     «на связи», `location` — не виден);
   - id уже есть — заменить только присланные части, остальные не трогать.
3. **Порядок.** `order` есть — расставить элементы по нему. Нет — порядок прежний, новые элементы в конец.

   Сервер обязан прислать `order`, если новый элемент встал не в конец. Если `order` назвал id, которого нет,
   состояние испорчено: выбросить `Down` и попросить `full`.

У игрока три части с отдельными хешами, потому что меняются они с разной частотой:

| часть | что внутри | меняется |
|---|---|---|
| `roster` | имя, роль, статус, аккаунт, когда выбыл, кем пойман, ушёл, возможности телефона, искры | редко |
| `presence` | когда был на связи, только если молчит дольше 20 с | когда пропал и когда вернулся |
| `location` | видимая позиция и почему видна | каждые несколько секунд у тех, кого видно |

### 8.6. Алгоритм телефона целиком

```
on Down d:
  clock.onServerTime(d.server_time_ms)
  if d.close != null: закончить (§13)
  if d.ack_up > 0: outbox.ackUpTo(d.ack_up); device.ackUpTo(d.ack_up)
  if d.error != null: событие Problem (§13)
  if d.state_id != 0:
      base = d.base_state_id == 0 ? empty : states[d.base_state_id]
      if base == null: needFull = true; return
      s = base.copy().apply(d.state)          // §8.4, §8.5
      states[d.state_id] = s; оставить 8 самых новых
      if d.state_id > shownId: shownId = d.state_id
  chat.merge(d.chat)                          // §11
  if d.server_time_ms >= lastEmitted: emit Snapshot(toGameSnapshot(states[shownId], d.server_time_ms))
  if d.chat_more: отправить Up сейчас
```

`Snapshot` уходит на каждый `Down` с состоянием или без, как v1 отдаёт снимок на каждый опрос. Каждый такой снимок — правда сервера на момент `server_time_ms`: состояние в `Down` — это база плюс всё, что изменилось к этому моменту, а `Down` без состояния бывает, только когда ничего не изменилось (§8.2). Поэтому правило приложения «из двух снимков новее тот, у кого больше `serverTimeMillis`» (`GameSessionManager.isOvertaken`) работает и для ответов команд, и для v2.

### 8.7. Push

- **Когда.** Игра собирает, кого касается изменение (`Pokes`, как в v1). После замка сервер шлёт каждой такой живой
  сессии push: `Down` с `reply_to = 0` и дельтой от `acked`, по правилам §8.2.
- **Как часто.** Не чаще `PUSH_GAP_MILLIS` (500 мс) на сессию; изменения за это время уходят одним push.
- **Подтверждение.** Push не ждёт ответа. Телефон подтверждает его в своём следующем `Up` через `ack_state`.
- **Чем лучше v1.** В v1 `Poke` заставлял телефон спросить снимок: два пути по сети вместо одного.

## 10. Кодирование значений

| значение | как | обратно |
|---|---|---|
| широта, долгота | E7: `round(deg × 10^7)`, половина — от нуля; `sint32` | `e7 / 10^7` |
| точность | дециметры вверх: `ceil(m × 10 − 10⁻⁶)`; `uint32`. Запас 10⁻⁶ — чтобы целые дециметры не уходили вверх из-за двоичной дроби (0,7 м × 10 = 7,000000000000001); меньше нуля и NaN — 0 | `dm / 10.0` |
| время | серверное, мс эпохи; внутри секций абсолютное, в `Up` — смещение от `Up.time_ms` (`sint64`) | — |
| точки в `Up` | первая абсолютная, каждая следующая — разность с предыдущей той же `Up` | сложить по порядку |
| токен радара | 8 строчных hex → 4 байта big-endian, `fixed32` | обратно в 8 строчных hex |
| секреты (`catch_code_secret`, `radar_secret`) | hex → байты | строчный hex |
| id (игры, игрока, поимки, аккаунта) | строка как в v1 | — |
| nullable-строка v1 | пустая строка = null | — |
| `onScreen` | наоборот: `off_screen`, чтобы ноль был значением v1 по умолчанию | `!off_screen` |
| перечисления | 0 = значение v1 по умолчанию (или null для nullable) | таблицы в `.proto` |
| редкие большие структуры (настройки, доска, задания, перки, вместимость, большая игра) | JSON `protocolJson` как есть, в `bytes` | `protocolJson.decodeFromString` |

Почему округление не меняет игру:

- 1e-7° — это 1,1 см, а точность GPS — метры.
- Округление точности вверх никогда не делает точку точнее. Если в v1 точка не годилась
  (`accuracy > maxUsableAccuracyMeters`), в v2 тоже не годится. Правила на сервере работают с тем, что пришло от
  телефона, а телефон шлёт уже округлённое.
- Тест равенства (§18) сравнивает v1 после того же округления.

Почему JSON внутри `bytes` для редких секций:

- Схемы `GameSettings` (с `GameRules` на 30+ полей), `BoardItem`, `QuestView`, `PerkView` не дублируются в `.proto` и
  развиваются по правилам v1.
- Они приходят раз за сессию или при редком изменении, так что на трафик это почти не влияет.
- `encodeDefaults = true`, как у `protocolJson`: если новый сервер поменяет значение по умолчанию, старый телефон всё
  равно получит настоящее значение.

## 11. Чат

- **Как в v1.** `Up.chat_after` — курсор. `Down.chat` несёт сообщения новее него, старые первыми. Телефон сливает их
  по `seq`, как сейчас.
- **Предел на `Down`** — `MAX_CHAT_BYTES` (8 КБ), не 100 сообщений, как в v1: 100 длинных сообщений не влезут в разумную
  датаграмму. Что не влезло, ждёт следующего `Up`, а `Down.chat_more = true` просит телефон прислать его сразу. Одно
  сообщение уходит всегда: оно короче предела (`ChatRules.MAX_LENGTH`, 300 символов).
- **Push чата.** Новое сообщение сервер шлёт сразу push-ем с `chat_push = true`, без состояния, как `ServerFrame.Chat`
  v1. Такой `Down` курсор телефона не двигает: если push потерялся, сообщение придёт со следующим `Up`. Push чата
  получают все сессии v2 — заголовок `X-Hovanki-Frames` не нужен.
- **Отправка сообщения** — по-прежнему `POST` по HTTPS (команда).

## 12. Время

- **Часы.** `Down.server_time_ms` есть в каждом `Down`. В v2.0 телефон считает сдвиг часов как v1: `ServerClock`
  берёт `server_time_ms` каждого `Down` и не учитывает задержку сети.
- **Улучшение на потом.** `reply_to` даёт время пути туда и обратно: ответ сравнить с моментом отправки `Up` этого
  `seq`. Сдвиг можно считать как NTP: `server_time + rtt/2 − время приёма`, по самому быстрому из последних
  ответов. Это отдельный шаг после v2.0: он меняет поведение часов, а v2.0 повторяет v1.
- **Время внутри секций** — абсолютное и от момента `Down` не зависит (§10). Иначе хеш секции менялся бы в каждом
  `Down`.

## 13. Ошибки и закрытие

**`Down.error`** — отказ одного `Up`, сессия жива. Поля как у `ApiError` v1, плюс `retry_after_s`.

| случай | `code`, `reason` | что делает телефон |
|---|---|---|
| больше 100 точек или 200 сигналов | `BAD_REQUEST` | `Problem`; такого быть не должно |
| слишком часто | `BAD_REQUEST`, `TOO_MANY_REQUESTS`, `retry_after_s` | подождать |
| ошибка сервера | `INTERNAL` | `Problem`, следующий `Up` по расписанию |

**`Down.close`** — сессия кончилась. По UDP сервер шлёт его один раз в ответ на очередной `Up`.

| `reason` | что делает телефон |
|---|---|
| `CLOSE_SESSION_REJECTED` | `ConnectionEvent.Ended(SESSION_REJECTED)` |
| `CLOSE_GAME_NOT_FOUND` | `Ended(GAME_NOT_FOUND)` |
| `CLOSE_REOPEN`, `CLOSE_REPLACED` (и незнакомая причина) | открыть новую живую сессию по HTTPS |
| `CLOSE_TOO_MANY` | открыть новую не раньше `retry_after_s` |
| `CLOSE_FALLBACK_V1` | перейти на v1, не пробовать v2 10 минут |

Когда игрок выбыл, ушёл или игра закончилась, сессия **не** закрывается: это изменения состояния, как в v1. Сессия
закрывается, только когда токен перестал быть токеном игрока (401 v1) или игру удалили (404 v1).

## 15. Как протокол меняется дальше

**Можно без новой версии:**

- новое поле в любом сообщении — со следующим свободным номером. Старый телефон его пропустит (Wire хранит
  незнакомые поля), старый сервер тоже;
- новая секция — новое поле в `State`. Старый телефон её не увидит, и это должно быть безопасно: значит, без неё
  старый телефон показывает то же, что показывал;
- новое значение перечисления — только если «0» на старом телефоне — приемлемое чтение. Иначе новое поле рядом, как
  `cause` рядом с `reason`;
- новое поле внутри JSON-секции — по правилам v1 (с значением по умолчанию).

**Нельзя:**

- менять номер или тип поля;
- переиспользовать номер (удалённые — в `reserved`);
- менять смысл нуля;
- делать в `Up` что-то обязательным для старого сервера.

**Новая версия протокола** — `type` датаграммы `0x3?`, `/api/v3/live/…`, подпротокол `hovanki.live.v3`. v2 живёт,
пока его используют.

**Другие виды игр (ADR 0005).** Номера 20–29 в `Up` и `Down` оставлены под состояния других видов. Состояние
пряток — `Down.state` (6). Общие для платформы куски (чат, время, подтверждения, закрытие) уже лежат вне `State`.

## 16. Безопасность и приватность

- **Конфиденциальность.** Всё, что едет по UDP, кроме заголовка и RESET, зашифровано AES-GCM ключами, которые телефон
  получил по TLS. Заголовок не секрет, но защищён как AAD.
- **Подделка.** Без ключа нельзя подделать ни `Up`, ни `Down`. Отвечать на неподтверждённые пакеты сервер не может
  (§5.8). RESET подделать нельзя без `reset_secret` сервера.
- **Повторы** отсекает окно (§5.3). Старый `Up`, пришедший позже, ничего не меняет (§7.1).
- **Усиление.** Ответ на незнакомый адрес — не больше трёх его байт, пока адрес не подтверждён (§5.6). RESET меньше
  вопроса и ограничен по частоте (§5.5).
- **Что видно игроку** — ровно что в v1: v2 режется из снимка v1 (позже оба — из `LiveView`). Проверки:
  - тест равенства на сервере;
  - `SnapshotAudit` в e2e на снимках, собранных из v2.
- **Логи.** Нельзя логировать ключи, `resetToken`, `reset_secret`, токены игры и содержимое `Up` и `Down`
  (координаты, чат). `session_id` можно только в отладке, он не секрет, но и пользы в логах от него нет. Метрики — счётчики
  без игроков: байты, датаграммы, потери по пропускам `pn`, причины закрытия, переходы UDP → WebSocket → v1.
- **Персональные данные** живут в памяти и умирают с сессией и игрой, как в v1. v2 ничего нового не хранит.

## 17. Пример обмена

Сеть: телефон на Wi-Fi, потом уходит на мобильную сеть.

1. **Открытие.** `POST /api/v2/live/open` → `sessionId = obLD1OX2Bxg`, ключи, `udp = {host: hovanki.duckdns.org,
   port: 443}`.
2. **Первый `Up`.** `Up{seq 1, ack_state 0, time_ms T, fixes [2], sightings [1], chat_after 0}`: 54 байта protobuf,
   84 байта датаграмма (§18).
3. **Полное состояние.** `Down{reply_to 1, ack_up 1, state_id 1, base 0, state: все 13 секций, chat: 12 сообщений}`.
   Для лобби на 10 игроков это около 3 КБ — три куска.
4. **Через 3 с.** `Up{seq 2, ack_state 1, fixes [3]}` (точки первого `Up` подтверждены, их больше нет) →
   `Down{reply_to 2, ack_up 2, state_id 2, base 1}` без секций. В лобби обычно ничего не меняется.
5. **Хост меняет роли.** Сервер шлёт push: `Down{reply_to 0, state_id 3, base 1, players: upsert двух игроков с одной
   частью roster}`. Около 60 байт.
6. **Переход на мобильную сеть.** Следующий `Up{seq 3, ack_state 3}` приходит с нового адреса:
   - сервер отвечает туда `Down{… path_challenge: 8 байт}`, не больше 3× размера `Up`;
   - `Up{seq 4, path_response}` подтверждает адрес;
   - дальше всё как раньше.
7. **Раунд.** Каждые 3 с: `Up` 60–150 байт (1–3 точки, сигналы радара) и `Down` 80–300 байт (позиции видимых,
   контакты радара, «я»). Против 6,5–10,6 КБ снимка v1.
